## How to write an entry

Append one entry per merged task, newest at the bottom. **Twelve lines or fewer.** The spec's *As built* footer owns the full account of what deviated and why; this entry is the index — what happened, and where each lesson was filed. (The archived logs average 7 KB an entry against a template that said "one line"; the cap is what keeps this file readable.)

```markdown
### YYYY-MM-DD · M0-03 · Domain events
**Built:** one or two lines — what exists now that didn't.
**Deviations:** none | *n*, in the spec's As built. Name here only one that changes a decision.
**Learned:** one line each, ending with where it was filed — Traps §n · AR §18.x · ledger row n · spent (stays here).
**Follow-ups:** tasks created, ledger rows added, or "none".
```

The PR number lives in the merge commit — do not write it here. Current State is written **as of the PR's merge**: the task the PR closes is *Last merged*. If a deviation changes a decision in `Architecture.md`, it needs a superseding ADR — say so here and link it.

**A durable lesson does not go in Current State.** A toolchain trap goes in [Traps.md](../Traps.md); a rule the code now depends on goes in [Architecture.md §18](../Architecture.md#18-invariants); a thing a named task must handle goes in the [carry-forward ledger](ROADMAP.md#carry-forward-into-m2), and one with no owner yet in the ROADMAP parking lot, one line. The entry says *what happened*, and links.

**At the end of a milestone**, move its entries to `archive/PROGRESS-M<n>.md`, promote anything durable out of them first, and leave this Log holding only the milestone in progress.

### 2026-09-11 · M2-00e · Specs for M2-13…M2-15, persistence, resume and acceptance

**Built:** the last five specs of M2, and with them the milestone is detailed before its `-01` starts — the rule kept on time, which is what M2-00a and M2-00f existed to make possible. Persistence as a port and two `readonly struct` DTOs ([M2-13a](tasks/M2-13a-save-port-and-dtos.md)); a JSON file written atomically that refuses a version it cannot read ([M2-13b](tasks/M2-13b-local-json-save-store.md)); a run on disk from its first frame and rewritten at every boundary ([M2-14a](tasks/M2-14a-snapshot-at-the-boundary.md)); a `Continue` that lands in the same arena with the same waves and the health the player had ([M2-14b](tasks/M2-14b-resume-and-continue.md)); and an acceptance task that closes the ledger row by row ([M2-15](tasks/M2-15-acceptance-and-tag.md)).
**Two splits, decided before the tasks start.** M2-13 was eight files: the port and the DTOs are a review about *what a run is*, the JSON and the migration harness about *how it is spelled on disk*, and the second cannot be judged until the first is settled. M2-14 splits at the write/read seam — everything through 14a is verifiable by looking at a file, while 14b is the menu, the container and the `RunConfig` sweep.
**Deviations:** none from the brief. Seven files — the five specs plus the two plan files the protocol requires the same change to update, which is M2-00b's and M2-00d's arithmetic. Two questions went to the owner rather than being guessed, and both came back as recommended: ledger row 1's shape, and what a resume is allowed to give back (a stage restarts whole; the rewind that implies is the ordinary checkpoint one, named rather than engineered around before a phone exists).
**Learned:** **writing the spec is what found the hole.** A boundary-only write leaves the *previous* run's file on disk for the whole of a fresh run's first stage, so a phone call during stage 1 resumes a run nobody is playing; the fix is an opening write in `RunSession.Start`, cheaper than a menu that deletes the file and durable from the first frame instead of the first door → M2-14a rules 1–2. **An invariant that names one class is one refactor from decorative:** `RunRecorder` must hold the `IClock` that `Core.Run` is forbidden, so M2-01's `RunSession_TakesNoClock` is widened to the whole namespace rather than worked around → M2-14a rule 12. **Nullable reference types are off project-wide**, so AR §10.3's `Task<RunSnapshot?>` compiles only if the DTOs are value types — an ambiguity in the architecture read as a constraint → M2-13a rule 2. And `in` is banned on the port's parameters, because an `async` method cannot take one and ADR-0007 says an async implementation is coming → M2-13a rule 3.
**Follow-ups:** ledger rows 1, 6, 10 and 11 now name the split tasks that own them, each with the *how*; row 1 leaves on **M2-14b**'s *As built*, not M2-13a's. M2-15 owns closing the table and opening M3's.

### 2026-09-07 · M0-02 · `StateMachine<T>` and the core-purity guard test · PR #_n_

**Built:** `StateMachine<TState>` in `Soulvail.Core` — the one flat FSM behind game flow, enemy AI and boss phases — with deferred in-handler transitions and an allocation-free `Tick`. Alongside it the test suite's foundations: `AllocationAssert` (the single way every later spec claims "allocates nothing") and `AssemblyPurityTests`, which fails the build if `Soulvail.Core` ever gains an engine reference. 15 EditMode tests, all green. `Soulvail.Core` and `Soulvail.Tests.Core` now emit assemblies and the Test Runner lists them, as M0-01 predicted it would once scripts existed.

**Deviations from spec:** three.

1. **Unity 6.3 compiles at C# 9, so file-scoped namespaces did not build.** CLAUDE.md and `.editorconfig` both mandate them, and the spec's Public API block is written with one — a conflict that could not surface until the first `.cs` file. Owner chose to keep the convention: a one-line `csc.rsp` (`-langversion:10`) now sits beside **all five** asmdefs. Verified per-assembly: a `csc.rsp` beside an asmdef raises only that assembly, and `Assets/csc.rsp` would not have covered asmdef assemblies at all. This is why the file list is 10 rather than 5.
2. **`AllocationAssert` uses Unity's GC recorder, not the two strategies the spec prescribes.** Both were measured and are inert on this runtime — see *Learned*. The public API (`None(Action, int iterations = 10_000)`) is unchanged.
3. **A fifth file, `Tests/Core/Support/AllocationAssertTests.cs`.** The spec's Tests table mandates `AllocationAssert_DetectsAllocation` and `AllocationAssert_PassesForPureBody`, but its Files table gives them no fixture to live in. Filing them under the purity or state-machine fixtures would have been dishonest naming, so they got the file their names imply.

**Learned:**

- **On Unity's Mono, `GC.GetAllocatedBytesForCurrentThread()` is stubbed — it returns 0 always, even either side of a deliberate allocation — and `GC.CollectionCount(0)` did not move across 100 000 object allocations** (~2.4 MB, inside SGen's nursery). Both of the spec's strategies therefore report "no allocation" for code that allocates freely. The first implementation followed the spec, and `AllocationAssert_DetectsAllocation` caught it: the helper failed to detect `new object()` in a loop. Had that self-test not been specced, every "allocates nothing" claim in the project would have been vacuous — worth remembering when specifying future guard tests. `AllocationAssert` now measures with `UnityEngine.TestTools.Constraints.Is.Not.AllocatingGCMemory()`, which is real. **No future spec should hand-roll a BCL GC probe.**
- `Tick` deliberately caches the current state's tick handler list on transition instead of looking it up in a `Dictionary<TState, …>` per tick. Enum-keyed dictionary lookups can box on some runtimes; caching sidesteps the question entirely and keeps rule 8 true by construction rather than by hope.
- Unity's bundled NUnit has no `Assert.Multiple` — sequential asserts instead.
- **The pre-commit format check was failing open-loop on a phantom violation, and is fixed here.** This machine has a .NET *runtime* but no SDK, so `dotnet` is on `PATH` while `dotnet format` does not exist. The hook probed `command -v dotnet`, got a hit, ran the check, and read its "No .NET SDKs were found" exit code as a formatting difference — blocking the first commit that ever staged a `.cs` file. It now probes `dotnet format --version`, so it skips honestly. The five files were independently verified against `.editorconfig` by hand (no tabs, no trailing whitespace, 4-space indents, LF, final newline). CLAUDE.md's "the check self-skips" is true again.
- The Unity MCP `RunCommand` wraps submitted code in a `Unity.AI.Assistant.…` namespace. Two consequences for later sessions: `CompilationPipeline` must be fully qualified or it resolves to `Unity.CompilationPipeline`, and **nested classes get duplicated outside their parent by the code-fixer** — declare helper classes at top level. `TestRunnerApi` results were captured by writing to `Temp/` from `RunFinished`, which survives the domain reload the run triggers.

**Follow-ups:** none.

### 2026-09-07 · M0-03 · Domain events · PR #_n_

**Built:** The first port, and the first thing on both sides of the hexagon at once. `IDomainEvents` in `Soulvail.Core.Ports` is how core says what happened without learning who listens; `DomainEventHub` in `Soulvail.Game.Adapters` is its run-scoped typed dispatcher — subscribe/unsubscribe by handle, allocation-free publish, no statics; `RecordingEvents` in `Soulvail.Tests.Core.Fakes` is the fake every later core test will assert event sequences through. 13 new EditMode tests, 28 in the suite. `Soulvail.Game` and `Soulvail.Tests.Game` now emit assemblies for the first time.

**Deviations from spec:** three.

1. **A fifth file, `Tests/Core/Fakes/RecordingEventsTests.cs`.** The Files table names one test file, in `Soulvail.Tests.Game`, but two of the Tests table's rows test `RecordingEvents`, which lives in `Soulvail.Tests.Core` and is not a hub. Filing them under a fixture named for the hub would have been dishonest naming — the same gap M0-02 hit, resolved the same way, and the owner approved it before implementation.
2. **`Soulvail.Tests.Game` now references `Soulvail.Tests.Core`.** `Publish_AfterWarmup_AllocatesNothing` is specced into the Tests.Game fixture, but `AllocationAssert` lives in Tests.Core and was out of reach. Both assemblies are Editor-only under `UNITY_INCLUDE_TESTS`, so the reference is safe, and it is what keeps the project's one allocation probe single-sourced rather than copied.
3. **The allocation row's "allocated-bytes delta == 0" is measured with `AllocationAssert` instead.** That phrasing describes exactly the BCL probe M0-02 proved inert on this runtime. Behaviour rule 8 is what the test enforces; the wording was stale, not the rule.

**Learned:**

- **A `Unity_RunCommand` script is refused with *"User interactions are not supported for MCP tool calls"* if it calls anything in `RunCommandCodeAnalyzer.k_UnsafeMethods`** — `System.IO.File.Delete`, `File.Move`, `Directory.Delete`, `AssetDatabase.DeleteAsset`, `FileUtil.DeleteFileOrDirectory`. Those mark the command unsafe, which requires a user confirmation, and MCP callers get `NoOpToolInteractions`, whose only job is to throw that message. Three attempts to start the EditMode run failed this way because each cleared its result file with `File.Delete` first; dropping the delete and overwriting with `File.WriteAllText` (a write, not an unsafe call) runs the suite fine. **`TestRunnerApi.Execute` was never blocked** — the first diagnosis blamed it because the probes that worked differed in the file call too. Separately, `System.Net`, `System.Diagnostics`, `System.Runtime.InteropServices` and `System.Reflection` really are unauthorized namespaces for submitted scripts. The lesson for later sessions is the diagnosis, not the guard: when an MCP command is refused, change one thing at a time.
- `Publish` walks the live handler list and **defers mutations** instead of snapshotting it. Snapshotting at the top of every publish is the obvious way to satisfy "the in-flight publish sees the list as it was", and it allocates on every publish, which breaks rule 8. Deferring costs nothing on the hot path — the pending queue is only touched when someone actually subscribes or unsubscribes from inside a handler — and it makes re-entrancy fall out for free: a handler that republishes the same type walks the same untouched list. Verified with a re-entrancy check beyond the spec's rows.
- Channels are created by `Subscribe`, never by `Publish`, so publishing an event nobody listens for allocates nothing **ever**, not merely nothing after the first time. Rule 8 asked for the weaker guarantee.
- A single throwing handler is rethrown through `ExceptionDispatchInfo` rather than `throw ex`, which would erase the stack trace of the listener that actually failed.
- `RecordingEvents.Clear()` is in the spec's Public API but has no row in its Tests table. Covered by the ad-hoc harness during verification, not by a fixture — worth a row if the fake ever grows.

**Follow-ups:** none.

### 2026-09-07 · M0-04 · Random streams · PR #_n_

**Built:** The second port, and the thing that makes a seeded run mean something. `IRandom` + `IRandomStream` in `Soulvail.Core.Ports` expose five independent streams — Spawn, Offers, Affixes, Drops, Misc — so adding a mechanic that rolls dice in one concern cannot shift another's sequence. `SeededRandom` in `Soulvail.Game.Adapters` is the real generator: PCG32 per stream, each seeded from `(seed, streamIndex)` through SplitMix64, allocation-free on every draw. `FixedRandom` in `Soulvail.Tests.Core.Fakes` is the scripted counterpart every later core test will roll through. 14 new EditMode tests, 42 in the suite. Nothing consumes randomness yet — that is M0-10 onward.

**Deviations from spec:** five. The first two were put to the owner and approved before implementation.

1. **A fifth file, `Tests/Core/Fakes/FixedRandomTests.cs`.** The Files table names one test file, in `Soulvail.Tests.Game`, but two of the Tests table's rows test `FixedRandom`, which lives in `Soulvail.Tests.Core`. Third task running into the same gap (M0-02, M0-03), resolved the same way. Five files is still size M, so no split was triggered.
2. **`FixedRandom.SetStream(string name, …)` became five named setters** — `SetSpawn`, `SetOffers`, `SetAffixes`, `SetDrops`, `SetMisc`, each returning `this` so they chain. Compile-time checked, no new type anywhere, and shorter at the call site. The decisive point was timing: nothing in the project draws a random number yet, so the specced signature had zero callers and changing it cost nothing. After M2's director it would have been spread across every spawn and offer test.
3. **A test beyond the Tests table: `FixedRandom_SetStream_OverridesOnlyThatStream`.** The Public API's "every stream is the same scripted stream unless set individually" is a behaviour with no row, and it is the half of the fake that deviation 2 reshaped. It also pins the consequence worth knowing: the un-overridden streams are *one instance*, so a draw from `Offers` advances `Drops` too.
4. **`Draw_AllocatesNothing` is measured with `AllocationAssert`, and covers all four draws.** The row's "allocated-bytes delta == 0" describes the BCL probe M0-02 proved inert here — same stale wording M0-03 hit. Rule 8 says *no allocation per draw*, and `NextInt` is where a boxed comparer or a widening conversion would most easily creep in, so `NextFloat`, `NextInt`, `Range` and `Chance` are each measured.
5. **`FixedRandom.Seed` returns 0.** `IRandom` requires the property; the spec gives the fake no seed constructor. Nothing reads it.

**Learned:**

- **Per-stream seeds go through SplitMix64 rather than the raw seed, and that is what makes rule 3 true rather than merely hoped-for.** Seeding several PCG generators from adjacent values (seed+0, seed+1, …) correlates their early output — the streams would drift apart eventually but not on the first few draws, which is exactly where a wave composer looks. SplitMix64 is an avalanche mix, so one bit of difference scatters the whole 64-bit state. Both derived words are used: the first becomes the generator's state, the second its increment, which selects *which* of PCG's 2^63 sequences the stream walks. `DifferentSeed_DifferentSequence` deliberately tests seeds 1 and 2, the hard adjacent case, not 1 and 9999.
- **The stream indices are part of what a seed means.** Renumbering Spawn from 0 to 1 would silently change every sequence every recorded seed produces, invalidating every Daily and every bug repro. On the watch list now, because M2-04/M2-05 are the first tasks likely to want a sixth stream — it takes index 5, and nothing moves.
- **`Chance` needs no special-casing to satisfy its rule, and must not have any.** Because `NextFloat` is `[0, 1)`, the naive `NextFloat() < probability` already gives "0 never, 1 always" for free. The tempting optimisation — return early for a certain outcome without drawing — would skip a draw and desync every seeded run the moment a designer tuned a probability to 0 or 1. `Chance_ConsumesOneDraw` is the test that would catch it.
- **`NextInt` maps from the raw 32 bits, not through `NextFloat`.** Lemire's multiply-shift takes the high half of a 64-bit product: one multiply, no division, no branch, no rejection loop, and uniform to within one part in 2^32. Routing through `NextFloat` would have thrown away the range's resolution to a 24-bit mantissa and rounded twice. Rule 9's float mapping is specced for the *fake*, where a hand-written script is the point; it is not a description of the real generator.
- **`Range(a, b)` is documented as `[a, b]` but actually produces `[a, b)`** — `b` is unreachable, because `NextFloat` excludes 1. ### 2026-09-07 · M0-05 · World snapshot · PR #_n_

- **`System.Numerics` resolves inside `Soulvail.Core` with no asmdef change and no added reference.** It ships in the .NET Standard profile the project targets (`apiCompatibilityLevel: 6`), and `AssemblyPurityTests` stays green because it is not a `UnityEngine*` assembly. ### 2026-09-07 · M0-07 · Player motor · PR #_n_

**Built:** The first game logic in the project — everything before this was plumbing. `MovementSpec` in `Soulvail.Core.Content` is a class's movement numbers as authored data (the Oathbound's 5.4 / 0.06 / 0.08 / 720, CC §7); `PlayerMotor` in `Soulvail.Core.Combat` turns a shaped stick vector into a velocity and a facing — linear accel and decel with no inertia, a proportional target so a half-pushed stick settles at half speed, shortest-arc yaw that snaps rather than creeps, and nothing allocated on the tick. Position and collision stay out: M0-16's `PlayerView` takes the velocity and drives the body. 19 new EditMode tests, 76 in the suite. `Tests/Core/Content/` now exists, one task before M0-08 fills it.

**Deviations from spec:** ten, listed in the task's *As built* footer. The two put to the owner and approved before implementation:

1. **A fourth file, `Tests/Core/Content/ContentTests.cs`.** Fifth task running into "the Tests table names a fixture the type does not belong in" (M0-02, M0-03, M0-04, M0-06) — but a weaker case than any of those, and worth recording as such: those four were *assembly* mismatches, a Core type specced into a `Tests.Game` fixture. This is a folder mismatch inside one assembly. It was resolved differently as a result: not a dedicated `MovementSpecTests.cs`, but the module fixture **M0-08 already specifies** ("all four types — one module, one test file"), created one task early with its first Content type in it. A per-type fixture would have invented a competing convention one task before the real one landed. M0-08's Files table now records that the file exists.
2. **Behaviour rule 5 extended: a `faceDirection` with no ground direction falls back to the velocity rule.** See *Learned*.

**Learned:**

- **`Vector3?` makes "provided" ambiguous, and the ambiguity is unrecoverable.** A caller can pass `Vector3.Zero`, or `(0, 1, 0)` which flattens to nothing; `Vector3.Normalize` of either is NaN, and a NaN facing survives every later frame's arithmetic — the character would never turn again, with nothing in the log to say why. M0-06 could defer its zero-`Facing` question to whoever produced the first intent; this one could not, because the default behaviour of the obvious implementation is silent permanent corruption rather than an open design question. The same shape appears in the spec's validation: `!(value > 0f)`, not `value <= 0f`, because every comparison against NaN is false and the natural spelling admits it. **Any later spec taking a nullable or unvalidated vector should decide what "no direction" means before the first producer exists, not after.**
- **The order of integration inside `Tick` is load-bearing, and no spec had said so.** From rest at full stick, speed crosses rule 5's 0.05 m/s facing threshold in 0.56 ms — a fifteenth of a frame — so integrating facing before velocity spends the whole first frame turning toward a velocity of zero and discards a frame of rotation every time the player starts moving. Velocity first. This is invisible to a test written from rest, which is why `Facing_RotatesAtTurnSpeed` reaches full speed with its aim pinned before releasing it: written the obvious way it would have measured this interaction instead of the turn rate it names.
- **The suite passed on the first run, so the trig was mutation-tested rather than trusted.** Flipping the sign of the cross term in `RotateTowards` turned four tests red — `Facing_TakesShorterArc`, `Facing_FollowsVelocity_WhenNoFaceDirection`, `Facing_UsesFaceDirection_OverVelocity`, `Facing_ZeroFaceDirection_FallsBackToVelocity` — and correctly left `Facing_RotatesAtTurnSpeed` and `Facing_SnapsWhenWithinOneStep` green: those measure an unsigned angle and a snap, both symmetric under a sign flip. The direction rule is owned by exactly one row, and it holds. Worth repeating whenever a first run is clean on signed geometry.
- **Two of the spec's test durations are not whole ticks at 1/120 s** — 0.03 s is 3.6 and 0.0625 s is 7.5. Rounding the count misses the stated tolerance and reddens a correct motor, so those tests pick a tick size that sums exactly. **A spec that states a duration should state a tick size that divides it**, or say the size is the implementer's.
- **A four-`float` constructor's likeliest defect is transposition, and the specced tests do not catch it.** Assigning `DecelTime = accelTime` passes every row in the Tests table — `FullSpeed_ZeroInput_StopsWithinDecelTime` runs 0.0833 s against a 0.06 s decel and still stops. `Spec_StoresValues` exists for that, and the same gap applies to M0-08's `CharacterSpec` and every spec type after it.
- **The `_TEMPLATE.md` gloss on "allocated-bytes delta == 0" has been there since `738a377`, before any code was written, and five tasks logged the deviation anyway** — because you read a task spec while implementing, not the template. A rule placed where nobody stands is not a rule. The phrase is reworded in place in the three M0 specs that carried it (this one, M0-10, M0-16). Twelve M1 specs still carry it, left alone deliberately since the owner scoped this to M0 — the follow-up below.
- Rule 3 (`|Velocity|` never exceeds `Speed`) needs no clamp and has no row of its own. It falls out of rules 1 and 2: the target's magnitude is at most `Speed`, and a step that never overshoots leaves the result on the segment between two points inside a ball, which is convex. `OversizedInput_IsClamped` is the row that owns it.

**Follow-ups:** one, unscheduled — reword "allocated-bytes delta == 0" in the fourteen M1 specs that still carry it (M1-01, -02, -03, -04, -05, -06, -08, -10, -11, -12, -13, -14, -15, -18). Docs only, no code. Noted alongside it: M0-02's spec body still describes the inert `GC` probe as `AllocationAssert`'s implementation, and its own *As built* asks for that comment to be superseded when the spec is next read as a pattern.

### 2026-09-07 · M0-08 · Content catalog · PR #_n_

**Built:** The vocabulary the rest of the project names things in. `ContentId` in `Soulvail.Core.Content` is a validated, stable content identity (`character.oathbound`) — a string, never an enum ordinal, so inserting content never repoints a save; `LocKey` is the address of a user-facing string, a distinct type from `ContentId` so the compiler refuses to let one stand in for the other; `CharacterSpec` is a class as immutable authored data — id, name key, max HP, and M0-07's `MovementSpec`; `ContentCatalog` is the boot-scope lookup, one dictionary per content kind, duplicates refused by name. 19 new EditMode tests, 95 in the suite. Nothing builds a catalog yet: M0-11 converts the first `CharacterDefinition.asset` into a `CharacterSpec`, and M0-12 registers the catalog in `BootScope`.

**Deviations from spec:** eight, listed in the task's *As built* footer. The three that change behaviour rather than test coverage:

1. **`ContentId` rejects null as a plain `ArgumentException`.** The Tests table asks for it, and NUnit's `Assert.Throws<T>` is an exact-type match, so the conventionally "better" `ArgumentNullException` would have reddened a correct constructor. See *Learned*.
2. **`CharacterSpec` rejects `default(ContentId)`**, a guard rule 4 does not list. It is what makes rule 2 unconditionally true — see *Learned*.
3. **`ContentId.IsValid` is a hand-written scanner rather than a `Regex`**, implementing the Public API's grammar verbatim. A regex would need either a static cached instance, in a project that bans static state, or a parse and match allocation per id.

**Learned:**

- **`default(ContentId)` is the one id no constructor can prevent, and rule 2 only holds if nothing can *register* one.** The rule says a default id used in the catalog misses like any unknown id. That is a statement about lookup, but it is falsifiable at construction: a spec built with a default id would sit in the dictionary under a key `Character()` reports as missing — the catalog would hold an entry and deny holding it, permanently and silently. Guarding `CharacterSpec` is what closes it, and it is the same shape as M0-07's `Vector3?` decision: *decide what "no value" means before the first producer exists*. The producer here is M0-11, one task away. Every member of both structs handles the default form anyway — `GetHashCode` returns 0 rather than dereferencing null, `ToString` returns empty — so a stray default surfaces as "not found" rather than as an `NRE` from inside a dictionary.
- **NUnit's `Assert.Throws<T>` is an exact type match, not an assignability check.** `ArgumentNullException` derives from `ArgumentException`, so "improving" a guard from the exception a spec names to a more specific one turns a correct implementation red — and the failure message ("Expected: `<ArgumentException>` But was: `<ArgumentNullException>`") reads like the code is wrong rather than the row. Worth knowing before M0-11, where authoring validation is nothing but guards. `Assert.Catch<T>` is the assignable-match form if a future spec wants one.
- **Two identical string literals are the same interned instance, so an equality test written with literals can pass on reference equality alone** and prove nothing about the ordinal comparison it names. `ContentId_Equality_IsOrdinal` and `LocKey_Equality_IsOrdinal` build one side with `new string(new[] { 'a', '.', 'b' })`, which cannot be interned. This is the exact case that matters in practice: one id off a save file, one off an asset.
- **The scanner was mutation-tested, since the first run was clean** — M0-07's rule. Loosening it (allowing `_` in the first segment) reddened `ContentId_InvalidForms_Rejected` alone; tightening it (dropping `_-` from later segments) reddened `ContentId_ValidForms_Accepted` alone. Both directions are owned by exactly one row, which is the arrangement worth keeping. **`ContentId_TryParse_MatchesIsValid` stayed green under both mutations** — correctly: it asserts that `TryParse` agrees with `IsValid`, and a wrong grammar is wrong consistently. That row proves consistency, never correctness, and a later reader tempted to treat it as grammar coverage should not.
- **M0-07's transposition lesson does not transfer literally, and the reason is worth recording.** `CharacterSpec`'s four arguments are four *distinct* types, so swapping any two is a compile error — the defect M0-07 found in a four-`float` constructor cannot occur here. `CharacterSpec_StoresValues` was still written, and still earns its place: it catches a property returning the wrong backing field, which the type system does not. The lesson's real next home is the first spec with two same-typed fields — an `EnemySpec` with two floats, or a `WeaponSpec` (M1-10).
- **`Characters` is wrapped rather than exposed as the array it is.** `CharacterSpec[]` implements `IReadOnlyList<T>`, so returning the copy directly lets any caller cast it back and mutate the catalog — rule 5's copy would protect nothing. `Array.AsReadOnly` costs one object once. Same instinct as M0-05's `ref`-returning trap: the copy nobody is watching is the one that goes wrong.
- `LocKey` is validated for *shape* only — non-empty, no whitespace — never against a table, per rule 3. The whitespace ban is not cosmetic: a trailing space picked up from an authored inspector field would become a key that resolves in no language, and the resulting blank label gives no clue why.

**Follow-ups:** none new. M0-07's docs-only follow-up (the fourteen M1 specs carrying "allocated-bytes delta == 0") is still open and untouched.

**Learned:**

- **A recording fake is itself an allocator, and it will be blamed on the system under test.** `Tick_AllocatesNothing` cannot be written the obvious way: `RecordingIntents` keeps every intent, so its `List<T>` doubles its array about fourteen times across the measured window, and the test goes red on a `Tick` that allocates nothing. The test therefore ticks 20 000 times *before* measuring and then calls `Clear`, since `Clear` keeps capacity. That was written up front rather than discovered, so it was checked the other way round — deleting the pre-grow does turn the test red, which is what makes it load-bearing rather than superstition. The real sink keeps one intent and has no array to double. **Every future allocation test that measures a system through a recording fake has this problem**, and the fake's `Clear` is documented as the way out.
- **The allocation probe was proved live through this path, not assumed.** M0-02's lesson was that a hand-rolled GC probe silently passes code that allocates; the generalisation is that an allocation test is only worth what its last failure proved. A `new object()` per tick reddens `Tick_AllocatesNothing` and nothing else. That check costs one run and is now the pattern for every "allocates nothing" row.
- **Both lifecycle events are published before the flag moves, and the symmetry is the useful part.** Rule 3 names the consequence for `Start` and demands a test; rule 7 states the same order for `End` and names nothing. Stated together the rule is *during either lifecycle event the session still reports the state it is leaving* — `IsRunning == false` inside `RunStarted`, `true` inside `RunEnded` — which is a consistent thing for M1-17's HUD to rely on. Documented in the type and pinned by a row, because documenting it made it a promise.
- **`RecordingEvents` cannot test an ordering rule, and it took a second fake to see it.** It records what was published, which says nothing about what was true at the moment it happened. A private nested `CapturingEvents` in the fixture hands each payload to a callback mid-publish — the first helper class in a test file in this project, and the smallest option that was not either a fourth file or a hook bolted onto a shared fake for two tests' benefit.
- **The "Tests table names a fixture this type does not belong in" gap did not occur, because it was checked before writing rather than discovered while writing.** No row tests `RecordingIntents`, so three files were enough. Five consecutive tasks logged that deviation; asking the question first is what ended the streak. The residue is that the fake's own contract is uncovered — `LastPlayerMove` throwing when empty, `Clear` — exactly as `RecordingEvents.Clear()` has been since M0-03.
- **The session takes no `IClock`, and AR §7 is corrected here** (the divergence M0-09 left for this task). Simulated time is the sum of each tick's `Dt`, which rides in on the snapshot; a clock would be a second answer to "how much time has passed", and the wrong one, since wall-clock keeps running while the game is paused or backgrounded. `IClock` (M2-01) is for persistence. §7 now shows `new RunSession(catalog, random, events, intents)` and carries the reasoning as a dependency-side statement of the rule §6 already makes about ports.
- **`Soulvail.Tests.Core` still has no `InternalsVisibleTo`, and M0-09's bet paid off exactly as predicted.** All 18 rows reach `RunState` through `session.State` and only read it. Nothing about writing this fixture wanted the seal opened.
- The first task where a specced row's behaviour was built by a *previous* task (`Config_DefaultId_Throws`, M0-09's guard). Worth the note only because it worked: the row reads as coverage of a contract rather than as an orphan, and the comment in the test says which task owns the behaviour.

**Follow-ups:** none new. ### 2026-09-07 · M0-11 · Character authoring · PR #_n_

**Built:** The first authored content in the project, and the first asset a designer can touch. `CharacterDefinition` in `Soulvail.Game.Authoring` is the Inspector half of `CharacterSpec` — seven `[SerializeField] private` fields and a `ToSpec()` that converts them, rethrowing every validation failure as a plain `ArgumentException` naming the asset so the Console points at a file rather than at the boot installer. `Oathbound.asset` is the class itself at CC §7's numbers (140 HP, 5.4 m/s, 0.06 / 0.08, 720 °/s), and `Oathbound_ToSpec_MatchesCoreCombatNumbers` pins all seven so a stray Inspector drag is a red test. 7 new EditMode tests, 120 in the suite. M0-08's catalog now has something real to hold; M0-12 registers it.

**Deviations from spec:** five, listed in the task's *As built* footer. The one that changes the project rather than the task:

1. **`CharacterDefinition` uses a block namespace, and `.editorconfig` + `CLAUDE.md` are changed to say why** — two files outside the Files table, approved by the owner after reproducing the finding. See *Learned*; it was forced, not preferred.

**Learned:**

- **Unity 6.3 will not link a `MonoScript` to a `MonoBehaviour` or `ScriptableObject` declared in a file-scoped namespace, and nothing anywhere reports it.** The C# compiler is fine — `csc.rsp`'s `-langversion:10` (M0-02) does its job and the type compiles, instantiates and runs. It is Unity's *own* importer-side parser, which extracts a file's class and namespace, that does not understand `namespace X;`. The consequences are all silent: `MonoScript.FromScriptableObject` returns null, `AssetDatabase.CreateAsset` writes `m_Script: {fileID: 0}` while logging only a vague "No script asset for CharacterDefinition", and the asset loads as null forever after. **Writing the correct GUID into the YAML by hand does not fix it** — that was tried; the reference was byte-correct (`fileID: 11500000`, the guid Unity itself reports) and the asset still would not load, because the `MonoScript` it points at has no class. Diagnosed by A/B/A on the real file, then confirmed with two throwaway ScriptableObjects in one folder, one compile cycle, differing only in namespace form: block resolved, file-scoped did not. **This is the M0-02 situation again — a convention that cannot hold for a whole class of files — but with no `csc.rsp`-shaped escape.** Every MonoBehaviour and ScriptableObject from here on (M0-13's scopes, M0-15's stick, M0-16's views and ticker, M0-17, M0-18) needs a block namespace; pure C# keeps file-scoped. `.editorconfig` silences the namespace diagnostic for the `Game/` and `Editor/` trees rather than enumerating folders that do not exist yet — the rule cannot be expressed as a path glob, and forgetting it is loud anyway.
- **`[Min]` is a drawer, not a guarantee, and the tests depend on that being true.** `ToSpec_InvalidHp_ThrowsNamingAsset` sets `_maxHp = 0` through `SerializedObject` on a field marked `[Min(1f)]`, and it sticks: the attribute clamps `EditorGUI` and nothing else. The same hole is open to a merge, a hand-edited YAML and a future JSON loader, which is the argument for `ToSpec` being the only way out of the type and for the real guards living in the core constructors.
- **A recording assertion can couple two rules without looking like it does.** `ToSpec_InvalidId_ThrowsNamingAsset` set a bad id, which trips `OnValidate`, so it carried a `LogAssert.Expect` to keep the Console tidy — and silencing `OnValidate` during mutation testing turned that row red alongside the row that actually owns rule 3. The tidiness was not worth the false ownership; unexpected *warnings* do not fail a test, so the Expect came out. **Mutation testing found this, not the green run** — the same argument M0-07 and M0-08 made for doing it, now with a case where what it caught was in the tests rather than in the code.
- **`CreateInstance` leaves `name` empty, which makes `Does.Contain(name)` vacuous.** Both "the message names the asset" rows would have passed against any message at all. Naming the fixture is what gives them something to find — the same shape as M0-08's interned-literal trap: an assertion that cannot fail proves nothing, and it takes a deliberate look to notice.
- **`ArgumentOutOfRangeException` and `ArgumentNullException` both derive from `ArgumentException`, so `ToSpec` narrowing every failure to the base type is a real promise, not a formality** — and NUnit's exact-type match (M0-08) is what makes it testable at all. The inner exception is kept, so the field and value survive into the log; the row asserts both halves, because narrowing without preserving would satisfy the type assertion while throwing the diagnostic away.

**Follow-ups:** none new. M0-09's hand-off to M0-16 and M0-07's docs-only follow-up (the fourteen M1 specs carrying "allocated-bytes delta == 0") are both still open and untouched.

### 2026-09-07 · M0-12 · Composition installers · PR #_n_

**Built:** The wiring, and the first time the project's objects are built by a container rather than by a test. `BootInstaller` in `Soulvail.Game.Composition` converts the authored `CharacterDefinition`s into a `ContentCatalog` and registers it with `PendingRun` for the life of the app; `RunInstaller` registers everything one run owns — `DomainEventHub` as `IDomainEvents` and itself, `IntentBuffer` as `IIntentSink` and itself, a `WorldSnapshot` at the 64-enemy cap, an `IRandom` seeded from the pending run, and `RunSession` as `IRunSession` — all `Lifetime.Scoped`, so disposing the run scope ends the run. `PendingRun` is the slot the menu writes and the run reads, and the one thing that has to survive a scene load. Both installers are scene-free statics, which is what lets `InstallerTests` build the real containers headlessly and resolve from them: 11 new EditMode tests, 131 in the suite. Nothing constructs these scopes yet — `BootScope` and `RunScope` are M0-13, and the `RunTicker` that would actually tick the session is M0-16.

**Deviations from spec:** seven, listed in the task's *As built* footer. The two that change behaviour rather than test coverage:

1. **`WorldSnapshot` is registered through a factory at `Lifetime.Scoped` rather than as an instance.** Rule 5 says "instance", the section header says "all `Lifetime.Scoped`", and VContainer cannot satisfy both — `RegisterInstance` is hardwired to Singleton. Resolved toward the header.
2. **Three guards in `BootInstaller.Install`** — null builder, null list, null element — none of them listed. The element guard is the one that matters: without it `ToSpec()` on an empty array slot throws an NRE from inside a loop, and `ContentCatalog`'s own null-entry guard is unreachable because conversion happens first.

**Learned:**

- **VContainer only disposes what it constructed, and this is the sharpest trap the container has.** `CreateTrackedInstance` adds an object to the scope's disposal list only when the registration's provider is not an `ExistingInstanceProvider` — that is, only when the container built it. So `builder.RegisterInstance(new DomainEventHub())` compiles, resolves, aliases the port and the concrete type to one object, passes ten of this task's eleven rows, and **is never disposed**: every run would leak every subscription into the next, and the symptom would be a HUD that updates twice, then three times, with nothing in the log. Proved by mutation rather than by reading: swapping the registration reddens exactly one row, `Run_ScopeDispose_DisposesHub`, and leaves everything else green. That row was flagged in the task prompt as the one asserting VContainer's behaviour rather than ours, and it turns out to be the most load-bearing row in the fixture. **The rule for every adapter after this: anything that owns a resource is registered as a type, never as an instance.** `ContentCatalog` is registered as an instance deliberately and safely — it is immutable, not `IDisposable`, and shared for the life of the app, so there is nothing to own.
- **`As<T>()` alone does not make the concrete type resolvable, and the failure would look like a missing registration.** `Registry.Build` inserts the implementation type as a *null guard* entry whenever `InterfaceTypes` is non-empty, so `Resolve<DomainEventHub>()` throws on a container that plainly contains one. `.AsSelf()` is what adds it back. Read out of the source rather than discovered, which is why both `.As<…>().AsSelf()` pairs were written that way from the start.
- **VContainer refuses a duplicate implementation-type key at build time**, so the "registered twice, two instances, port and views disagree" bug cannot happen silently for one concrete type: the second mutation tried (`As<IDomainEvents>()` and `AsSelf()` as two registrations) throws `ArgumentException: An item with the same key has already been added` and reddens all seven run-scope rows at scope construction. Worth recording because it bounds what `Run_EventsPortAndHub_SameInstance` actually owns — the container catches the same-type case, so that row's real job is the divergence that *does* build: a Func registration for the interface beside a type registration for the class.
- **A `Lifetime.Singleton` registered inside a child scope resolves scope-locally, not from the root.** `ScopedContainer.ResolveCore` consults its own registry first and only delegates to the parent when the registration is not its own. So the rejected `RegisterInstance` form would have behaved per-run despite its Singleton label — the label was the defect, not the lifetime, which is exactly why deviation 1 changes the spelling and not the behaviour.
- **`PendingRun` crossing the scope boundary is the half worth testing.** Registered Singleton in boot, it resolves through the run scope's parent chain, so the menu's write and the run's read hit one object. `Boot_PendingRun_IsSingleton` pins it at the root, but `Run_Random_SeededFromPendingRun` is the row that would actually catch a re-registration in `RunInstaller` — the mistake that would give the run its own empty `PendingRun` and an unseeded generator.
- **A lazily-registered warning has to be expected before the resolve, not before the build.** `Run_WithoutPendingRun_UsesFallbackSeed` emits its warning inside `Resolve<IRandom>()`, because a Func registration does not run at `Install` or `Build` time. `LogAssert.Expect` placed at the top of the test reads like it is guarding the whole thing and is in fact guarding one line.
- **`PendingRun.Set` deliberately does not validate the id.** `RunConfig` already owns "nobody chose a class" by name (M0-09), and M0-09's own entry predicted this task as the source of that mistake. Guarding here too would give one mistake two messages and two places to keep in step.
- **The "Tests table names a fixture this type does not belong in" gap did not occur, checked before writing** — all eleven rows test `BootInstaller`, `RunInstaller` or `PendingRun`, all three in `Soulvail.Game.Composition`, all reachable from the one specced fixture in `Soulvail.Tests.Game`. Second task running to ask first (M0-10 was the first).

**Follow-ups:** none new. M0-09's hand-off to M0-16 (whether `RunState.Motor` narrows) is unchanged and still open — nothing in this task reads the handle. M0-07's docs-only follow-up (the fourteen M1 specs carrying "allocated-bytes delta == 0") is still open and untouched. For M0-13, which is next: both installers are ready to be called from `BootScope`/`RunScope`, and `BootInstaller`'s null-element guard exists specifically for the serialized `CharacterDefinition[]` that scope will carry.

### 2026-09-08 · M0-13 · Scopes and scenes · PR #_n_

**Built:** The game has an entry point. `BootScope` is the root `LifetimeScope` — a prefab named as `RootLifetimeScope` in `VContainerSettings`, instantiated before the first scene loads and kept under `DontDestroyOnLoad` — and it is the only place in the project that names content assets for the container: `Oathbound.asset` sits in its serialized `CharacterDefinition[]`, forwarded to `BootInstaller` alongside `SceneLoader` and the `BootFlow` entry point. `RunScope` is the per-run child that wraps `RunInstaller`, and it assigns no parent, which is exactly what makes pressing Play in the Run scene resolve to the root anyway. `SceneLoader` is the one way anything changes scene: `Boot`/`Menu`/`Run` constants, `Active`, and an awaitable single-mode `LoadAsync` that faults its task rather than throwing when a name is empty or absent from the build. `BootFlow` sets `Application.targetFrameRate = 60` and hands Boot off to Menu — **only** when the active scene is Boot, so the direct-Play workflow is not hijacked, the same decision `RunInstaller`'s unseeded-run fallback made in M0-12. Three scenes exist at build indices 0/1/2: Boot (black camera, Canvas, a TMP "Soulvail" label), Menu (camera, empty Canvas — content in M0-17), Run (camera, a `RunScope` object — content in M0-16). `SampleScene` and `SampleSceneProfile` are gone. Nothing is ticked yet: no entry point resolves `IRunSession`, so `RunScope` builds a container and starts no run. 131 EditMode tests, unchanged — this task specs none, and none were invented.

**Deviations from spec:** eight, listed in the task's *As built* footer. The three that matter:

1. **`SceneLoader` does not use `Application.CanStreamedLevelBeLoaded`** — see *Learned*. The specced API is inert and would have rejected every load.
2. **`ProjectSettings.asset` gains `VContainerSettings` in `preloadedAssets`** — not in the Files table, and rule 1 is simply false without it.
3. **Two owner-approved additions outside the table**: TMP Essential Resources (44 assets, without which rule 5's label cannot exist) and repointing `Mobile_RPAsset`/`PC_RPAsset` to `DefaultVolumeProfile` (without which this task's own removal leaves two dangling references).

**Learned:**

- **`Application.CanStreamedLevelBeLoaded` is inert in the Editor, and it fails in the direction that looks like correctness.** It returned `false` for `Boot`, `Menu` and `Run` — by bare name *and* by full asset path — at a moment when `SceneManager.sceneCountInBuildSettings` was 3 and `GetScenePathByBuildIndex` listed all three correctly. A `LoadAsync` guarded by it rejects every scene in the game, and the symptom is a Boot screen that never advances with an `ArgumentException` blaming Build Settings that are in fact correct. **This is M0-02's lesson in a new API**: the obvious probe answered confidently and wrongly, and the only reason it was caught is that the build-settings write was verified by asking three different APIs the same question instead of one. `SceneUtility.GetBuildIndexByScenePath` is honest but path-only — `-1` for a bare name — so `IsInBuild` walks the build list and compares both forms. Worth generalising: **when a Unity API answers a yes/no question about project state, prove it says "yes" to something true before trusting its "no".**
- **A `VContainerSettings` asset does nothing unless it is in `PlayerSettings.GetPreloadedAssets()`.** `VContainerSettings.Instance` is assigned in `OnEnable`, and in the Editor the only thing that triggers it is `LoadInstanceFromPreloadAssets()` at `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)`. The package's `Assets/Create/VContainer/VContainer Settings` menu item does the preload registration as part of creating the asset; creating it with `AssetDatabase.CreateAsset` alone — which is what an automated setup naturally does — leaves an asset that inspects correctly, points at the right prefab, and never loads. `Instance` being null then makes `LifetimeScope.IsRoot` false and `GetRuntimeParent` return null, so every scene scope silently becomes its own root with an empty container.
- **`LifetimeScope.GetRuntimeParent` reaches the settings root last, after `parentReference` and `FindParent()`.** That ordering is what rule 1 is really built on, and it is why `RunScope` has no parent assigned in the Run scene: assigning one would break Play-in-Run rather than help it. Read from the package source, not executed — no Play-mode verification was possible from this session.
- **The Unity MCP's `RunCommand` assembly does not reference VContainer**, so `AddComponent<RunScope>()` fails to compile with "no implicit reference conversion to `UnityEngine.Component`" plus a missing-assembly error naming `LifetimeScope`. `gameObject.AddComponent(Type.GetType("Soulvail.Game.Composition.RunScope, Soulvail.Game"))` works and binds correctly. Every future task that builds a scene or prefab around a VContainer type through the MCP hits this.
- **Unity's API level has no non-generic `TaskCompletionSource`** — `TaskCompletionSource<bool>` is the shape. Its `RunContinuationsAsynchronously` is deliberate: without it the awaiting code resumes inline inside `AsyncOperation.completed`, which Unity raises from inside its own scene management, so a chained load would be re-entrant.
- **Deleting a template asset is rarely self-contained.** `SampleSceneProfile` looked like scene-local sample dressing and was in fact the `m_VolumeProfile` of *both* URP render pipeline assets. The removal was specced in one line; satisfying it honestly meant touching two files the spec never mentions. Checking `grep -rl <guid>` across `Assets` and `ProjectSettings` before any deletion cost one command and would have cost a broken render pipeline otherwise.
- **TMP Essential Resources were never imported in this project** (`TMP_Settings.instance` null, no `Assets/TextMesh Pro/`), despite `Unity.TextMeshPro` being referenced by `Soulvail.Game` since M0-01. `TMP_PackageResourceImporter.ImportResources(true, false, false)` does it non-interactively. The 44 assets include a `.ttf` and a `.png`, both correctly routed to LFS by `.gitattributes`.
- **Vendoring a package's assets breaks the pre-commit whitespace check, and the fix is `.gitattributes`, not the hook and not the files.** TMP's shaders ship with trailing whitespace, space-before-tab indents and blank lines at EOF; `git diff --cached --check` flagged ten of them and refused the commit. "Fixing" them is the wrong move twice over — they are third-party, and Unity silently reverts any edit on the next TMP reimport. `"Assets/TextMesh Pro/**" -whitespace` unsets the attribute for that tree only, which is the mechanism `git diff --check` is built to honour; our own `.cs` and `.shader` files stay `unspecified` and still checked. Verified with `git check-attr` and by re-running the hook's exact pathspec. **Any future vendored tree needs the same line** — the hook's own exclusion list is for Unity-serialised *formats*, which is a different axis and should not be extended with vendor paths.

**Follow-ups:** one, recommended not created. **`SceneLoader` deserves EditMode tests and the spec's "everything here needs scenes" is no longer true of it** — `LoadAsync`'s two rejection paths and `Active` need no scene load, they were exercised by hand this session through the real object, and the `CanStreamedLevelBeLoaded` trap is exactly the kind of thing a test pins permanently. Owner's call whether that is an `M0-13a` or rides along with M0-17, which already owns the Boot → Menu PlayMode smoke test. M0-09's hand-off to M0-16 (whether `RunState.Motor` narrows) and M0-07's docs-only follow-up are both still open and untouched.

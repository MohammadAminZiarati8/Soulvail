| **What works** | **A run is a descent, and it survives the app closing.** Boot → Menu → `Descend` (or `Continue`) → a run that arrives in an arena, seals it, spends a threat budget on telegraphed waves, opens a door when they are dead, and puts the player one stage deeper with the budget, curves and scaling that go with it. **Core owns every outcome**; Unity reports facts and senses and renders events. Three archetypes fight differently — the Husk closes, the Spitter kites to 14 m and will not shoot through a pillar, the Bloater walks in and detonates — and all three are authored data on one shared body, told apart by tint and scale. Arenas change at a boundary, drawn from the mode's roster by seed and stage. Everything the player cannot see has an indicator: screen-edge arrows for off-frame threats, a dimmer marker for a focus held out of range, rings for spawns and blasts. A run writes itself to disk at its opening frame and at every boundary, and deletes itself on death. **And as of M3-01a a kill is worth something:** experience is banked on the death, drained on the tick between the death check and the director, and crossing a threshold publishes a level and banks a pick — visible on the debug overlay as `lvl 3 0.42 owed 2`. **As of M3-01b the level is in the file**: the boundary write carries level, absolute XP and banked picks, a resumed run comes back at the level it had before `RunStarted` is published, and **a `run.json` written by the M2 build still loads** — it migrates to v2 and means what v1 meant, level 1 and nothing earned. **And as of M3-03 a run has a live tree**: given a class with one, it knows which nodes may be taken, taking one puts its effects on the player's stats through the registry, a resumed run gets its picks back *before* its hit points are clamped against the maximum those picks moved, and the boundary write carries them in take order. **As of M3-04 the game can also say which three of those a player would be shown** — a seeded, weighted, no-replacement draw from the available set, one draw per pick, from the `Offers` stream and no other, so the same seed against the same tree state always gives the same offer in the same order. Nothing calls it yet. Composition is `BootScope` → `RunScope`/`MenuScope`, **no statics anywhere**. **Task-by-task detail is in the [M0](archive/PROGRESS-M0.md), [M1](archive/PROGRESS-M1.md) and [M2](archive/PROGRESS-M2.md) archives** — this row is the shape, not the history. |

## How to write an entry

Append one entry per merged task, newest at the bottom. **Twelve lines or fewer.** The spec's *As built* footer owns the full account of what deviated and why; this entry is the index — what happened, and where each lesson was filed. (The archived logs average 7 KB an entry against a template that said "one line"; the cap is what keeps this file readable.)

```markdown
### YYYY-MM-DD · M0-03 · Domain events
**Built:** one or two lines — what exists now that didn't.
**Deviations:** none | *n*, in the spec's As built. Name here only one that changes a decision.
**Learned:** one line each, ending with where it was filed — Traps §n · AR §18.x · ledger row n · spent (stays here).
**Follow-ups:** tasks created, ledger rows added, or "none".
```

The PR number lives in the merge commit — do not write it here. Current State is written **as of the PR's merge**: the task the PR closes is *Last merged*. If a deviation changes a decision in `Architecture.md`, it needs a superseding ADR — say so here and link it.

**A durable lesson does not go in Current State.** A toolchain trap goes in [Traps.md](../Traps.md); a rule the code now depends on goes in [Architecture.md §18](../Architecture.md#18-invariants); a thing a named task must handle goes in the [carry-forward ledger](ROADMAP.md#carry-forward-into-m3), and one with no owner yet in the ROADMAP parking lot, one line. The entry says *what happened*, and links.

**At the end of a milestone**, move its entries to `archive/PROGRESS-M<n>.md`, promote anything durable out of them first, and leave this Log holding only the milestone in progress. **M2 is the first milestone this was done for on time** — M0's and M1's were archived a milestone late and at 381 KB between them, which is the failure the rule was written against.

**Built:** **the tree exists as data, and a node can now carry the effect M3-05 built.** `SkillSpec` is CH §4's four kinds with the effects taking it puts into force; `ActiveSpec` is what an Active is when it fires — authored base cooldown, trigger, cast effects — and **rule 1 is checked in both directions, unlike `EnemySpec`**: an Active without its block is a skill that cannot fire, a block on a Passive is a cooldown nothing will run, and `ParentId` is the same rule again. `TriggerSpec` is CC §6.4's condition as one or two ANDed `TriggerClause`es over the nine `CombatBlackboard` fields — **ADR-0005's "pure predicates, carried by the `SkillSpec` as data" made authorable**, because a lambda cannot come out of an asset and an enum-and-a-threshold can. `SkillTreeSpec` is three branches of tiers of ids with `TryLocate` as a dictionary built once. `ContentCatalog` gained the fourth and fifth kinds through the same `Index`, plus **one second index nothing else has** — `TryGetTreeFor(characterId)`, the door a run actually uses.

**Learned:** **AR §18.3's NaN spelling is about which side of a predicate NaN lands on, and the `!` is not part of the rule.** Rule 6 prescribed `!(value < threshold)`; applied to `AtLeast` — the only comparison a `!` could belong to — `!(NaN < 0.6)` is **true**, so a broken blackboard would have satisfied every `AtLeast` clause the player owns and fired every active at once, which is the exact failure the rule's own sentence forbids.

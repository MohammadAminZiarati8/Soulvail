## How to write an entry

Append one entry per merged task, newest at the bottom. **Twelve lines or fewer.** The spec's *As built* footer owns the full account of what deviated and why; this entry is the index — what happened, and where each lesson was filed. (The archived logs average 7 KB an entry against a template that said "one line"; the cap is what keeps this file readable.)

```markdown
### YYYY-MM-DD · M0-03 · Domain events
**Built:** one or two lines — what exists now that didn't.
**Deviations:** none | *n*, in the spec's As built. Name here only one that changes a decision.
**Learned:** one line each, ending with where it was filed — Traps §n · AR §18.x · ledger row n · spent (stays here).
**Follow-ups:** tasks created, ledger rows added, or "none".
```

The PR number lives in the merge commit — do not write it here. Current State is written **as of the PR's merge**: the task the PR closes is *Last merged*. If a deviation changes a decision in `Architecture.md`, it needs a superseding ADR — say so here and link it.

**A durable lesson does not go in Current State.** A toolchain trap goes in [Traps.md](../Traps.md); a rule the code now depends on goes in [Architecture.md §18](../Architecture.md#18-invariants); a thing a named task must handle goes in the [carry-forward ledger](ROADMAP.md#carry-forward-into-m3), and one with no owner yet in the ROADMAP parking lot, one line. The entry says *what happened*, and links.

**At the end of a milestone**, move its entries to `archive/PROGRESS-M<n>.md`, promote anything durable out of them first, and leave this Log holding only the milestone in progress. **M2 is the first milestone this was done for on time** — M0's and M1's were archived a milestone late and at 381 KB between them, which is the failure the rule was written against.

**Built:** five specs where the ROADMAP had four titles — [M4-01a](tasks/M4-01a-combatant-stats-and-triggers.md) the stat an effect can aim at · [M4-01b](tasks/M4-01b-boss-agent-framework.md) phases, the beat and adds · [M4-02](tasks/M4-02-warden-behaviours.md) the Warden's three attacks · [M4-03](tasks/M4-03-boss-arena-and-views.md) its body and the arena hazard · [M4-04](tasks/M4-04-segmented-boss-bar.md) the segmented bar GD §16.2 has wanted since M2-15. **Build order is ID order.** M4-00b specs M4-05…M4-07.

**Deviations:** *1*. **M4-01 split at the effects/AI seam before starting**, against the ROADMAP's single title, because the owner's requirement — *"the boss can get buff and debuff, skills, and everything that player can get"* — is a question about `Core/Effects`, and a phase machine is a question about `Core/Ai`. Two arguments, two reviews; M3-12's three-way split is the precedent.

**Learned:** **the combat machinery was already almost entirely target-agnostic and nobody had checked.** `Health` is one class for both bodies, `EnemyAgent` already carries two `Stat`s, `GrantedShieldPool` is keyed by `object`, `EffectRegistry.Apply` takes an `object source`, `SkillRunner`'s constructor names no player — and **`EnemyAgent.IsVulnerable` already exists**, so GD §9.1 rule 3's invulnerable beat needs no edit to the damage path. **Exactly two couplings block a boss with buffs and skills**: `ModifyStat` names a `PlayerStat` with the handler holding *the* `PlayerStats`, and `EnemyBlackboard` is a perception blackboard with no health fraction while `TriggerSpec` reads the player's `CombatBlackboard` → both are M4-01a's Files table. · **`EnemySpawned` gains no `IsBoss` flag**, and the nearby precedent was re-examined rather than copied: M3-13b's defaulted `IsElite` was right for a *look*, and a boss is not one — the phase count rides on `BossPhaseChanged` instead → spent in M4-01b rule 7. · **M4-02 deliberately contradicts M3-11b on capacity overflow**: a ninth zone throws, a fifth shockwave drops, because an add-heavy boss phase is where a ceiling actually gets hit → spent in M4-02 rule 8.

**Follow-ups:** **no ledger row moves, and one is inherited loudly.** [Row 1](ROADMAP.md#carry-forward-into-m4) — the unreadable HUD — was ruled out of M4 by the owner right after the tag, so **M4-04's rule 8 forbids it from ticking a readability row**: it is the first task since M3-15's verdict to add a readout, and it lands a full-width band directly above M3-10b's 4 dp XP strip. Row 3 gains four device questions (telegraph legibility at phone size — GD §9.1 rule 7, which says to test *before calling it done* — the beat reading as a beat rather than a freeze, overlapping transparent VFX at fill-rate, and whether 75–120 s of one enemy holds attention). **One parking-lot line opened on the owner's words:** a **stage editor**, promoted when a designer wants stage 7 to differ from stage 6 for a reason no curve expresses — not M4's, because building an editor for one roster entry is tooling that outlives its content. **And one refusal recorded rather than left to be rediscovered:** no parallel `EnemyStat` enum.

### 2026-09-18 · M4-01a · A stat an effect can aim at, and a trigger a boss can read about itself

**Built:** `IStatBlock` — one address book, two implementations: `PlayerStats` (declaration plus `Has`, nothing else moved) and the new `CombatantStats` over an `EnemyAgent`, answering `MaxHp`, `MoveSpeed` and `ContactDamage` and **refusing everything else by name rather than minting a `Stat`**. `ModifyStat` gained a `StatTarget` defaulted to `Player`; `ModifyStatHandler` gained `Aiming(self)`, a scope that aims it for one call, and **a `Self` effect applied outside one throws rather than falling back to the player**. `EnemyBlackboard` gained `HpFraction` and `ShieldFraction`, written in `EnemySystem.Perceive` beside `DistanceToPlayer`. **It is used by nothing and moves no number in any run this build plays.**

**Deviations:** *3*, in the spec's [As built](tasks/M4-01a-combatant-stats-and-triggers.md). The one that changes a decision: **`PlayerStat` gained `ContactDamage`**, against the Files row that says it gains nothing, because two named test rows require `CombatantStats` to answer it and the Tests table wins. `PlayerStats.Resolve` therefore refuses a *legal* member for the first time, and **the enum's name is now the one thing about it that lies** — raised for the owner rather than renamed, because `ModifyStatDefinition` serialises it by ordinal into nine authored assets and a rename is a move.

**Learned:** **Unity writes a line for a serialised default** — `_stat: 0` is in every shipped asset and `MaxHp` **is** 0 — so "no diff because Unity omits defaults" is false; the diff is absent because **Unity does not rewrite an asset on disk when the script that reads it grows a field**. Measured with an in-memory clone serialised outside `Assets/`, which writes `_target: 0` in full — **Traps §1** (an API's silence is not agreement either). **A corpse's blackboard is frozen, not zeroed**: `EnemySystem.Perceive` skips the dead, so a dead boss's `HpFraction` is its last living reading — pinned by `Blackboard_ACorpseKeepsItsLastReading` and handed to **M4-01b**. **Proving a refusal red first paid for itself twice**: it showed the three rows that catch a fallback, and it caught a wrong assertion of ours about `DepthScaling`'s invisible depth-1 modifiers — **spent**.

**Follow-ups:** **no ledger row closes or opens.** Two things are handed to **M4-01b** in its *Next task* row: how a `SkillRunner` reads an enemy's blackboard (M4-01a rule 7 only put the fields there), and the corpse-fraction rule above. One thing is handed to **the owner**: rule on renaming `PlayerStat` to `StatId`, which is a move touching every authored asset's serialised enum. One pre-existing `ArenaView.OnValidate` false warning was found and deliberately not fixed — **Traps §1**'s family, described in *As built* for whoever next touches that file.

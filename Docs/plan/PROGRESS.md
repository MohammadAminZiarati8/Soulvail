| **What works** | **The game plays from a cold start.** Press Play in Boot and the app reaches a menu, one tap starts a run, and a cyan capsule moves around a grey box, driven end to end through core: a thumb (or WASD, or a stick) is shaped, written into a snapshot, decided on by `RunSession`, emitted as an intent, and applied to a `CharacterController` — no view touching gameplay state at any point. That is the whole of what M0 set out to prove about the architecture; what is left in the milestone is a camera, a menu, and an APK. Underneath it, in order: `RunSession` is the brain and the only implementation of `IRunSession`: `Start` resolves the class from the catalog, builds `RunState` with a `PlayerMotor` facing +Z and the generator's seed, publishes `RunStarted`; `Tick` sums `Dt` into `State.Time`, records the reported player position, advances the motor and writes exactly one `PlayerMoveIntent`; `End` publishes `RunEnded` and leaves the finished state readable. Everything before it is the plumbing it stands on. Every wire of ADR-0003's boundary exists in shape, the two things core needs before a run can start sit behind it, and so does the shape of the run itself. **How the player moves**: `PlayerMotor` + `MovementSpec` turn a stick vector into a velocity and a facing. **What things are called**: `ContentId`, `LocKey`, `CharacterSpec` and `ContentCatalog` give core a stable vocabulary for content and text, so nothing in core ever names an asset or a raw string. **What a run is**: `IRunSession` is the one inbound port the body holds — `Start`, `Tick`, `End` — `RunConfig` is what a run is started with, `RunState` is the live run that only core may write, and `RunStarted`/`RunEnded` are the first two domain events. Around them: `StateMachine<T>`, three outbound/inbound ports — `IDomainEvents`, `IRandom`, `IIntentSink` — and the payloads `WorldSnapshot`/`EnemySense` (in) and `PlayerMoveIntent` (out) in `Soulvail.Core`; `DomainEventHub`, `SeededRandom`, `IntentBuffer` and the `Num` vector conversions on the Unity side; `RecordingEvents` and `FixedRandom` as the fakes every later core test asserts through. **What a class is, as data**: `CharacterDefinition` is the Inspector half of `CharacterSpec` and `Oathbound.asset` is the first authored content in the project — the CC §7 numbers a designer can tune, converted by `ToSpec()` into the immutable record core consumes, with every validation failure rethrown as an `ArgumentException` naming the asset. **How it is all wired**: `BootInstaller` and `RunInstaller` are the two scene-free static installers that name every registration — the catalog and `PendingRun` for the life of the app, and per run the hub, the buffer, the snapshot, the seeded generator and the session, all `Lifetime.Scoped` so disposing the scope ends the run. `PendingRun` is what the menu will write and the run will read. A test builds both containers for real and resolves through them, so a wiring mistake is red in the Test Runner rather than silent on a phone. **Where the app starts**: `BootScope` is the root scope prefab named in `VContainerSettings` (and registered in `preloadedAssets`, without which none of it loads), instantiated before the first scene and kept under `DontDestroyOnLoad`; it carries `Oathbound.asset` and hands `BootInstaller` the only content references in the project. `RunScope` wraps `RunInstaller` and deliberately names no parent, so it finds the root whether the Run scene was reached through the Menu or opened and played directly. `SceneLoader` is the single route between scenes and `BootFlow` is the entry point that sets 60 fps and moves Boot → Menu — whenever Boot is the scene we are in, checked once at start and again on every `sceneLoaded`, so a cold launch *into* Boot from somewhere else still hands off (M0-17), while Play-in-Run is untouched because loading Run never loads Boot. Three scenes are in the build at 0/1/2 — Boot with a black camera and a TMP splash, Menu with a title and a button, Run with a `RunScope` object — and the URP template's `SampleScene` and `SampleSceneProfile` are gone. **How a session starts**: `MenuScope` is the Menu's scope, parentless like `RunScope` so it finds the root either way, registering the one thing the scene owns; `MenuPresenter` is the menu's entire behaviour — `Descend` writes the first catalogued class and an `Environment.TickCount` seed into `PendingRun`, takes the button out of service before anything else so a second touch cannot start a second load, and awaits the Run scene, handing the button back if that load faults. `Menu.unity` is a black camera, the TMP title, a 480 × 160 reference-pixel button (≥ 53 dp on every screen shape the game targets) and the `EventSystem` without which uGUI routes nothing. The two strings on it are the only raw user-facing strings in the project, parked for M6-10. **How a thumb reaches it**: `Soulvail.inputactions` is the one actions asset — a single `Player` map carrying all eight actions M0–M3 need (`Move`, `MovementSkill`, `Skill1`–`Skill4`, `Focus`, `Pause`) under a **Touch** scheme (`Touchscreen`/`Gamepad`/`Pointer`, gamepad included because the coming floating stick emits as a virtual one) and a **KeyboardMouse** scheme — and `InputAdapter` is the only thing in `Soulvail.Game` that reads it: `Move` clamped to the unit disc, zero while disabled or disposed, `Enable`/`Disable` idempotent over the `Player` map alone. Only `Move` is consumed; the other seven are bound so later tasks add a reader, not a binding. It is project-wide Actions now, and the URP template's asset is gone. **What the thumb actually touches**: `StickShaper` is the stick's arithmetic as pure functions — `Shape` (dead to 8 dp, linear to 40 dp, flat at 1 beyond, direction preserved exactly), `Recenter` (past 60 dp the origin trails the thumb by exactly 60 dp, so a drag-back registers on the next frame) and `PixelsPerDp` — every number pinned to 1e-4 by tests, because a thumb is the same physical size on every phone while a pixel is not. `FloatingStick` is the frame-owning half: one captured pointer, zero on touch-down, recentre-and-report on drag, a guaranteed final zero on release *and* on disable-mid-drag before the base class removes the virtual device. It feeds `<Gamepad>/leftStick` and never reads the Input System, so it and `InputAdapter` meet only through the actions asset — on a phone, this *is* the gamepad the `Touch` scheme lists. `SafeAreaFitter` keeps the HUD out from under a notch, and `Hud.prefab` assembles all of it: overlay Canvas at 1920×1080 match 0.5 → `SafeArea` → `Region` (left 45 %, transparent, raycastable) → `Base`/`Knob` discs hidden until touch. **What closes the loop**: `SnapshotBuilder` is the senses — one `Clear`-then-write per frame of the only three things core cannot know, with `Dt` clamped at `MaxDt` (50 ms) so a hitch or a scene load becomes slow motion instead of a teleport through a wall, and the stick mapped X→world X, Y→world Z unrotated because the M0 camera has yaw 0 (the day it can turn, the rotation goes *there*, never in core). `PlayerView` is the body and decides nothing: intent velocity plus an integrated gravity term (−20 m/s², pinned at −1 while grounded), one `CharacterController.Move` at the snapshot's `Dt`, `LookRotation` to the intent's facing with no smoothing because core already turned at 720°/s; its `Velocity` is what core asked for, deliberately not `controller.velocity`, which would read as "stopped trying" the moment the player leans on a wall. `RunTicker` is the frame order and nothing else — build, clear intents, tick core, apply if `HasPlayerMove` — and owns the run's two ends: `NeverSleep` and the stick enabled at `Start`, `End()` and the timeout restored on dispose. `RunScope` carries the one reference a static installer cannot have, the scene's `PlayerView`, and registers those pieces `Scoped`. `Player.prefab` is a capsule whose mesh is exactly its controller's shape with a facing bar on top; `GreyBox.prefab` is a 36 × 36 floor, four walls and four mesh-collided pillars, all static; `Run.unity` holds both plus `Hud.prefab` and the `EventSystem` the stick needed before any touch could reach it. `RunState.Motor` is now `internal` — M0-16 confirmed nothing outside core reads it — with `PlayerVelocity` and `PlayerFacing` as the public reads. **What the player sees, and what the developer reads**: `FollowCamera` holds a fixed top-down angle — pitch 57°, yaw 0, 16 m back — and `SmoothDamp`s after the player in `LateUpdate`, because `RunTicker` ticks in the Update phase and a camera that read the body's position there would race it; its rotation is authored, never derived, and rebuilt each frame so the angle is live-tunable in play. Yaw 0 is load-bearing: it is the only reason `SnapshotBuilder`'s unrotated stick mapping is camera-relative, and the day it changes the rotation goes into the builder, never into core. At those numbers the view spans 25.6 m of depth × 32.8 m of width — it frames the *player*, not the whole 36 m arena, which M0-20 decides on purpose. `DebugOverlay` is one line of TMP text refreshed 10×/s from a preallocated `StringBuilder`, showing the snapshot's `MoveInput`, the intent's speed and facing (zeroed, never stale, when `HasPlayerMove` is down) and a smoothed fps; it reads only the two ends of the frame, so a wrong number localises the fault to one side of the boundary. It disables itself in `Awake` outside the Editor and development builds, and its canvas deliberately carries no `GraphicRaycaster` so it can never take a thumb from the stick beneath it. **How it leaves the Editor**: `AndroidBuild` is one menu item and the `BuildPipeline` call behind it — scenes read from Build Settings so a build cannot disagree with the Editor about what was playtested, `Development | AllowDebugging` for a dev build, architectures pinned for the build and restored in a `finally`, and a throw rather than a log when the result is not `Succeeded`, because a failed build leaves the previous APK sitting at the output path. It configures nothing else: player settings are project state, visible in a diff, not rewritten by whoever last pressed build. **`Builds/Android/Soulvail-dev.apk` exists — 82.4 MB, `com.soulvail.dev`, `0.1.0`/`1`, minSdk 25, targetSdk 36, six `.so` under `lib/arm64-v8a/` and no other ABI.** ARM64-only is not a choice: Unity 6.3 cannot build x86-64 for Android, which voids the spec's BlueStacks-runs-it-natively plan. Landscape is enforced as Auto Rotation with portrait off, so the two landscape orientations are the only ones the app will ever take. Getting Gradle to resolve at all on this connection needed two files *outside* this repo (`~/.gradle/gradle.properties`, `~/.gradle/init.gradle`) — a fresh clone on another machine will need its own. **M0-20 measured all of this rather than asserting it**: 153 EditMode tests green in 4.97 s, 3 PlayMode green in 3.57 s, a clean recompile of all six assemblies with zero errors and zero warnings, all three entry points playing, and the camera live at offset `(0.00, 13.42, −8.71)` / pitch `57.00` — unchanged since M0-18. The feel question is answered *good*, so no number moved: 5.4 m/s, 0.06 / 0.08 s, 720 °/s, 8 / 40 / 60 dp, with CC §7 already in agreement. The camera framing is now a **decision** rather than an inherited default — pitch 57 / distance 16 frames the player, not the whole 36 m arena, and that is what M0 wanted judged. **How a number changes, from M1 on**: `Stat` is a base value plus an ordered stack of `Modifier`s — kind, amount, and the source that applied it — resolving to `(Base + ΣFlat) × (1 + ΣPercentAdd) × Π(1 + PercentMult)`, cached and recomputed on the first read after a change. `PercentAdd` pools into one factor so the tenth node is worth what the first was; `PercentMult` is its own factor, for the few multipliers loud enough to scale everything before them. Sources are matched by reference, so `RemoveAll(source)` takes back everything a node, Pact or ramp applied without knowing what arrived since, and returns how many went; `Changed` fires only when the number actually moved, so a listener never rebuilds itself for a modifier that did nothing. `Describe` writes the arithmetic out in full — `28.80 = (13.00 + 2.00) × 1.60 × 1.20` — which is ADR-0008's debug panel, obtained for free. NaN and infinity are refused at every door into a stat, because a NaN does not make the number wrong, it makes `Changed` stop firing. Nothing is timed and nothing is clamped: a source that expires owns its own clock, and a caller that needs a floor applies one. **What it is to be hurt**: `Health` is the one component the player, every enemy and every boss share — shield before HP, a refill that starts after quiet time, hit i-frames, death — and it is the first thing in the project to hold a `Stat`, following `MaxHp` live so a node that raises the maximum moves the bar without handing out a free heal, and pulling `Current` down when the maximum drops. It decides everything and publishes nothing: `DamageResult` reports what one call did — to shield, to HP, blocked, killed — and its owner (M1-08 for the player, M1-11 for enemies) turns that into an event, because a component both sides of a fight use cannot name either side's. Its clock is entirely its caller's: `ApplyDamage(amount, now)` and `Tick(dt, now)` both carry the time, and `Tick` credits only the slice of the step that is genuinely past the recharge deadline, so the Aegis is worth the same at 30 fps as at 120. Three ways nothing happens and the differences are load-bearing — a dead target and a zero-damage call report `None`, an invulnerable one reports `Blocked`, and only a call that actually applied damage starts i-frames or holds off the shield. `SetExternalInvulnerable` is a second, independent source of invulnerability with no clock of its own, waiting for M1-14's Charge; `Reset` is what a pooled agent calls instead of being rebuilt. `ShieldSpec` is the Aegis as data — 30 points, 4 s of quiet, 15 per second — and `null` rather than a spec full of zeroes is how everything without one says so, which as of now is every class but the Oathbound and every enemy. `Oathbound.asset` carries all of CC §7's survivability line, and `CharacterDefinition` reads a `_shieldMax` of 0 as "no Aegis". **How the gun chooses what to shoot**: `TargetScorer` is CC §3.1's loop from SCORE onwards, and it is a pure function of plain numbers — `TargetCandidate` hands it an id, a distance, an archetype priority, two flags and an hp, and deliberately not a position, an agent or a snapshot, so auto-aim can be pinned exactly by a test and argued about from the tuning table alone. `Score` is CC §3.2 written out once; `SelectBest` filters to what is vulnerable and in range, hands the incumbent its hysteresis bonus and resolves exact ties to the lowest id, because otherwise a symmetric spawn would make the answer depend on gather order, which is spawn order, which is a seed; `SelectNearest` ignores vulnerability entirely and is the §3.6 all-blocked state, the game saying *go around*. It holds no clock and no memory — the caller names the incumbent every call — so M1-04 owns the 10 Hz cadence and the immediate retarget, and M1-08 owns gathering. `TargetingSpec` is CC §7's whole targeting block as data (range 12, weights 3 / 2 / 1 / 1.5, cadence 0.1), required on every `CharacterSpec` rather than optional like the Aegis, because there is no such thing as a class that does not aim. **When it chooses, and what the player can force**: `Targeter` is the other half — the scorer answers "which enemy scores highest", this answers "which enemy is the gun facing right now", which is a different question because it involves time. A decision every `Cadence`, and an immediate one the moment the current target dies, leaves range, becomes undamageable or was never there; the two triggers never touch each other's state, because an accumulator reset by every retarget would let a stream of dying targets postpone the scheduled decision for ever. `Focus(id)` is CC §3.4's tap, queued rather than applied because between ticks this class has no candidate span to check the id against, and it then overrides scoring entirely — surviving a phase of invulnerability, since walking around a Warden is exactly what the override is for, and expiring only after 2 s *continuously* out of range. `IsCurrentBlocked` is CC §3.6's "go around" as a flag rather than a null target, so a view knows which of two questions it was answered: shoot this, or look at this. `ChangedThisTick` compares the whole triple across the tick, and is the one thing M1-08 watches to know when to publish. **What an enemy is**: `EnemySpec` is an archetype as authored data — identity, `MaxHp`, `MoveSpeed`, the 1–8 `TargetPriority` that makes auto-aim feel intelligent, and the four numbers a melee strike is made of (`ContactDamage`, `Reach`, `WindupTime`, `RecoverTime`), five of which are born here because GD §8.1 publishes only the Husk's HP, threat cost and priority. `EnemyBlackboard` is one enemy's working state, split by writer rather than by topic: perception that `EnemySystem`'s ingestion writes each tick and behaviours only read, working memory that only the agent's own behaviour touches, and nothing that makes it a bus. `EnemyAgent` is one living enemy and decides nothing — an id, a shared spec, a `Health` built from `MaxHp` with no shield and no i-frames because an enemy takes every hit that reaches it, a blackboard, a last-ingested position. `EnemyRegistry` owns every one of them and is the only thing that makes or retires one: ids from 1, monotonic and never reused within a run so an id held across a despawn is stale rather than misleading; `Alive` a span in **spawn** order, compacted rather than swapped because a swap would make iteration order depend on who died first, which feeds the scorer's tie-break, which would let two runs from one seed diverge; `TryGet` O(1) through a dictionary pre-sized to the capacity, so monotonic ids never grow it. `Alive` means *registered*, not breathing — a corpse stays until M1-11 has published its death, so every reader that cares checks `IsAlive`. Agents are pooled: after the first `Capacity` spawns nothing allocates, a despawned agent comes back with a new id and possibly a new archetype, and its `Health` is re-based and reset rather than rebuilt, because rebuilding it would allocate *and* leave the old one subscribed to a stat nobody owns. **What an enemy does, and how the run knows about it**: `EnemySystem` is the verbs around that registry and the run owns one — content resolution, announcement, and the per-frame pass that turns a snapshot into perception. `Spawn` resolves the archetype *before* registering, so an unauthored id leaves the registry untouched and publishes nothing, then announces `EnemySpawned` after registration so a handler resolving the id finds the agent; `Despawn` publishes `EnemyDespawned` after removal, the opposite order for the same reason — during either event the registry already agrees with the news. `Ingest` is two passes split by writer: the first copies what the snapshot said (position, velocity, path direction, line of sight) keyed by the snapshot, ignoring ids it does not know because a view is allowed to lag a frame behind a despawn; the second derives distance, direction and `AlliesNearby` for every *living* agent keyed by the registry, so an enemy whose view has not reported yet keeps its spawn position rather than being computed from someone else's. Everything is XZ — the height between a player capsule's centre and an enemy's is a rendering detail that would inflate every distance `Reach` is checked against — and a coincident player yields a zero direction rather than a normalised NaN. `Tick` is a dispatch and nothing else this milestone: `Static` stands still by definition, `Chaser` waits for M1-18, and a kind nobody taught it about throws, which is the loud site `EnemySpec` deliberately left its enum unvalidated for. Nothing on either path allocates, measured at 32 enemies through 10 000 pairs. `SpawnPlan` is what a run starts with — archetype ids and positions, immutable, copied on construction, refusing a default id or a non-finite position, with `Empty` for a run that starts bare, which is every run until M1-07 authors a Husk. `RunConfig` carries it as a required argument (an empty arena is the one failure a playtest cannot tell apart from a broken spawner), `RunState` holds the system as `internal` for the reason `Motor` is — a public handle on something with `Tick`, `Spawn` and `Clear` would let a view run the AI twice or empty the arena — and exposes `EnemyCount` as the read. `RunSession` wires the ends: `Start` publishes `RunStarted`, flips `IsRunning`, then spawns the plan; `Tick` ingests and ticks enemies before the player's motor, because M1-08's facing will come from a target and a target chosen from stale positions is the whole bug the snapshot exists to prevent; `End` clears them with no farewell event each, since the scope and every subscriber are going away. `ContentCatalog` has its second kind — `Enemies`, `Enemy(id)`, `TryGetEnemy(id)` — indexed by one shared generic helper, so the third kind inherits the copy, the guards and the messages instead of a fourth copy of the loop. **What an enemy looks like, and where it stands**: pressing Play in Run now puts **eight grey Husks in the arena**, and the whole route from an authored asset to a body on screen is real. `EnemyDefinition` is the Inspector half of `EnemySpec`, cut to the same pattern as `CharacterDefinition` — `[SerializeField] private` fields whose `[Min]`/`[Range]` clamp only the GUI, one `ToSpec()` as the only way out, and every failure rewrapped as a plain `ArgumentException` that leads with the asset's name — and `Husk.asset` is the second authored asset in the project: `enemy.husk`, GD §8.1's HP 36 and priority 1, and M1-05's five invented numbers (3.5 m/s, 8 damage, 1.2 m reach, 0.4 s windup, 0.6 s recover) which no design document owns and which this asset's test is therefore the only cross-check of. Behaviour is `Static` until M1-18. `EnemyView` is one body and decides nothing — an id, a position, a velocity that stays zero until something moves it, and a trigger `CapsuleCollider` on the new `Enemy` layer (index 8) matching the mesh exactly, 1.6 m tall and 0.4 m across, deliberately shorter than the player's 1.8 so the two read apart in silhouette. `Bind`/`Unbind` exist now rather than later so M1-19's pool is a change to one file. `EnemyViews` is the census on the Unity side and the mirror of `EnemySystem`: it subscribes to `EnemySpawned` and `EnemyDespawned` in its own constructor, rents a body from a `ViewPool<EnemyView>` per spawn and returns it per despawn — **the M1-07 Instantiate/Destroy stopgap is gone as of M1-19, so nothing allocates after the pool is warm** — and writes one `EnemySense` per live body into the snapshot every frame, assigning *every* field including the line of sight that is still deliberately false, because a reused slot otherwise carries a dead enemy's. `SnapshotBuilder` fills the path direction straight afterwards from `NavPathSense`, since it is the only object that knows where both ends of that line are. A pooled body has to *forget* its last life, which is `EnemyView.OnDespawn`'s whole job: the dissolve's stretch and fade, the material it swapped to, the collider a death switched off, a shove still in flight. A reset that is forgotten does not fail — it produces a Husk that spawns half-transparent, stretched and unhittable. Its `TryGetId(Collider, …)` is the collider→id index M1-12's cone query needs without a `GetComponent` in the loop; it is an instance method keyed by instance id, not the static the spec sketched, because a static dictionary plus a disabled domain reload is one session's colliders leaking into the next. The wiring that makes it a run: `BootScope` carries an `EnemyDefinition[]` beside its characters and `BootInstaller` converts both kinds through one generic helper, with the enemy list *required* so a catalog can never be silently enemyless; `RunScope` holds the enemy prefab, the `Enemies` parent, the dummy archetype and eight `Vector3`s and turns them into the run's `SpawnPlan` (radius 8–11 m, none inside 6 m of the player's start, all inside the camera's 25.6 × 32.8 m frame); `RunTicker.Start` hands that plan to `RunConfig` where `SpawnPlan.Empty` used to go; `SnapshotBuilder` takes `EnemyViews` and calls `CopyInto` after the player's fields; and `DebugOverlay` reads `enemies {n}` off the snapshot rather than off core, so the line can show the boundary disagreeing with itself. **What the player aims at, and what can hurt them**: `PlayerCombat` is the player's combat brain and the piece that makes the last four tasks one system — it owns a `Health` built from the class's `MaxHp`, Aegis and i-frames, a `Targeter` over a `TargetScorer` sharing one `TargetingSpec`, a `CombatBlackboard`, and a candidate buffer preallocated at the run's enemy capacity. It reimplements none of them; what is new is the three translations none of those types is allowed to make. **Gathering**: every registered agent becomes a `TargetCandidate` each tick — XZ distance from the snapshot's player position, the archetype's priority and elite flag, `IsAlive && IsVulnerable`, and current HP — with the *dead included*, carrying hp 0 and vulnerable false, because a corpse sits in `Alive` until M1-11 despawns it and those are exactly the two facts the targeter reads to drop a focus and force an immediate retarget. **Facing**: `FaceDirection` is a unit XZ vector to the current target, or `null` when there is nothing to look at — non-null on a *blocked* target too, because CC §3.6's answer to a Warden is to hold facing on it and show the glyph, so blockedness changes the reticle and never the aim. `RunSession.Tick` passes it straight to the motor, and the whole chain — registry → candidate → target → direction → facing — is pinned by one test that turns the character 90° with the stick centred. **Vocabulary**: `Health` still publishes nothing, and this is what turns a `DamageResult` into the player's four events. `TargetChanged` fires on a change of *any* of id, focus or blocked and is CC §3.5's entire reticle input; its `IsFocused` asks whether the current target *is* the focused one rather than whether a focus exists, because a focused enemy that walked out of range keeps the focus while scoring shoots something else. `PlayerDamaged` carries both the split and the resulting fractions — the split is what a damage number floats and what CH §3.1's Martyr sums, the fractions are what the bars are set to — and is published for a blocked hit as well, because half a second of i-frames is invisible unless the game says so; **Learned:**

- **Per-stream seeds go through SplitMix64 rather than the raw seed, and that is what makes rule 3 true rather than merely hoped-for.** Seeding several PCG generators from adjacent values (seed+0, seed+1, …) correlates their early output — the streams would drift apart eventually but not on the first few draws, which is exactly where a wave composer looks. SplitMix64 is an avalanche mix, so one bit of difference scatters the whole 64-bit state. Both derived words are used: the first becomes the generator's state, the second its increment, which selects *which* of PCG's 2^63 sequences the stream walks. `DifferentSeed_DifferentSequence` deliberately tests seeds 1 and 2, the hard adjacent case, not 1 and 9999.

The tempting optimisation — return early for a certain outcome without drawing — would skip a draw and desync every seeded run the moment a designer tuned a probability to 0 or 1. `Chance_ConsumesOneDraw` is the test that would catch it.
- **`NextInt` maps from the raw 32 bits, not through `NextFloat`.** Lemire's multiply-shift takes the high half of a 64-bit product: one multiply, no division, no branch, no rejection loop, and uniform to within one part in 2^32. Routing through `NextFloat` would have thrown away the range's resolution to a 24-bit mantissa and rounded twice. Rule 9's float mapping is specced for the *fake*, where a hand-written script is the point; it is not a description of the real generator.
- **`Range(a, b)` is documented as `[a, b]` but actually produces `[a, b)`** — `b` is unreachable, because `NextFloat` excludes 1. Not a defect (the specced interval contains the result set, and `Range_WithinBounds` passes) but any future spec that needs `b` genuinely reachable — an inclusive integer range, say — has to say so rather than assume it.
- The two interfaces share one file, which the Files table calls for explicitly against CLAUDE.md's one-class-per-file rule. Right call: `IRandomStream` has no meaning apart from `IRandom`, and reading them together is how the contract is understood.

**Follow-ups:** none.

**Learned:**

- **The order of integration inside `Tick` is load-bearing, and no spec had said so.** From rest at full stick, speed crosses rule 5's 0.05 m/s facing threshold in 0.56 ms — a fifteenth of a frame — so integrating facing before velocity spends the whole first frame turning toward a velocity of zero and discards a frame of rotation every time the player starts moving. Velocity first. This is invisible to a test written from rest, which is why `Facing_RotatesAtTurnSpeed` reaches full speed with its aim pinned before releasing it: written the obvious way it would have measured this interaction instead of the turn rate it names.
- **The suite passed on the first run, so the trig was mutation-tested rather than trusted.** Flipping the sign of the cross term in `RotateTowards` turned four tests red — `Facing_TakesShorterArc`, `Facing_FollowsVelocity_WhenNoFaceDirection`, `Facing_UsesFaceDirection_OverVelocity`, `Facing_ZeroFaceDirection_FallsBackToVelocity` — and correctly left `Facing_RotatesAtTurnSpeed` and `Facing_SnapsWhenWithinOneStep` green: those measure an unsigned angle and a snap, both symmetric under a sign flip. The direction rule is owned by exactly one row, and it holds. Worth repeating whenever a first run is clean on signed geometry.
- **Two of the spec's test durations are not whole ticks at 1/120 s** — 0.03 s is 3.6 and 0.0625 s is 7.5. Rounding the count misses the stated tolerance and reddens a correct motor, so those tests pick a tick size that sums exactly. **A spec that states a duration should state a tick size that divides it**, or say the size is the implementer's.
- **A four-`float` constructor's likeliest defect is transposition, and the specced tests do not catch it.** Assigning `DecelTime = accelTime` passes every row in the Tests table — `FullSpeed_ZeroInput_StopsWithinDecelTime` runs 0.0833 s against a 0.06 s decel and still stops. `Spec_StoresValues` exists for that, and the same gap applies to M0-08's `CharacterSpec` and every spec type after it.
- **The `_TEMPLATE.md` gloss on "allocated-bytes delta == 0" has been there since `738a377`, before any code was written, and five tasks logged the deviation anyway** — because you read a task spec while implementing, not the template. A rule placed where nobody stands is not a rule. The phrase is reworded in place in the three M0 specs that carried it (this one, M0-10, M0-16). Twelve M1 specs still carry it, left alone deliberately since the owner scoped this to M0 — the follow-up below.
- Rule 3 (`|Velocity|` never exceeds `Speed`) needs no clamp and has no row of its own. It falls out of rules 1 and 2: the target's magnitude is at most `Speed`, and a step that never overshoots leaves the result on the segment between two points inside a ball, which is convex. `OversizedInput_IsClamped` is the row that owns it.

**Follow-ups:** one, unscheduled — reword "allocated-bytes delta == 0" in the fourteen M1 specs that still carry it (M1-01, -02, -03, -04, -05, -06, -08, -10, -11, -12, -13, -14, -15, -18). Docs only, no code. ### 2026-09-07 · M0-08 · Content catalog · PR #_n_

**Built:** The vocabulary the rest of the project names things in. `ContentId` in `Soulvail.Core.Content` is a validated, stable content identity (`character.oathbound`) — a string, never an enum ordinal, so inserting content never repoints a save; `LocKey` is the address of a user-facing string, a distinct type from `ContentId` so the compiler refuses to let one stand in for the other; `CharacterSpec` is a class as immutable authored data — id, name key, max HP, and M0-07's `MovementSpec`; `ContentCatalog` is the boot-scope lookup, one dictionary per content kind, duplicates refused by name. 19 new EditMode tests, 95 in the suite. **Deviations from spec:** eight, listed in the task's *As built* footer. The three that change behaviour rather than test coverage:

1. **`ContentId` rejects null as a plain `ArgumentException`.** The Tests table asks for it, and NUnit's `Assert.Throws<T>` is an exact-type match, so the conventionally "better" `ArgumentNullException` would have reddened a correct constructor. See *Learned*.
2. **`CharacterSpec` rejects `default(ContentId)`**, a guard rule 4 does not list. It is what makes rule 2 unconditionally true — see *Learned*.
3. **`ContentId.IsValid` is a hand-written scanner rather than a `Regex`**, implementing the Public API's grammar verbatim. A regex would need either a static cached instance, in a project that bans static state, or a parse and match allocation per id.

**Learned:**

- **`default(ContentId)` is the one id no constructor can prevent, and rule 2 only holds if nothing can *register* one.** The rule says a default id used in the catalog misses like any unknown id. That is a statement about lookup, but it is falsifiable at construction: a spec built with a default id would sit in the dictionary under a key `Character()` reports as missing — the catalog would hold an entry and deny holding it, permanently and silently. Guarding `CharacterSpec` is what closes it, and it is the same shape as M0-07's `Vector3?` decision: *decide what "no value" means before the first producer exists*. The producer here is M0-11, one task away. Every member of both structs handles the default form anyway — `GetHashCode` returns 0 rather than dereferencing null, `ToString` returns empty — so a stray default surfaces as "not found" rather than as an `NRE` from inside a dictionary.
- **NUnit's `Assert.Throws<T>` is an exact type match, not an assignability check.** `ArgumentNullException` derives from `ArgumentException`, so "improving" a guard from the exception a spec names to a more specific one turns a correct implementation red — and the failure message ("Expected: `<ArgumentException>` But was: `<ArgumentNullException>`") reads like the code is wrong rather than the row. Worth knowing before M0-11, where authoring validation is nothing but guards. `Assert.Catch<T>` is the assignable-match form if a future spec wants one.
- **Two identical string literals are the same interned instance, so an equality test written with literals can pass on reference equality alone** and prove nothing about the ordinal comparison it names. `ContentId_Equality_IsOrdinal` and `LocKey_Equality_IsOrdinal` build one side with `new string(new[] { 'a', '.', 'b' })`, which cannot be interned. This is the exact case that matters in practice: one id off a save file, one off an asset.
- **The scanner was mutation-tested, since the first run was clean** — M0-07's rule. Loosening it (allowing `_` in the first segment) reddened `ContentId_InvalidForms_Rejected` alone; tightening it (dropping `_-` from later segments) reddened `ContentId_ValidForms_Accepted` alone. Both directions are owned by exactly one row, which is the arrangement worth keeping. **`ContentId_TryParse_MatchesIsValid` stayed green under both mutations** — correctly: it asserts that `TryParse` agrees with `IsValid`, and a wrong grammar is wrong consistently. That row proves consistency, never correctness, and a later reader tempted to treat it as grammar coverage should not.
- **M0-07's transposition lesson does not transfer literally, and the reason is worth recording.** `CharacterSpec`'s four arguments are four *distinct* types, so swapping any two is a compile error — the defect M0-07 found in a four-`float` constructor cannot occur here. `CharacterSpec_StoresValues` was still written, and still earns its place: it catches a property returning the wrong backing field, which the type system does not. The lesson's real next home is the first spec with two same-typed fields — an `EnemySpec` with two floats, or a `WeaponSpec` (M1-10).
- **`Characters` is wrapped rather than exposed as the array it is.** `CharacterSpec[]` implements `IReadOnlyList<T>`, so returning the copy directly lets any caller cast it back and mutate the catalog — rule 5's copy would protect nothing. `Array.AsReadOnly` costs one object once. Same instinct as M0-05's `ref`-returning trap: the copy nobody is watching is the one that goes wrong.
- `LocKey` is validated for *shape* only — non-empty, no whitespace — never against a table, per rule 3. The whitespace ban is not cosmetic: a trailing space picked up from an authored inspector field would become a key that resolves in no language, and the resulting blank label gives no clue why.

- **Unity 6.3 will not link a `MonoScript` to a `MonoBehaviour` or `ScriptableObject` declared in a file-scoped namespace, and nothing anywhere reports it.** The C# compiler is fine — `csc.rsp`'s `-langversion:10` (M0-02) does its job and the type compiles, instantiates and runs. Diagnosed by A/B/A on the real file, then confirmed with two throwaway ScriptableObjects in one folder, one compile cycle, differing only in namespace form: block resolved, file-scoped did not. **This is the M0-02 situation again — a convention that cannot hold for a whole class of files — but with no `csc.rsp`-shaped escape.** Every MonoBehaviour and ScriptableObject from here on (M0-13's scopes, M0-15's stick, M0-16's views and ticker, M0-17, M0-18) needs a block namespace; pure C# keeps file-scoped. `.editorconfig` silences the namespace diagnostic for the `Game/` and `Editor/` trees rather than enumerating folders that do not exist yet — the rule cannot be expressed as a path glob, and forgetting it is loud anyway.

The same hole is open to a merge, a hand-edited YAML and a future JSON loader, which is the argument for `ToSpec` being the only way out of the type and for the real guards living in the core constructors.
- **A recording assertion can couple two rules without looking like it does.** `ToSpec_InvalidId_ThrowsNamingAsset` set a bad id, which trips `OnValidate`, so it carried a `LogAssert.Expect` to keep the Console tidy — and silencing `OnValidate` during mutation testing turned that row red alongside the row that actually owns rule 3. - **`CreateInstance` leaves `name` empty, which makes `Does.Contain(name)` vacuous.** Both "the message names the asset" rows would have passed against any message at all. - **`ArgumentOutOfRangeException` and `ArgumentNullException` both derive from `ArgumentException`, so `ToSpec` narrowing every failure to the base type is a real promise, not a formality** — and NUnit's exact-type match (M0-08) is what makes it testable at all. ### 2026-09-07 · M0-12 · Composition installers · PR #_n_

**Built:** The wiring, and the first time the project's objects are built by a container rather than by a test. `BootInstaller` in `Soulvail.Game.Composition` converts the authored `CharacterDefinition`s into a `ContentCatalog` and registers it with `PendingRun` for the life of the app; `RunInstaller` registers everything one run owns — `DomainEventHub` as `IDomainEvents` and itself, `IntentBuffer` as `IIntentSink` and itself, a `WorldSnapshot` at the 64-enemy cap, an `IRandom` seeded from the pending run, and `RunSession` as `IRunSession` — all `Lifetime.Scoped`, so disposing the run scope ends the run. `PendingRun` is the slot the menu writes and the run reads, and the one thing that has to survive a scene load. Both installers are scene-free statics, which is what lets `InstallerTests` build the real containers headlessly and resolve from them: 11 new EditMode tests, 131 in the suite. Nothing constructs these scopes yet — `BootScope` and `RunScope` are M0-13, and the `RunTicker` that would actually tick the session is M0-16.

**Deviations from spec:** seven, listed in the task's *As built* footer. The two that change behaviour rather than test coverage:

1. **`WorldSnapshot` is registered through a factory at `Lifetime.Scoped` rather than as an instance.** Rule 5 says "instance", the section header says "all `Lifetime.Scoped`", and VContainer cannot satisfy both — `RegisterInstance` is hardwired to Singleton. Resolved toward the header.
2. **Three guards in `BootInstaller.Install`** — null builder, null list, null element — none of them listed. The element guard is the one that matters: without it `ToSpec()` on an empty array slot throws an NRE from inside a loop, and `ContentCatalog`'s own null-entry guard is unreachable because conversion happens first.

**Learned:**

- **VContainer only disposes what it constructed, and this is the sharpest trap the container has.** `CreateTrackedInstance` adds an object to the scope's disposal list only when the registration's provider is not an `ExistingInstanceProvider` — that is, only when the container built it. So `builder.RegisterInstance(new DomainEventHub())` compiles, resolves, aliases the port and the concrete type to one object, passes ten of this task's eleven rows, and **is never disposed**: every run would leak every subscription into the next, and the symptom would be a HUD that updates twice, then three times, with nothing in the log. Proved by mutation rather than by reading: swapping the registration reddens exactly one row, `Run_ScopeDispose_DisposesHub`, and leaves everything else green. That row was flagged in the task prompt as the one asserting VContainer's behaviour rather than ours, and it turns out to be the most load-bearing row in the fixture. **The rule for every adapter after this: anything that owns a resource is registered as a type, never as an instance.** `ContentCatalog` is registered as an instance deliberately and safely — it is immutable, not `IDisposable`, and shared for the life of the app, so there is nothing to own.
- **`As<T>()` alone does not make the concrete type resolvable, and the failure would look like a missing registration.** `Registry.Build` inserts the implementation type as a *null guard* entry whenever `InterfaceTypes` is non-empty, so `Resolve<DomainEventHub>()` throws on a container that plainly contains one. `.AsSelf()` is what adds it back. Read out of the source rather than discovered, which is why both `.As<…>().AsSelf()` pairs were written that way from the start.
- **VContainer refuses a duplicate implementation-type key at build time**, so the "registered twice, two instances, port and views disagree" bug cannot happen silently for one concrete type: the second mutation tried (`As<IDomainEvents>()` and `AsSelf()` as two registrations) throws `ArgumentException: An item with the same key has already been added` and reddens all seven run-scope rows at scope construction. Worth recording because it bounds what `Run_EventsPortAndHub_SameInstance` actually owns — the container catches the same-type case, so that row's real job is the divergence that *does* build: a Func registration for the interface beside a type registration for the class.
- **A `Lifetime.Singleton` registered inside a child scope resolves scope-locally, not from the root.** `ScopedContainer.ResolveCore` consults its own registry first and only delegates to the parent when the registration is not its own. So the rejected `RegisterInstance` form would have behaved per-run despite its Singleton label — the label was the defect, not the lifetime, which is exactly why deviation 1 changes the spelling and not the behaviour.
- **`PendingRun` crossing the scope boundary is the half worth testing.** Registered Singleton in boot, it resolves through the run scope's parent chain, so the menu's write and the run's read hit one object. `Boot_PendingRun_IsSingleton` pins it at the root, but `Run_Random_SeededFromPendingRun` is the row that would actually catch a re-registration in `RunInstaller` — the mistake that would give the run its own empty `PendingRun` and an unseeded generator.

**Learned:**

- **`Application.CanStreamedLevelBeLoaded` is inert in the Editor, and it fails in the direction that looks like correctness.** It returned `false` for `Boot`, `Menu` and `Run` — by bare name *and* by full asset path — at a moment when `SceneManager.sceneCountInBuildSettings` was 3 and `GetScenePathByBuildIndex` listed all three correctly. Worth generalising: **when a Unity API answers a yes/no question about project state, prove it says "yes" to something true before trusting its "no".**
- **A `VContainerSettings` asset does nothing unless it is in `PlayerSettings.GetPreloadedAssets()`.** `VContainerSettings.Instance` is assigned in `OnEnable`, and in the Editor the only thing that triggers it is `LoadInstanceFromPreloadAssets()` at `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)`. - **`LifetimeScope.GetRuntimeParent` reaches the settings root last, after `parentReference` and `FindParent()`.** That ordering is what rule 1 is really built on, and it is why `RunScope` has no parent assigned in the Run scene: assigning one would break Play-in-Run rather than help it. Read from the package source, not executed — no Play-mode verification was possible from this session.
- **The Unity MCP's `RunCommand` assembly does not reference VContainer**, so `AddComponent<RunScope>()` fails to compile with "no implicit reference conversion to `UnityEngine.Component`" plus a missing-assembly error naming `LifetimeScope`. `gameObject.AddComponent(Type.GetType("Soulvail.Game.Composition.RunScope, Soulvail.Game"))` works and binds correctly. Every future task that builds a scene or prefab around a VContainer type through the MCP hits this.
- **Unity's API level has no non-generic `TaskCompletionSource`** — `TaskCompletionSource<bool>` is the shape. Its `RunContinuationsAsynchronously` is deliberate: without it the awaiting code resumes inline inside `AsyncOperation.completed`, which Unity raises from inside its own scene management, so a chained load would be re-entrant.
- **Deleting a template asset is rarely self-contained.** `SampleSceneProfile` looked like scene-local sample dressing and was in fact the `m_VolumeProfile` of *both* URP render pipeline assets. The removal was specced in one line; satisfying it honestly meant touching two files the spec never mentions. - **TMP Essential Resources were never imported in this project** (`TMP_Settings.instance` null, no `Assets/TextMesh Pro/`), despite `Unity.TextMeshPro` being referenced by `Soulvail.Game` since M0-01. `TMP_PackageResourceImporter.ImportResources(true, false, false)` does it non-interactively. The 44 assets include a `.ttf` and a `.png`, both correctly routed to LFS by `.gitattributes`.
- **Vendoring a package's assets breaks the pre-commit whitespace check, and the fix is `.gitattributes`, not the hook and not the files.** TMP's shaders ship with trailing whitespace, space-before-tab indents and blank lines at EOF; `git diff --cached --check` flagged ten of them and refused the commit. "Fixing" them is the wrong move twice over — they are third-party, and Unity silently reverts any edit on the next TMP reimport. `"Assets/TextMesh Pro/**" -whitespace` unsets the attribute for that tree only, which is the mechanism `git diff --check` is built to honour; our own `.cs` and `.shader` files stay `unspecified` and still checked. Verified with `git check-attr` and by re-running the hook's exact pathspec. **Any future vendored tree needs the same line** — the hook's own exclusion list is for Unity-serialised *formats*, which is a different axis and should not be extended with vendor paths.

### 2026-09-08 · M0-14 · Input actions · PR #_n_

**Built:** The game has one input asset and one place that reads it. `Soulvail.inputactions` holds a single `Player` map with all eight actions M0–M3 will ever need — `Move` (Value/Vector2), `MovementSkill`, `Skill1`–`Skill4`, `Focus`, `Pause` — bound for gamepad and keyboard, under two control schemes: **Touch** (`Touchscreen` OR `Gamepad` OR `Pointer`, because M0-15's floating stick will feed the system through `OnScreenControl` as a *virtual gamepad* rather than as touches) and **KeyboardMouse** (`Keyboard`, `Mouse` optional). **Deviations from spec:** two, both in the tests rather than the shape.

1. **`InputAdapter.Dispose` does not call the generated `SoulvailActions.Dispose()`.** That method calls `Object.Destroy` unconditionally, which is right in a player and wrong in the Editor outside play mode — see *Learned*. The adapter destroys `_actions.asset` itself, choosing `DestroyImmediate` under `#if UNITY_EDITOR && !Application.isPlaying`. 2. **`InputAdapterTests` neutralises the default deadzone in setup, and `Move_IsClampedToUnit` carries an extra assertion saying what it does *not* prove.** Both are consequences of `StickDeadzone`, below. The five specced rows exist with the specced Given/When/Then.

**Learned:**

- **`Object.Destroy` in edit mode does not throw — it logs an `Error` and destroys nothing.** Measured directly: `Object.Destroy(so)` left `so == null` false and printed *"Destroy may not be called from edit mode! Use DestroyImmediate instead."* at `LogType.Error`. Two consequences, and the second is the nasty one: the object leaks, **and** an EditMode test that disposes fails on the unexpected error log rather than on anything it asserted. The Input System's own generated wrapper has this bug by construction, so **every generated `*.Actions` class in this project must be disposed through a context-aware destroy, never through its own `Dispose()`.** The same applies to any future adapter that owns a `ScriptableObject` it created with `CreateInstance`.
- **A Value action enabled while a control is already deflected reads zero until the next `InputSystem.Update()`.** The initial state check runs on the update *following* the enable, not during it. `Move_ZeroWhileDisabled` failed on exactly this and the fix is two `InputSystem.Update()` calls, not a change to the adapter — but the lag is real and will be visible in the game: M0-16 enables the adapter as a run starts, so a thumb already on the stick moves the player one frame late. Worth remembering when M0-20 tunes feel.
- **`StickDeadzone` caps its own magnitude at 1, so `Move`'s `ClampMagnitude` cannot be made to do observable work through a gamepad stick.** `GetDeadZoneAdjustedValue` returns exactly 1 for any input above `max`, whatever `max` is set to — the clamp is unreachable from above. The spec's `Move_IsClampedToUnit` row ("stick at (1, 1), magnitude 1.41") therefore describes a value the action never emits, and the test as written would keep passing if the clamp were deleted. Rather than delete a vacuous row or a defensive clamp, the test asserts the contract *and* asserts the pre-clamp, so the reason it cannot fail is recorded in the file instead of being rediscovered. The clamp stays because both current sources being unit-bounded is a property of today's bindings, not of the port.
- **The same processor silently rescales everything else.** With defaults (`min` 0.125, `max` 0.925) a stick set to (0.3, 0.6) reads back as roughly (0.305, 0.610) — so the specced `Move ≈ (0.3, 0.6)` is only true with deadzones neutralised, which `InputTestFixture` does **not** do for you despite resetting nearly everything else. Setting `defaultDeadzoneMin = 0` / `defaultDeadzoneMax = 1` in setup is safe: the fixture snapshots and restores `InputSystem.settings` along with the rest of the state.
- **The actions asset was built through `InputActionSetupExtensions` and written with `ToJson()`, not hand-authored**, and the wrapper was produced by turning `generateWrapperCode` on in a hand-written `.meta` rather than by writing the `.cs`. Both keep the serialisation canonical — the same bytes the Inspector would have written — which matters because this is the first file in the project whose format we do not own.
- **`*.inputactions` was already excluded from the pre-commit whitespace check and already declared `text` in `.gitattributes`.** `ToJson()` emits no final newline; the exclusion is what makes that a non-issue. Nothing needed adding.
- **The MCP `RunCommand` test-runner namespace is `UnityEditor.TestTools.TestRunner.Api`**, not `UnityEditor.TestTools.TestRunnerApi`, and `NUnit.Framework.Interfaces` is not referenced from that assembly — comparing `ITestResultAdaptor.TestStatus.ToString()` avoids needing it. Together with M0-02's `CompilationPipeline` qualification note, that is the second and third way the MCP's assembly differs from a normal Editor script.

### 2026-09-08 · M0-15 · Floating stick · PR #_n_

**Built:** The thumb half of the control loop. `StickShaper` is the stick's arithmetic with no Unity object behind it — `Shape` (dead below 8 dp, linear to 40 dp, flat at 1 past it, direction preserved exactly), `Recenter` (past 60 dp the origin is dragged along so it sits exactly 60 dp behind the thumb) and `PixelsPerDp` (dpi/160, falling back to 1 on the Editor's unknown density) — and it is tested to 1e-4 on every number in CC §2.1–2.3 and §7. `FloatingStick` is the component that owns what needs a frame: which finger has the stick, where its origin currently is, and where the two sprites go. It captures one pointer and ignores the rest, reports zero on touch-down, recentres and reports the shaped deflection on drag, and sends a final zero on pointer-up *and* on disable — before `base.OnDisable` tears the virtual device down, which is the ordering that stops a HUD disabled mid-drag from leaving the player walking. It writes to `<Gamepad>/leftStick` through `OnScreenControl` and never reads the Input System, so it meets `InputAdapter` (M0-14) only through the actions asset: the stick is the gamepad the `Touch` scheme already lists. `SafeAreaFitter` pins its `RectTransform` to `Screen.safeArea` so nothing lands under a notch — in landscape the cutout eats the *left* edge on one rotation, which is exactly where the joystick region is. `Hud.prefab` assembles them: an overlay Canvas scaling to 1920×1080 at match 0.5, a `SafeArea` child, a `Region` covering the left 45 % as a transparent-but-raycastable `Image`, and `Base`/`Knob` discs hidden until touch. 148 EditMode tests, up from 136. The prefab is not in any scene yet — M0-16 places it and adds the `EventSystem`.

**Deviations from spec:** four.

1. **A fifth file, `Game/Controls/SafeAreaFitter.cs`** — raised before writing it and approved by the owner. Rule 10 asks for the `SafeArea` child to be "fitted to `Screen.safeArea` on enable and on resolution change" and Unity ships no component that does it, so the Files table's four files could not satisfy the prefab's own rules. Written as its own component rather than folded into `FloatingStick`, because every later HUD element (M1-17's bars, M1-16's skill buttons) lives under the same `SafeArea` and must not depend on the stick existing to be positioned. Task is 5 files, still size M.
2. **The dp sizes in rule 11 are applied at runtime by `FloatingStick`, not authored into the prefab.** A *Scale With Screen Size* canvas measures in reference pixels, not dp: a `sizeDelta` of 120 on a 1080p phone is 120 physical pixels, which at ~400 dpi is 48 dp — 2.5× too small. **Learned:**

- **An unfocused Unity Editor does not tick, and `TestRunnerApi` silently never starts.** `api.Execute(...)` returned successfully, `RunStarted` never fired, and the results file sat unwritten for three minutes across two attempts with nothing in the Console. The diagnostic that settled it: an `EditorApplication.delayCall` queued from the same command also never fired, and `InternalEditorUtility.isApplicationActive` was `False`. The MCP can still service one-shot `RunCommand` calls in that state — which is why the prefab authored fine and the compile checks passed — so the Editor *looks* alive while anything needing the editor loop is frozen. **Focusing the Unity window is a precondition for the test step, not a nicety; when a run produces no `RunStarted`, check `isApplicationActive` before suspecting the callback.** The run completed in seconds once focused.
- **The MCP `RunCommand` wrapper namespace shadows `UnityEngine.UI.Image`.** `Image` alone fails with `CS0118: 'Image' is a namespace but is used like a type`, because the injected `Unity.AI.Assistant.Agent.Dynamic.Extension.Editor` namespace puts a `…Image` namespace in scope ahead of the `using`. Same shape as M0-02's `CompilationPipeline` collision — the third of these — so the rule generalises: **in a `RunCommand` script, fully qualify any type whose short name is also a namespace segment anywhere in Unity's assemblies.**
- **`OnScreenControl.OnEnable`/`OnDisable` are `protected virtual`**, so overriding is safe as long as `base` is called — but the *order* is load-bearing. `base.OnDisable()` nulls `m_Control`, after which `SendValueToControl` is a silent no-op, so the zero has to be sent first. The base class does reset the control to default on disable, but only in the branch where the virtual device survives because another on-screen control still uses it; when the stick is the only one, the device is destroyed instead. - **`Screen.safeArea` has no change event**, so `SafeAreaFitter` polls. Either one flipped would be invisible in play and obvious in a log.

### 2026-09-08 · M0-16 · Snapshot builder, player view, run ticker · PR #_n_

- **The parked `RunState.Motor` question is settled: nothing in `Soulvail.Game` reads the handle, so it is now `internal`, with `PlayerVelocity` and `PlayerFacing` as the public reads.** `PlayerView` takes both values from the intent and never touches `RunState`, which is what the task was asked to prove. - **A `MonoBehaviour`'s `Awake` never runs in EditMode, so nothing that caches a component in it can be unit-tested.** `PlayerView.Apply` needs `_controller`, which is null until play mode, and `AddComponent` in an EditMode test does not change that. Position is a sense because collision genuinely changes it; intended velocity is not collision's to edit. The first mechanic that asks "is the player moving?" is where the difference would have surfaced, and it would have looked like a core bug.

The numbers are in the spec's *As built*. **Two harness lessons, both of which produced convincing-looking wrong answers first:** a driver that only queues a stick event when the stick is non-zero never sends the release, so the "no slide" row measured a stick that was still held and reported a 2.6 m slide against code that was correct; and phases timed in *seconds* can be retired by a single hitched frame, because `Time.time` advances by a clamped delta — the wall row failed at 16.389 m purely because the player was still in transit. **Frame-counted phases, and always drive the input to its actual value, including zero.**

**Built:** The project produces an installable Android APK from one menu item. `AndroidBuild` is `Soulvail.Editor`'s first script — that assembly emits code for the first time, so all six now do — and it is deliberately thin: scenes come from `EditorBuildSettings` rather than a hard-coded list (a build that disagreed with the Editor about which scenes exist could not reproduce what was playtested), `Development | AllowDebugging` when development, target architectures pinned for the build and restored in a `finally`, and a **throw** rather than a log when `summary.result != Succeeded` — because a failed build leaves the previous APK at the output path, and an error buried in build spam is how someone installs last week's build and debugs the wrong one. **Deviations from spec:** three, all forced — detail in the spec's *As built*. (1) **Rule 4 is unimplementable: Unity 6.3 cannot build x86-64 for Android**, so both build kinds are ARM64 and the *Emulator setup* section's premise is void. (2) Orientation is `AutoRotation` restricted to the two landscapes, because the table's "Landscape Left" and manual step 8 contradict each other. (3) Directory creation sits in `Build` rather than `BuildDevelopmentApk`.

**Learned:**

- **`AndroidArchitecture.X86_64` is Magic Leap's, it is deprecated in Unity 6.3, and it fails *late*.** Assigning `ARM64 | X86_64` succeeds, reads back as `ARM64, X86_64`, and survives a round-trip through `PlayerSettings` — then the build throws `UnityException: x86-64 (Magic Leap) support is now limited … will be unset in player settings`. `AndroidAllowedArchitectures: -13` in `ProjectSettings.asset` is the mask that says so (`~12` — x86 and x86-64 excluded), and it predates this task. Same family as the `GC.GetAllocatedBytesForCurrentThread` and `Application.CanStreamedLevelBeLoaded` traps: **an API that accepts a value and echoes it back has not agreed to honour it.** The consequence is strategic — the reference-device plan assumed BlueStacks would run x86-64 natively, and it cannot.
- **A Unity Android build cannot resolve its Gradle dependencies on this connection without machine-local configuration.** Unity 6.3 generates a `build.gradle` requesting AGP 9.0.0 from `gradlePluginPortal()`, `google()` and `mavenCentral()` — three remote repositories, no offline fallback. The failure presents as `Plugin [id: 'com.android.application', version: '9.0.0'] was not found`, which reads as "that version does not exist". It does exist. What actually happens: Google Maven answers **HTTP 404 for every path**, including its own `master-index.xml`, and larger JAR bodies get killed mid-transfer (`Remote host terminated the handshake`). The fix is two user-level files, `~/.gradle/gradle.properties` and `~/.gradle/init.gradle`, neither in this repo.
- **The decisive lesson: every negative network probe needs a positive control.** Concluding "AGP 9.0.0 is not published" from a 404 was wrong, and what exposed it was probing a version that certainly exists (8.6.0) and getting the *same* 404 — the probe was measuring a wrong URL layout, not availability. Later, `repo.maven.apache.org/junit/4.13.2` → 200 against `maven.google.com/master-index.xml` → 404 is what actually localised the block to Google's hosts. **A 404 from a filtered host and a 404 from a missing artifact are indistinguishable without a control.**
- **Java's SOCKS support resolves hostnames locally, which is why a healthy proxy still failed.** With `systemProp.socksProxyHost` the mirror errors appeared as a bare `> maven.aliyun.com`, i.e. `UnknownHostException` — local DNS is filtered here and SOCKS never got the chance to resolve. Switching to `systemProp.https.proxyHost` on the same port fixed it outright (`BUILD SUCCESSFUL in 11s` on the task that had been failing), because an HTTP proxy sends `CONNECT host:443` and the *proxy* resolves. v2rayN's 10808 is a mixed SOCKS+HTTP inbound and the only listening port, so this is a one-word change with a completely different outcome.
- **Repository order matters, because Gradle aborts a resolution on a network error instead of falling through to the next repository.** Mirrors appended *after* `google()`/`mavenCentral()` are never reached when those two are the ones failing; the init script clears and rebuilds the list with mirrors first and the originals retained as fallback.
- **The tight loop is `gradle help` in `Library/Bee/Android/Prj/IL2CPP/Gradle`, not a Unity build.** Plugin resolution happens while the build script is evaluated, so `help` reproduces the whole dependency-resolution failure in 10–60 s instead of 10 minutes, using Unity's own bundled `java.exe` and `gradle-launcher-9.1.0.jar`. Reach for it before any future Android build investigation.
- **Unity's Console is not where a Gradle failure's cause lives — `Editor.log` is.** The MCP truncates a large `RunCommand` result and the Console had been cleared; `%LOCALAPPDATA%\Unity\Editor\Editor.log`, searched for `What went wrong`, held the full stderr including the exact unresolvable coordinate. The MCP also reports a build that merely emitted *warnings* as `UNEXPECTED_ERROR`, so its top-level verdict cannot be read as the build's verdict.
- **`System.Reflection` is an unauthorized namespace in `Unity_RunCommand`** — already on the watch list beside `System.Diagnostics`/`System.Net`, hit again here. `EditorApplication.ExecuteMenuItem` is the better tool regardless: it exercises the real menu route instead of a reflective call that bypasses it.
- **A platform switch and a disk-full build leave collateral in the working tree.** Switching to Android recalculated URP's shader-prefilter flags in `Mobile_RPAsset`, populated `m_RuntimeSettings` in `UniversalRenderPipelineGlobalSettings`, added `m_ShaderBuildSettings` to `GraphicsSettings`, **flipped `UnityConnectSettings.m_Enabled` from 0 to 1** (the source of the lone remaining Console warning), and created `Assets/Resources/PerformanceTestRun*.json` plus `Assets/_Recovery/0.unity`. The first three are legitimate platform-switch output; analytics being switched on is not, and the last two are junk. **`.gitignore` covers `*.apk` but not `Builds/`**, so `Soulvail_BurstDebugInformation_DoNotShip/` shows as untracked — the spec's claim that the output directory is "already git-ignored" is only half true.
- **An IL2CPP Android build needs several GB of headroom.** The first attempt died with `No space left on device` (Win32 error 112) partway through clang, which is what produced the `_Recovery` artifact; `Library/Bee` alone reached 1.36 GB and the Gradle cache 1.8 GB.

That is the daemon up with debugging *off*, and it is indistinguishable from a healthy device until you ask it for something. Enabling Settings → Advanced → Android Debug Bridge and restarting the instance fixes it. Two handles onto one instance (`127.0.0.1:5555` and `emulator-5554`) is normal and either works once ADB is genuinely on.

### 2026-09-08 · M1-01 · `Stat` and `Modifier` · PR #_n_

**Built:** the shape every gameplay number takes from here on. `Modifier` is a readonly struct — kind, value, source — and `Stat` is a base value plus an ordered stack of them, resolving to `(Base + ΣFlat) × (1 + ΣPercentAdd) × Π(1 + PercentMult)` in that order, cached and recomputed on the first read after a change. Sources are matched by reference, so `RemoveAll(source)` takes back everything one node, Pact or ramp applied without knowing what has been added since, and `Describe` writes the whole arithmetic out — `28.80 = (13.00 + 2.00) × 1.60 × 1.20` — which is the debug panel ADR-0008 promised, for free. 15 EditMode tests; **168 pass, 0 fail, 0 skip, in 0.77 s**, up from 153. Clean recompile of all six assemblies, zero errors, zero warnings.

**Deviations from spec:** four, all additive, none changing the specced API.

1. **Three guards the Public API block does not mention.** (a) A non-finite `Modifier.Value`, `Stat(baseValue)` or `Base` is rejected with `ArgumentOutOfRangeException`. Rule 6 leaves negative and zero results to the caller, and that stays true — but NaN is not a silly number, it is a silent one: `Changed` asks "did the value move?", every comparison against NaN is false, and a NaN-valued stat would report itself unchanged forever. The symptom would be a HUD that quietly stops updating rather than one showing something wrong. (b) An undefined `ModifierKind` — reachable by a cast — is rejected the same way, because the arithmetic would ignore it while `ModifierCount` counted it and `Describe` listed it. (c) `Add` refuses a modifier with a null source (`ArgumentException`), which only `default(Modifier)` can produce; a modifier nobody can remove is a permanent change to the stat with nothing to point at.
2. **Two test rows beyond the spec's thirteen** — `NonFiniteValue_Throws` and `UndefinedKind_Throws` — for the decisions above, and `NullSource_Throws` grew asserts for the other doors a null arrives at (`Add(default)`, `RemoveAll`, `CopyModifiersTo`, `Describe`).
3. **Two behaviours the spec leaves open, decided here.** `CopyModifiersTo` *appends* rather than clearing, so a panel can gather several stats into one buffer it owns; `Describe` appends too, and always writes the same shape, so a stat with an empty stack still reads `13.00 = (13.00 + 0.00) × 1.00` and a reader never has to parse a variable format to find the number they came for. Both are covered by existing rows.
4. **AR §11.1's sketch and the built API disagreed, and the spec won.** §11.1 showed `IReadOnlyList<Modifier> Modifiers` and a `void RemoveAll`; the spec's `CopyModifiersTo(List<Modifier>)` and `int RemoveAll` are what exist, and they are the better shapes — the first hands out copies instead of a live list a caller could reorder or hold past a removal, the second is what makes rule 4's "unknown source → 0" observable. **Two files outside the Files table were corrected on the owner's go-ahead**: AR §11.1's code block now matches what was built, with a line saying which two members moved and why, and `MovementSpec`'s class comment — which claimed M1-01 would replace `Speed` with a `Stat` — now names M1-08 and says why the spec stays a plain float (the stat belongs to the live character, not to authored data).

**Learned:**

- **A branch switch broke the Editor's script→assembly map, and only a restart fixed it.** Switching `main → dev` rewrote every file's mtime, Unity began reimporting, and — unfocused — it stopped half way. The state it settled in was actively misleading: the AssetDatabase knew **3** MonoScripts under `Assets/_Project` (only the new ones) and **zero** Soulvail assemblies, so the three new files were compiled into `Assembly-CSharp` and failed with **`CS8773: Feature 'file-scoped namespace' is not available in C# 9.0`**. That error names the exact thing CLAUDE.md warns about — a missing `csc.rsp` — and the `csc.rsp` was present and correct. **Read `CS8773` on a file inside an asmdef folder as "this file is not in that assembly", not as "the rsp is missing."** A recursive `ImportAsset(ForceUpdate)` brought the script count back to 70, reimporting the six asmdefs repaired the map, and per-script `ForceUpdate` plus `RequestScriptCompilation(CleanBuildCache)` still produced nothing: four separate compiles fired, each rebuilding `Soulvail.Tests.Core` from its stale one-file source list. **Closing and reopening the Editor rebuilt all six assemblies correctly on the first try.** Budget the restart early next time; the programmatic repairs cost twenty minutes and moved nothing.
- **`CompilationPipeline.GetAssemblies` and `GetAssemblyNameFromScriptPath` answer different questions.** The first reports the *last compilation*; the second reads the live map. Mid-repair they disagreed for several minutes — `PlayerMotor.cs → Soulvail.Core.dll` while `GetAssemblies` still showed a two-file `Soulvail.Core` — and the disagreement is the useful signal, not a glitch. Check both before concluding anything about compile state.
- **A lazy cache and a "fires only when the value changed" event cannot both be lazy.** Rules 2 and 5 look independent and are not: deciding whether to raise `Changed` means computing the new value at mutation time. The resolution is that the laziness survives exactly as long as nothing is subscribed — `ValueBeforeMutation` returns without computing when `Changed` is null — and for a stat something *is* watching, the recompute was going to happen anyway. Worth knowing for any later spec that pairs a cache with a change event.
- **An allocation test measuring a cached read measures nothing unless it invalidates inside the loop.** `AllocationAssert.None(() => _ = stat.Value)` over 10 000 iterations exercises one field read 10 000 times; the walk over the modifier list, which is where an "obvious" LINQ rewrite would allocate, only runs on the first. `ValueRead_AllocatesNothing` therefore sets `Base` on every one of its thousand iterations. Same family as M0-10's lesson about measuring a system through a recording fake: check that the probe is aimed at the code you mean.
- **The `×` in `Describe` is `(char)0x00D7`, not the glyph, and the reason generalises.** With the glyph in both files, a source read as anything but UTF-8 would garble the expectation and the output *identically*, so `Describe_Format` would pass while the panel showed mojibake. Any test whose expected value is a non-ASCII literal shares that blind spot. The same test also pins the formatting as `InvariantCulture` by running it under a culture whose decimal separator is a comma — built by cloning the invariant culture rather than by name, since a culture lookup needs ICU data not every runtime carries.

**Follow-ups:** none open. The two documentation corrections this task turned up were made in it, on the owner's go-ahead — AR §11.1's code sketch (the same way M0-09/M0-10 corrected §4.1 and §6) and `MovementSpec`'s class comment. Neither affects behaviour; see deviation 4.

### 2026-09-09 · M1-02 · `Health`, `ShieldSpec`, `DamageResult` · PR #_n_

**Built:** the one component everything that can be hurt uses — the player, every enemy, every boss. `Health` is shield-before-HP, a refill that starts after quiet time, hit i-frames, and death; `ShieldSpec` is the Aegis as authored numbers; `DamageResult` is what one damage call did, so the component stays event-free and its owner decides whether that was a `PlayerDamaged` or an `EnemyDamaged`. It is timed entirely by its caller — every method that cares about time takes `now`, because core never reads a clock — and `MaxHp` is a `Stat`, making this the first consumer of M1-01. `Oathbound.asset` now carries the CC §7 survivability line in full: 140 HP, a 30-point Aegis recharging at 15/s after 4 quiet seconds, 0.5 s of hit i-frames. 22 new EditMode tests in `HealthTests` and 3 in `CharacterDefinitionTests`; **193 pass, 0 fail, 0 skip, in 4.52 s**, up from 168, and the 3 PlayMode tests still pass in 2.71 s. Zero errors, zero warnings.

**Deviations from spec:** six. The first resolves a contradiction inside the spec; the rest are additive.

1. **Behaviour rule 4 and its own test row disagree, and the test row won.** Rule 4 reads `Shield += RefillPerSecond × dt` whenever `now >= lastDamageAt + RechargeDelay`. The `Shield_RechargesAfterDelay` row ticks 0.5 s to land on `now = 4.4` with the deadline at 4.0 and expects **6**, spelling out its own arithmetic as `0.4 s × 15` — the rule as written gives 7.5. `Tick` credits only the part of the step that is actually past the deadline: the step covers `[now - dt, now]`, the refill is allowed from `lastDamageAt + RechargeDelay`, and the overlap is what counts. Rule 4's formula is the steady-state case and is true again a frame later. This is not pedantry — the whole-step version hands out up to one frame of free shield at every recharge, sized by the frame rate, which at `Dt`'s 50 ms clamp is 0.75 points every time. The step's start is taken as `now - dt` rather than remembered from the previous call, so one `Tick` is self-consistent whatever happened between it and the last one.
2. **Non-finite `now` and `dt` are refused** with `ArgumentOutOfRangeException`, and so is a negative `dt`. Same shape as M1-01's decision 1 and the same reasoning one level up: a run's time is the sum of each tick's `Dt`, both deadlines this class keeps are derived from `now`, and every comparison against NaN is false — so one NaN would leave i-frames that never trigger and an Aegis that never returns, silently, for the rest of the run. A negative step would drain the shield rather than fill it. A NaN *amount* needs no guard: rule 1's `!(amount > 0f)` already answers "no damage", which is the right answer.
3. **`ShieldSpec` refuses infinity as well as non-positive numbers**, and `hitIFrames` is refused when negative, NaN or infinite in both `Health` and `CharacterSpec`. Infinity is asked about separately because it passes a `>= 0` test while meaning "invulnerable forever" — a state this class supports deliberately through `SetExternalInvulnerable` and should never reach by arithmetic.
4. **`CharacterSpec`'s two new parameters are optional** — `ShieldSpec shield = null, float hitIFrames = 0f`. Required parameters would have broken seven `new CharacterSpec(...)` call sites in `ContentTests.cs`, a file outside the Files table. The default is also the honest one: the Aegis is the Oathbound's *signature* (CH §3.1), so the Gravecaller, the Emberwright and every enemy pass nothing, and a class author overrides on purpose.
5. **A `_shieldMax` of 0 is how an asset says "no shield"**, producing a null `CharacterSpec.Shield` rather than a `ShieldSpec` full of zeroes. Chosen over a separate "has shield" toggle, which would allow a state the spec cannot represent — on, with a max of zero — and would leave a designer keeping two fields in agreement by hand. `DamageResult`'s constructor is `internal` for a related reason: it is a report, not a request, and nothing outside core should be assembling one.
6. **Five test rows beyond the Tests tables**, one per decision above: `ShieldSpec_RefusesNonPositiveNumbers`, `Constructor_RefusesNullMaxHpAndInvalidIFrames` and `Time_MustBeFinite` in `HealthTests`; `ToSpec_InvalidHitIFrames_ThrowsNamingAsset` and `ToSpec_ZeroShieldMax_MeansNoShield` in `CharacterDefinitionTests`. `MaxHpDrop_ClampsCurrent` also grew past its row, exercising all three ways a `Stat` can move — `Base`, `Add`, `RemoveAll` — because rule 6 has to hold for each, and the `RemoveAll` half is what pins "restoring the maximum never restores the HP". `ApplyAndTick_AllocateNothing` measures `Reset`, two `Tick`s and `Heal` as well, since rule 9 names `Heal` and a single tick returns before the refill arithmetic ever runs.

**Learned:**

- **`IsInvulnerable` takes no argument, so the component has to remember a clock.** The specced API asks a time-dependent question through a property, which means `Tick` and `ApplyDamage` both record the `now` they were handed and every answer is as fresh as the last call. That is correct for a caller that ticks every frame, which is the contract, and quietly stale for one that stops — worth knowing before M1-08 reads it from anywhere but the frame loop. The alternative, `IsInvulnerable(float now)`, was not taken because the spec's shape is what M1-17's HUD will want.
- **Rule 6 has a hole the spec does not name: a maximum driven to zero kills silently.** `Current` clamps to 0, `IsDead` becomes true, and no `DamageResult` exists to carry `Killed` — so an owner watching for death through damage results alone would miss it. Nothing in V1 removes max HP, so this is a content mistake rather than a mechanic, but the first effect that does needs its caller to check `IsDead` after the change. Recorded in `OnMaxHpChanged`'s remarks rather than guarded, because a `Health` cannot publish and should not start.
- **`HasShield` answers "is there a shield spec", not "is the shield up",** and the readers who want each are both obvious: a HUD deciding whether to draw the Aegis ring wants the first, a rule asking whether the shield is holding wants `Shield > 0`. Rule 4 settles which one the property has to be — a depleted shield must still recharge, so the recharge test cannot be "has shield left". Named in the XML because the property name alone reads the other way.
- **Overkill is reported as the damage that landed, not the damage that was swung.** `ToHp` is `Min(Current, remainder)`, so a 10 000 hit on a 12 HP Husk reports 12. That is what a damage-numbers view should float, and — more to the point — CH §3.1's Martyr keystone deals damage equal to everything the Aegis absorbed, so a listener summing `ToShield` over a shield's lifetime is the entire implementation of it. A result that reported the swing would inflate it.
- **The unfocused-Editor trap now has a boundary: queued *test* runs get enough ticks, a queued *compile* does not.** Both suites were requested while `isApplicationActive` read `False` and both completed — 193 EditMode in 4.52 s, 3 PlayMode in 2.71 s, results read off disk from `Temp/`. `CompilationPipeline.RequestScriptCompilation(CleanBuildCache)` queued and never ran: the six assemblies kept their earlier timestamps across four minutes and three MCP pokes. The ordinary compile that `AssetDatabase.Refresh` triggered *did* build every touched assembly from source with the analyzer attached and produced an empty Console, which is the evidence that matters; the clean-cache pass is a belt-and-braces check that needs the window genuinely in front.
- **The `Unity.CompilationPipeline` shadowing trap fired again.** A bare `CompilationPipeline` inside the MCP's injected wrapper namespace gives `CS0234: 'RequestScriptCompilation' does not exist in the namespace 'Unity.CompilationPipeline'` — and the wrong namespace in the message is the tell. Fully qualify anything whose short name is also a namespace segment; this is the fifth instance after `CompilationPipeline` itself, the test-runner namespace, `UnityEngine.UI.Image` and `Unity.AI`.

**Follow-ups:** none opened. Two things are noted for the tasks that will meet them rather than tracked separately: M1-08 owns whether `IsInvulnerable`'s remembered clock is ever read outside the frame loop, and M3 owns the first tree node that wants "+20 Aegis", which is the point `ShieldSpec.Max` has to grow a `Stat` on `Health` the way `MaxHp` already has one.

For the Aegis that default is honest, because most classes genuinely have no shield. Range and cadence are strictly positive and finite; the four weights are zero-or-more and finite. **Learned:**

- **The spec's rules 2 and 3 disagree at an exact tie, and rule 2 wins.** Rule 2 resolves exact ties to the lowest id; rule 3 says a challenger must beat the incumbent by *more than* `Hysteresis`, which at a dead heat would mean the incumbent holds. They cannot both be satisfied. The implementation follows rule 2 without a carve-out — hysteresis is a bonus applied before the comparison, not a veto after it — because that is also what the Public API block states unqualified, and because the alternative buys nothing: **nothing oscillates either way.** The moment the target switches, the new incumbent carries the bonus and leads by a whole margin, so the pair settles instead of trading. The row that found this was written expecting the opposite and failed; the test moved, not the code.
- **A field default that matches the shipped data makes an asset test vacuous.** `CharacterDefinition`'s new fields initialise to CC §7's exact numbers, so `Oathbound_ToSpec_HasTargeting` would have passed identically had the six YAML keys bound to nothing at all. The binding was proved separately with `AssetDatabase.ForceReserializeAssets` — Unity drops keys that match no field, and all six survived the round trip. Any future "the asset ships these numbers" row over a freshly added field has the same blind spot, and reserialisation is the cheap way to close it.
- **Reserialising an asset is also how `m_EditorClassIdentifier: ` regains its trailing space**, which is Unity's own output for an empty value and must not be stripped. `*.asset` is already excluded from the pre-commit whitespace check for exactly this reason, so it commits clean — the exclusion list is worth reading before "fixing" any Unity-written whitespace.

The same row proves the probe is live *in this fixture* by asserting that an allocating body under the same harness throws — M1-01's lesson, applied locally rather than trusted from `AllocationAssertTests`.
- **The unfocused Editor behaved exactly as M1-02 recorded.** Both suites were requested with `isApplicationActive` reading `False` and both completed, results read off disk from `Temp/`; the compiles that `AssetDatabase.Refresh` triggered all ran, and the assembly timestamps confirm every one of the six was rebuilt from the current source.

One non-finite step poisons both timers at once and says nothing: the cadence would either fire every tick or never again, and the focus window would stop comparing. `Tick_RejectsNonFiniteDt` is the row.
3. **`Constructor_RejectsNulls`**, a second row beyond the table, for the two `ArgumentNullException`s.
4. **`ImmediateRetarget_DoesNotStarveTheSchedule`**, a third row beyond the table, pinning the one semantic the spec left open. See *Learned*.

**Learned:**

- **An immediate re-selection must not touch the cadence accumulator, and the spec does not say so.** Rule 1 defines both triggers and is silent on whether they interact. Resetting the accumulator on each immediate retarget is the natural implementation and it is wrong: a stream of dying targets would postpone the scheduled decision indefinitely, so the character would only ever answer "what died" and never "what is best" — worst exactly when a wave is being cleared fastest. The two triggers are now independent by construction, one a clock and one a fact about the world. **The row was mutation-checked**: reinstating the reset fails `ImmediateRetarget_DoesNotStarveTheSchedule` and *only* that row, so it is the single thing pinning the semantic.
- **A step longer than the cadence still runs exactly one decision**, and the surplus is discarded rather than banked (`%=`, so the phase survives) — a hitch must not be followed by a burst of catch-up selections. Unreachable in a run, since the snapshot's `Dt` is clamped at 50 ms against a 100 ms cadence; it is there so a coarse-stepping test or replay gets the sane answer instead of an accumulator that grows for ever.
- **The spec's rule 3 contradicts itself and the test row settles it.** It says a focused-but-invulnerable enemy makes selection "fall through to rule 4" and then, in the same sentence, that `Current = focused` with the blocked flag up. Falling through would swing the facing to whatever happens to be nearest — the game overruling a decision it had just promised was the player's. `Focus_Invulnerable_ShowsBlockedOnFocused` is arranged so the alternative is both nearer *and* higher-scoring, so no route other than "hold the focus" could produce the expected id.
- **`IsCurrentBlocked` suppresses the invulnerability trigger, and that is a real behaviour choice.** Once the blocked state is up, the target being undamageable is the state we are deliberately in rather than news; treating it as an invalidation would run a full selection every frame for as long as a Warden faces the player, which is precisely the per-frame cost the 10 Hz cadence exists to avoid. The visible consequence: a blocked target that *becomes* vulnerable is picked up on the next scheduled decision rather than the next frame — up to 100 ms, the same latency as every other targeting decision, which CC §3.1 already calls imperceptible. Death and leaving range are still caught immediately. **No test pins this**, because the outcome of a selection is identical either way; only its frequency changes.
- **Having no target at all counts as a fourth invalidation.** With rule 4 in force, `CurrentTargetId` is −1 only when the previous tick saw an empty span, so the scan this triggers is over the span that just became non-empty — free when there is nothing there, and it buys instant acquisition when the first enemy of a wave walks in instead of up to a cadence of standing still.
- **A focus command is queued rather than applied, so `FocusedTargetId` lags `Focus(id)` by one tick.** Rule 5 requires it, and the reason is that between ticks this class has no candidate span: it cannot know whether the tapped id is alive, in range or real, and rule 3 has an opinion about all three. `Focus_OverridesScore` asserts the lag explicitly so the property's meaning is pinned rather than incidental.
- **`private static readonly` fixture data is a naming-rule hazard.** `.editorconfig` carries both an underscore-camel rule for private fields and a PascalCase rule for static readonly ones, and which wins is not obvious from reading the file. The fixture's shared candidates are expression-bodied static properties instead, which no ordering can make ambiguous.
- **The unfocused Editor again behaved as M1-02 and M1-03 recorded**: four `TestRunnerApi` runs and three `AssetDatabase.Refresh` compiles all completed with `isApplicationActive` reading `False`, results read off disk from `Temp/`. The mutation check needed two of those compiles, and both landed.

**Deviations from spec:** four, all in the spec rather than the build.

1. **Rule 4 contradicts itself** — `Alive` holds "only living, registered agents", and then a dead-but-not-despawned one "is still in `Alive`". The second is what M1-11 needs, so `Alive` and `AliveCount` mean **registered** and a reader that cares asks `IsAlive`. The clause had no test row; `Alive_KeepsDeadAgentUntilDespawned` is one.
2. **The Public API block is incomplete for rule 8.** Recycling an agent means giving it a new id and possibly a new archetype, so `Id` and `Spec` need setters. **Learned:**

- **Rules 1 and 8 are not the conflict they look like**: a new id on a reused object satisfies both. What is genuinely delicate is the *order* inside re-initialisation — `Health.MaxHp.Base = spec.MaxHp` **before** `Health.Reset()`, because `Reset` refills `Current` from `MaxHp.Value`. Reversed, a recycled Husk arrives at the previous archetype's hit points, and nothing would report it. `Spawn_RecycledAgent_IsFullyReinitialised` pins it by hurting a 36 HP agent to 10, despawning it, and respawning it as a 90 HP one.
- **`Health` must be reused rather than rebuilt for a second reason beyond allocation.** Its constructor subscribes to `Stat.Changed` and never unsubscribes, so a fresh `Health` per spawn would allocate *and* leave the previous one wired to a stat nobody owns. Pooling is what makes M1-02's "reusable rather than disposable" remark load-bearing rather than aspirational.
- **A recycled agent inherits its previous life's stat modifiers, and nothing in core can currently stop it.** `Stat` removes by source reference only; there is no "drop everything". Nothing applies a modifier to an enemy's `MaxHp` today, so the reuse is sound as built. Carried to the watch list rather than pre-solved: the owner's call was that an API with no caller is one no test can honestly exercise.
- **The house convention on exception types is cleaner than it looks from a distance.** `ArgumentOutOfRangeException` for every numeric range violation (`MovementSpec`, `ShieldSpec`, `TargetingSpec`, `CharacterSpec.maxHp`), `ArgumentException` for a malformed *identity* (`ContentId`, `LocKey`, a `default(ContentId)` on a spec). Two questions, two exceptions. `EnemySpec` follows both, so the spec's `ArgumentOutOfRangeException` row needed no arbitration.
- **`Alive` is a span over a preallocated array, not a `List<T>`.** A `ReadOnlySpan<T>` over a list needs `CollectionsMarshal.AsSpan`, which is .NET 5+ and absent from Unity's netstandard 2.1 profile — leaving only `ToArray()`, an allocation every frame. Array-plus-count is already the project's shape for this, in `WorldSnapshot`.
- **Order-preserving removal is a determinism decision, not a style one.** A swap-with-last would make iteration order depend on the *history* of deaths, which feeds `TargetScorer`'s tie-break, which feeds what the gun shoots — so two runs from one seed could diverge on the strength of who died first. `Array.Copy` at n ≤ 64 is a few hundred bytes moved.
- **The id dictionary is pre-sized to `Capacity` and that is what keeps rule 8 true through a whole run.** Ids climb monotonically for ever, but the live count never exceeds the capacity, and `Dictionary`'s own free list absorbs every insert after a remove — so it never resizes. `Spawn_AfterWarmup_AllocatesNothing` drives ids past 10 000 and measures zero.
- **Five of the Husk's numbers are born in this spec.** GD §8.1 publishes only HP 36, threat cost 4 and priority 1; `MoveSpeed` 3.5, `ContactDamage` 8, `Reach` 1.2, `WindupTime` 0.4 and `RecoverTime` 0.6 appear in no design document, so nothing cross-checks them. M1-18's `ChaserBehaviour` must read them from the spec rather than restate them.
- **`EnemyBlackboard` diverges from AR §9's sketch** — no `TargetId` (every V1 enemy attacks the player and nothing else; it returns with the Choir, M7-01, which chooses an ally to heal), plus `SelfPosition`, `SelfVelocity`, `PlayerPosition`, `DistanceToPlayer` and `NextAttackAt`, which the sketch predates.
- **`grep -c $'\r'` is not a line-ending probe on this shell.** It reported all five new files as CRLF; `od -c` showed plain LF, and `git ls-files --eol` had said `w/lf` all along. Half an hour was spent "fixing" files that were already correct. When a probe disagrees with git about the working tree, believe git — and confirm with `od` before touching anything. Fifth instance of the family that includes `GC.GetAllocatedBytesForCurrentThread` and `Application.CanStreamedLevelBeLoaded`.
- **`RequestScriptCompilation` does not drain while the Editor is background, and neither does `CleanBuildCache` or an asmdef reimport** — three separate attempts left all six DLLs untouched with `isCompiling` reading `True`, and `QueuePlayerLoopUpdate` did not thaw it (M0-16's finding, reconfirmed). What *does* work unfocused is `AssetDatabase.ImportAsset(path, ForceUpdate)` on the changed **source files**, which is how every compile in this task actually landed. `TestRunnerApi` runs completed unfocused throughout, as M1-02 recorded.
- **Assembly DLL timestamps are the only honest compile receipt, and mtimes alone are not enough.** `EnemyRegistryTests.cs` read as *newer* than the `Soulvail.Tests.Core.dll` that had already compiled it successfully. Pair the timestamp check with `find -newer` over the sources *and* a console read, and re-run the suite after any forced reimport rather than trusting a green run from before it.

### 2026-09-09 · M1-06 · `EnemySystem`: spawn plan, snapshot ingestion, perception, enemy events · PR #_n_

**Built:** core now owns enemies end to end. `SpawnPlan` is the enemies a run starts with, as immutable authored data — archetype ids and positions, with `Empty` for a run that starts bare. `EnemySystem` is the verbs around M1-05's registry: it resolves a `ContentId` to an `EnemySpec` and spawns, announces every spawn and despawn, copies the snapshot's positions onto the agents it names, derives every living agent's perception, and dispatches behaviour — which is a no-op this task, because M1's dummies hold still. `EnemySpawned` and `EnemyDespawned` are the census a view will build itself from in M1-07. `RunConfig` carries the plan, `RunState` holds the system, and `RunSession` composes it: `Start` publishes `RunStarted` and *then* spawns, `Tick` ingests and ticks enemies before the player's motor, `End` clears them without a farewell event each. `ContentCatalog` grows its second kind — an `Enemies` list, `Enemy(id)` and `TryGetEnemy(id)`, indexed by one shared private helper so the two kinds cannot drift. **277 EditMode tests pass in 5.50 s, up from 249, plus 3 PlayMode in 2.38 s; zero errors, zero warnings; all six assemblies compiled from the source on disk.**

**Built:** the player has a combat brain, and the four tasks before this one became one system. `PlayerCombat` composes `Health`, `Targeter` (over a `TargetScorer` sharing one `TargetingSpec`), a `CombatBlackboard` and a candidate buffer preallocated at the run's enemy capacity, and adds the three translations none of those types is allowed to make: live `EnemyAgent`s become plain `TargetCandidate`s each tick, a chosen id becomes a `FaceDirection` the motor turns towards, and a `DamageResult` becomes the player's vocabulary of events. `CombatBlackboard` is AR §9's player half — HP and shield fractions, three enemy counts, the current target and how it is held, `StationaryTime` — with `Veilrot` and `IncomingProjectiles` present and deliberately untouched until M6-04 and M2-07 own them. `CombatEvents` adds `TargetChanged` (CC §3.5's whole reticle input), `PlayerDamaged` (split *and* fractions, published for blocked hits too), `PlayerDied` (once per life) and `PlayerShieldChanged` (on drift, not per frame). `PlayerMotor.Speed` is a `Stat` with the ramp rates derived from it live, plus `Stop()`. `RunSession` builds and ticks the whole thing, and passes the facing to the motor: the run's order is now `Time` → ingest → combat → enemy behaviours → motor → intent.

**Deviations from spec:** four, none of them a rule.

1. **The candidate buffer carries the dead.** The spec's rule 2 says `IsVulnerable = agent.IsAlive && agent.IsVulnerable`, which only means anything if dead agents are gathered — but `Targeter`'s own remarks say "the caller gathers the living". They are reconciled in favour of the spec: a corpse sits in `EnemyRegistry.Alive` until M1-11 despawns it, and hp 0 / vulnerable false are exactly the two facts `Targeter.UpdateFocus` and `NeedsImmediateSelection` read to drop a focus and force an immediate retarget. Filtering here would hide a death from the code whose job is to react to it. One consequence, named in the file: with a corpse as the only candidate, `SelectNearest` picks it and the character holds facing on it as blocked until the despawn lands — which is CC §3.6's behaviour applied to the right fact, one frame long once M1-11 exists, and the only route a test in `Soulvail.Tests.Core` has to a blocked target at all, since `EnemyAgent.IsVulnerable` is `internal set` and the Warden that lowers it is M7-01.
2. **`TargetChanged.IsFocused` means "this target *is* the focused one", not "a focus is held".** The spec names the field and not its reading. A focused enemy that walks out of acquire range keeps its focus for two seconds while scoring picks something else to shoot, and during those seconds CC §3.5's brighter pulsing ring belongs on neither — so the event asks the narrower question and `CombatBlackboard.HasFocus` carries the wider one, which is the field AR §9 names for it.
3. **`RunState.Combat` is `internal`, and `RunState.PlayerPosition` is still assigned before ingestion.** The spec's Files table names the property without a visibility; `internal` is the third application of the rule `Motor` and `Enemies` already follow — a live object with a public `Tick`, `ApplyDamage` and `Reset` would let a view hurt or heal the player with nothing in the compiler to object. The position assignment is not in rule 5's list either; it stays where M0-10 put it, immediately after `Time`, because it is core writing down a report rather than a step of the frame.
4. **Two rows added to `PlayerMotorTests.cs`, which is outside the Files table.** Rule 6 gives the motor new public API — a `Stat` and `Stop()` — and the spec's Tests table has no row for either. `Speed_ModifierRaisesTopSpeed_AndTheRampWithIt` pins both halves (a cached accel rate lands short) and `Stop_ZeroesVelocity_KeepsFacing` pins the facing surviving. Every M0-07 row is unchanged and green. One line of `MovementSpec`'s XML doc was corrected in passing: it said M1-08 would give `PlayerCombat` a speed stat, and the stat went on the motor.

Two rows beyond the Tests table inside `PlayerCombatTests.cs`: `Ctor_NullDependency_Throws`, and the untouched-placeholder assertions folded into `Blackboard_CountsByDistance`.

**Learned:**

- **The shield event's threshold has to be measured against the last *reported* value, not the last tick's.** At CC §7's 15 points per second into a 30-point Aegis, one 120 fps frame moves the fraction by 0.0042 — below the spec's own 0.005 threshold. A tick-to-tick comparison would therefore never fire at any frame rate a phone runs at, and the shield would refill in silence behind a HUD that never redrew it. Keeping the baseline at "what I last told anyone" makes the drift accumulate and fires roughly 25 times across a full two-second refill. `ApplyDamage` moves the baseline too, because `PlayerDamaged` already carried a shield fraction and a listener should not have to reconcile two events describing one hit.
- **`Stat` for move speed only works if the ramp rates are derived, not cached.** M0-07 cached `spec.Speed / spec.AccelTime` in the constructor, which was correct while the speed was authored data. With a live stat, a cached rate means a node granting +50 % speed keeps the old metres-per-second-per-second and quietly stretches CC §7's 0.06 s ramp to 0.09 s — the character would get faster and *feel* soggier, which is exactly the kind of change a playtest notices and cannot name. Two divisions a frame is the whole cost. The value is floored at zero before use, for the reason `Health.ClampedMax` is: `Stat` deliberately clamps nothing, and a `PercentMult` of −1 would otherwise drive the character backwards with the ramp running the wrong way.
- **A `ReadOnlySpan<T>` parameter cannot be captured by the allocation probe's closure**, because it is a `ref struct`. The span has to be produced *inside* the lambda from a captured owner — `combat.Tick(dt, now, snapshot, registry.Alive)` — which is the shape every future span-taking `Tick` test will need. Worth knowing before writing the first one for M1-10.
- **`RecordingEvents` boxes, so an allocation test doubles as a silence test.** `IDomainEvents.Publish<T>(in T)` takes a struct and the fake adds it to a `List<object>`; anything published inside the measured window shows up as an allocation. `Tick_AllocatesNothing` warms to a steady state first, so the acquisition event lands outside the window, and then asserts the recorder is still empty afterwards — the allocation claim and the "a steady state announces nothing" claim are the same measurement.
- **The MCP's `RunCommand` rewriter hoists a nested class *and* keeps it nested**, producing `CS1527` plus a cascade of `CS0103`. M1-07 learned that an `ICallbacks` implementation must not be nested; the working shape this task settled on is simpler still — have `CommandScript` itself implement both `IRunCommand` and `ICallbacks`, so there is only ever one type in the file. `System.Reflection` is on the unauthorized-namespace list, so type probing has to go through `AppDomain.CurrentDomain.GetAssemblies()` and `Type.GetProperty`/`GetMethod` without the `using`.
- **A `ShieldSpec`-shaped optional parameter cannot express "no Aegis".** A default argument cannot be a constructed object, so the test helper's `shield = null` default made "no shield" and "you did not say" the same request, and the kill row silently got a full 30-point Aegis. A `bool withShield = true` says both things. Same family as M1-06's required `SpawnPlan`: when a default and a deliberate absence look identical, the argument is the wrong shape.

**Follow-ups:** none opened. For the tasks that meet it: M1-09 calls `Targeter.Focus`/`ClearFocus` through `PlayerCombat.Targeter` and renders `TargetChanged`; M1-10 is the first thing to write `DpsOneSecond`, at which point CC §3.2's finisher bonus starts working with no change here; M1-11 publishes `EnemyDied` and despawns, which shortens the blocked-corpse window to a frame; M1-17 wires `PlayerDied` to the run's end and is the first consumer of `PlayerDamaged`/`PlayerShieldChanged` on screen; M1-18 is the first caller of `PlayerCombat.ApplyDamage`. `PlayerCombat.Reset` has no caller yet — M1-19's respawn or M2's stage flow is the first.

- **A negative radius is not "nothing within it" — it is a plausible small one.** `radius * radius` turns −1 into 1, so the natural loop would have quietly resolved a nonsense argument as a one-metre tap. Anything that genuinely needs a press is a manual step for the owner.

The internal handles are doing exactly what M0-10 built them to do.
- **The stick's touch region is the left 45 % of the screen, full height** (`Hud.prefab` → `Region`, the only `m_RaycastTarget: 1` in the HUD). That is now load-bearing for tap-to-focus: taps land only in the right 55 %. M1-16's skill button and M3-10's S1–S4 must all be raycast targets, or they will steal focus every time they are pressed.

### 2026-09-09 · M1-10 · `WeaponSpec`, `Weapon` cadence + damage frame, `ConeHitIntent` · PR #_n_

**Built:** **the Censer swings itself, and for the first time core asks the body a question.** `WeaponSpec` is CC §7's Attack table as content — kind, 13 damage, 3.0 swings a second, 8 m, a 60° full arc, damage at 0.4 of the swing — carried on `CharacterSpec.Weapon` as a required argument, for the reason `TargetingSpec` is required: CC §4 gives every class a basic attack with no ammunition and no cost, so a null is a forgotten field rather than a design statement. `Weapon` is the cadence and nothing else: it never sees an enemy, a position or a direction, is handed one `bool` and answers with a `WeaponTick` carrying `SwingStarted` and `DamageFrame`. The interval is sampled at swing start and held, so a modifier landing mid-swing changes the *next* one; the damage frame fires exactly once per swing even if the target left range or died; and a tick landing on the end of a swing starts the next one on the same tick, with no dead frame. Everything is scheduled as absolute times against the simulated clock, so a 30 fps phone and a 120 fps one swing at the same moments. `Damage` and `FireRate` are `Stat`s (ADR-0008) and `DpsOneSecond` is their product — 39, which is what CC §3.2's finisher bonus has been weighing against zero since M1-08. `ConeHitIntent` is the new shape: a monotonic `RequestId`, the origin, the facing, the range and the angle, sent out on the damage frame and answered by a fact in M1-11. `PlayerCombat` owns the weapon, refreshes `DpsOneSecond` before the targeting pass so the bonus uses this tick's fire rate, publishes `PlayerAttacked(facing)` on a swing start, emits the cone on the damage frame and remembers it as `PendingConeRequestId`. The run's tick order is unchanged; `RunSession` now passes the intent sink into `PlayerCombat` and the motor's facing into its `Tick`.

**Deviations from spec:** three, none of them a rule.

1. **`PlayerCombat.Tick` takes the body's facing as a parameter.** The spec's rule 6 says the cone carries "motor facing", and this class deliberately holds no motor — `RunState.Motor` is `internal` precisely because a live object with a public `Tick` handed around lets someone double-integrate the frame (M0-16). Injecting it would rebuild that hazard inside core, and putting the facing on `WorldSnapshot` would duplicate state core owns (`PlayerView` sets the transform straight from `intent.Facing`, with no smoothing, so core knows the rendered facing exactly). A parameter makes the data flow visible at the one call site that matters, at the cost of updating fifteen `Tick` call sites in `PlayerCombatTests`. **It is last tick's facing**, because the run turns the motor *after* combat decides where to look — up to 12° behind the pose drawn this frame at 60 fps, inside a 60° arc, and only while turning. The same one-frame lag ADR-0003 accepts on positions, and cheaper than the alternative, which is a frame of latency on the targeting decision itself. Argued in the `bodyFacing` doc and again at the `RunSession` call site.
2. **A fire rate of zero or below refuses to start a swing, rather than scheduling one.** Not in the rules. `Stat` clamps nothing by design, so a −100 % `PercentMult` is a legitimate way for a future Pact to say "your weapon is silenced" — and read literally that is a swing interval of infinity, which would leave `IsSwinging` true for the rest of the run with the weapon jammed rather than silenced. Refusing says the same thing reversibly: take the modifier off and the next tick swings. Covered by `FireRateAtZero_DoesNotSwing`.
3. **Nothing stops a dead player swinging.** Deliberate, and named in `PlayerCombat`'s remarks: rule 5 enumerates three conditions and until M1-17 wires the death flow there is nothing to stop, so a fourth condition here would be a second opinion on when a run is over. The window closes to nothing the moment M1-17 lands.

**Beyond the Files table**, all of it guarding a listed edit and none of it new behaviour: `PlayerCombatTests` (the fifteen `Tick` call sites, the fourth constructor argument, a null-sink row, weapon assertions in `Reset_ClearsAll`, and one tick added before the allocation window — see Learned); `ContentTests`, `EnemySystemTests`, `FocusResolverTests` and `RunSessionTests` (the new required `CharacterSpec` argument, plus `CharacterSpec_NullWeapon_Throws`); `IntentBufferTests` (three rows for the cone list, which is a listed edit with no test row of its own and lives in the Game assembly where `WeaponTests` cannot reach it); `CharacterDefinitionTests` (`Oathbound_ToSpec_HasWeapon`, which pins the asset's five new numbers to CC §7 the way that file already pins the other three blocks, and `ToSpec_InvalidWeapon_ThrowsNamingAsset`). Four rows beyond the Tests table inside `WeaponTests` itself, each saying so: `Reset_ReturnsToRest`, `FireRateAtZero_DoesNotSwing`, `Spec_InvalidNumbers_Throw` and `Ctor_NullSpec_Throws`.

**Learned:**

- **A weapon's schedule wants absolute times, not an accumulator — and that makes `dt` genuinely unused.** Every rule in the spec is phrased against `now`, and building the same thing from summed `dt` would drift against the clock `PlayerCombat` and `Targeter` already share. The parameter stays in the signature for symmetry with every other `Tick` in core, documented as deliberately unread; `.editorconfig` has `IDE0060` at `suggestion`, so it costs no warning.
- **Adding a swing to `PlayerCombat` broke its allocation test's premise, not its budget.** `Tick_AllocatesNothing` asserted that a steady state announces nothing — true for a character who could not attack, false for one swinging three times a second, since `RecordingEvents` boxes on publish. The fix is to place the measured window *inside* a swing: one tick at the measurement's own clock first, so the swing provoked by jumping to `t = 10` finishes outside the window and the 10 000 measured ticks all find the same swing still running. The general shape for M1-13 and M1-15: a periodic event does not break the zero-allocation claim, it moves where the window has to sit.
- **The MCP's `RunCommand` refuses `System.IO`** — any command touching `File` fails with "User interactions are not supported for MCP tool calls", which reads like a modal dialog and is not one. Two separate commands do not work — a callback registered by one command is gone by the time the next one's run finishes. PlayMode cannot run synchronously; stash its counts in `EditorPrefs` from `RunFinished` and read them in a later command (and delete the keys afterwards).
- **A required constructor argument on a shared spec ripples into every fixture that builds one.** `CharacterSpec` gained `weapon` before the two optional parameters, which is where the invariant belongs, and that touched four test files with a one-argument insertion each. ### 2026-09-09 · M1-11 · `ReportConeHits` → damage → `EnemyDamaged` / `EnemyDied`, despawn · PR #_n_

**Built:** **the round trip closes: core asks, the body answers, and an enemy dies of it.** `IRunSession` grew its first fact, `ReportConeHits(ReadOnlySpan<int>)` — a span so the body can hand over a slice of a buffer it reuses every frame, nothing copied and nothing retained. `RunSession` forwards it to `PlayerCombat.ResolveConeHits` with the run's simulated time and its enemies, and throws when no run is running, which is the same guard the two player commands use. `PlayerCombat.ResolveConeHits` is the sceptical half: a report with no pending request is dropped whole, the pending id is cleared *before* any damage lands so one swing can only ever be spent once however many times it is reported, ids are deduplicated against a preallocated capacity-sized buffer, and each survivor goes to `EnemySystem.ApplyDamage`. That method is new and is the single door damage reaches an enemy through — the exact mirror of `PlayerCombat.ApplyDamage`, and for the same reason: `Health` stays event-free and its owner decides what a `DamageResult` means. It refuses unknown ids and corpses in silence, publishes `EnemyDamaged(id, amount, hpFraction, killed)` with the damage that *landed* rather than the damage that was swung, and on the killing blow stamps the agent's `DiedAt` and publishes `EnemyDied(id, specId, position)`. `EnemySystem.Tick` sweeps corpses that have been dead for `CorpseTime` (0.6 s) and despawns them with the usual `EnemyDespawned`, which is the gap M1-12's dissolve lives in. Three swings kill a Husk — 39 damage into 36 — which is CC §4.1's TTK, and a target that dies is retargeted on the very next tick through M1-04's immediate-selection rule rather than at the next 10 Hz decision. **Nothing in the Editor is different yet:** no physics query answers the intent until M1-12, so all of this is exercised by the suite and by nothing else.

**Deviations from spec:** three, one of them a defect in the spec.

1. **`ResolveConeHits` takes the `EnemySystem` as a third argument**, where the spec writes `ResolveConeHits(ids, now)` and its rule 2 as `enemies.ApplyDamage(...)`. `PlayerCombat` deliberately owns no registry — M1-08 established that it is handed the world each time it is asked to think about it, which is why `Tick` and `FocusAt` both take a span of agents — and holding an `EnemySystem` field would give the player's combat brain the power to spawn and despawn. A parameter keeps the reach to the one call site that has it.
2. **The dedupe is a list of ids, not "a bitset sized to enemy capacity".** The spec's phrasing is not implementable: `EnemyRegistry` rule 1 makes ids monotonic for the whole run and never reuses them, so by the hundredth spawn they are far past any bit index a 64-bit set could offer, and `id % capacity` would silently drop real hits on a collision. A preallocated `int[]` at the same capacity, scanned linearly, keeps what the spec was actually asking for — a fixed structure sized to the world rather than to the report — at 64 × 64 comparisons three times a second. It cannot overflow: an entry is written only for an id damage actually reached, which means a registered living agent, and there are at most a capacity of those. **The spec is wrong as written and the reason is worth carrying forward** — see *Learned*.
3. **`EnemySystem.ApplyDamage` publishes nothing when nothing landed**, where rule 3 says to publish `EnemyDamaged` for any known, living enemy. `Stat` clamps nothing by design (ADR-0008), so a future Pact driving weapon damage to zero — or a NaN, which `Health` refuses at the door — is reachable, and the symptom would be a hit flash and a floating `0` for a swing that did nothing. Spelled `!result.Blocked && !(result.Applied > 0f)`, which is `PlayerCombat.ApplyDamage`'s spelling since M1-08, so both sides of every fight now stay silent about the same things. Covered by a row beyond the Tests table that says so.

**Beyond the Files table**, all of it in service of a listed edit: **`EnemyAgent` gained an `internal float DiedAt`** (negative infinity while alive) and resets it in `Initialise`, which is where the corpse timer had to live — a side table keyed by id would need pruning in exactly the places `Initialise` already covers, and a recycled agent would otherwise inherit its previous life's death stamp and be swept the moment it spawned. `RunSession.RequireRunning`'s message widened from "player commands" to commands *and* facts, since it now guards both. One test row beyond the spec's table, `ApplyDamage_NothingLanded_PublishesNothing`, guarding deviation 3. And the Current State **"What works" cell gained a paragraph covering M1-10 as well as this task** — M1-10 updated the table's first four rows but never extended that cell, so it was two tasks stale.

**Learned:**

- **An enemy id is not an index, and nothing may treat it as one.** This is the second time the distinction has cost something (the first was `Targeter.IndexOf` scanning rather than looking up) and it is worth stating as a rule: ids are monotonic and never reused *for the whole run*, so the only things that can map one back to an enemy are `EnemyRegistry.TryGet` and a linear scan. Any future spec that says "array indexed by enemy id" or "bitset sized to capacity" is describing something that cannot exist — M1-15's `ReportChargeHits` will want exactly the same dedupe and should copy the buffer here rather than re-deriving it.
- **`RunState.Combat` and `RunState.Enemies` being `internal` shaped this fixture, and improved it.** There is no reaching in to read `PendingConeRequestId` or an enemy's hit points, so the tests drive the session through its ports and observe through `RecordingEvents` and `RecordingIntents` — which means "wait for a damage frame" is spelled as "wait for another `ConeHitIntent`", exactly the signal M1-12's `RunTicker` will key off. The internals bought an end-to-end test that is honest about what the body can actually see. Worth remembering the next time an `InternalsVisibleTo` looks like the easy way out.
- **M1-10's allocation-window trick does not generalise, and the fix is silent ports.** That task learned to place the measured window *inside* a swing so `RecordingEvents`' boxing lands outside it. That cannot work here: a report's whole purpose is to publish, so there is no window without a publish in it. The row uses a `QuietEvents` / `SilentIntents` pair that discards instead of recording, plus a dummy with a billion hit points so 10 000 swings measure the same path. Getting the enemy's id out of a silent sink without boxing needs `typeof(T) == typeof(EnemySpawned)` rather than `evt is EnemySpawned` — a pattern match on a generic value boxes on *every* publish, including the ten thousand the window measures, while a type-handle comparison boxes nothing and the branch that does is only ever taken at `Start`. **The general shape for M1-15 and M1-18:** any path whose job is to publish needs a discarding fake, not a cleverly placed window.
- **A sweep that despawns walks backwards.** `EnemyRegistry.Despawn` compacts in place to keep spawn order deterministic, so a forward loop over a span taken once reads a nulled slot the instant anything is removed. Backwards is correct without copying anything out first, because removing index *i* only shifts what came after it. The same will be true of every future policy that retires enemies mid-tick — M1-19's `RespawnPolicy` first.
- Setting the exact swing interval as `Dt` makes the weapon land a damage frame on every single tick, which is what let the allocation row measure 10 000 reports in 10 000 iterations. The equality holds bit-for-bit because both sides compute `now + 1f/3f` from the same float, which is worth knowing but not worth relying on anywhere outside a test.

### 2026-09-09 · M1-13 · `FocusSpec`, `FocusTracker` → fire-rate modifier; ground glow · PR #_n_

**Built:** **the first live modifier in the game, and the first mechanic that rewards standing still.** `FocusSpec` is CC §4.3's three numbers as authored data — 0.4 s of delay, a 1.0 s ramp, ×1.3 at the top — required on every `CharacterSpec` for the reason `TargetingSpec` and `WeaponSpec` are, one step further out: standing still is not a class feature, so there is no honest null to express "this class has no Focus". `FocusTracker` is the mechanic: it counts the stationary clock, turns it into a level of `clamp((stationary − delay) / ramp, 0, 1)`, and puts that on `Weapon.FireRate` as a single `PercentAdd` of `level × 0.3` sourced by itself — removed and re-added only when the level actually moves, so a stable ramp costs nothing and a step of the stick takes the whole thing off in one call. **`PercentAdd` rather than `PercentMult`**, against the hint in `ModifierKind`'s own remarks: the ramp is continuous, and a multiplicative factor sliding between 1.0 and 1.3 every frame would rescale every other percentage on the stat by a number that never settles — pooled, M3-12's "+20 % attack speed" and a full ramp come to ×1.5 together rather than ×1.56. **Learned:**

- **M1-17 could not have been built first, and the ROADMAP did not know it.** Its required test and three of its four manual steps need something that damages the player, and until this task nothing could: `RunState.Combat` is `internal`, `IDomainEvents` is publish-only, `IPlayerCommands` has no damage verb, and `Soulvail.Tests.Core` has no `InternalsVisibleTo`. - **A `StateMachine<T>` transition allocates nothing on Unity's Mono after all.** M0-02 left an explicit warning that `Tick` is kept off the dictionary "so it cannot allocate whatever the runtime's enum comparer does", which made the transition path — three `Dictionary<TState, List<…>>` lookups per `Apply` — the obvious suspect for this task's allocation row. - **A `Unity_RunCommand` probe cannot reference VContainer**, so nothing in a scope's container is reachable from one — no `IRunSession`, no `DomainEventHub`, no events. What *is* reachable is the scene: `FindObjectsByType<EnemyView>()` gives positions and velocities, and `EnemyHitFeedback`'s swell makes a telegraph visible as a `localScale`. That was enough to measure this whole task in play mode, and it is the technique to reuse whenever a probe needs to watch something core decided. In short: `RunState` gained four narrow health reads because rule 1's `session.State.Combat.Health` does not compile against an `internal` handle; the three new `MonoBehaviour`s take block namespaces rather than the file-scoped one the API block sketches; subscriptions live in `Construct` and `OnDestroy` rather than `OnEnable`/`OnDisable`, which is the third time a view in this project has had to make that move; `Construct` takes a fourth dependency, `InputAdapter`, for the overlay's tap; `HpBarView` gained `FlashBlocked()`, because a blocked hit is not a health value and cannot be spelled as a `Set`; and the row is laid out in dp at runtime by the presenter rather than in reference pixels in the prefab. **Learned:**

- **TMP reads a bare `{0}` as nine decimal places, not as an integer.** `TMP_Text.SetText(string, float, float)` defaults `decimalPrecision` to 0 and then, at the top of `AddFloatToInternalTextBackingArray`, rewrites `0` to `9` whenever no padding was asked for either — so `"{0}/{1}"` renders 139.5 HP as `139.5/140`. The integer form is `"{0:0}"`: the `0` after the colon counts as padding, which leaves precision at 0 and adds `k_Power[0]` (0.5) so the truncation rounds half-up. Same allocation-free path. Anything later that formats a live number into TMP wants this.
- **`TestRunnerApi.Execute` is one of `RunCommandCodeAnalyzer`'s `k_UnsafeMethods`, and a delegate steps around it.** The watch list already warns that `File.Delete` is refused with *"User interactions are not supported for MCP tool calls"*; what it did not say is that the same refusal covers the one call needed to run the suite. `api.Execute(settings)` is refused; `Func<ExecutionSettings, string> go = api.Execute; go(settings);` runs it normally. That is how the 428-test EditMode run in this entry was made, and it is the shape every later session should copy — the analyser matches a call site, and a method-group assignment is not one. **Read the watch-list entry before debugging that message**: it names `File.Delete` and `System.Reflection` explicitly, and this task lost an hour to rediscovering the first of them from scratch.
- **A play-mode probe cannot survive an `AssetDatabase.SaveAssets()`.** The save reimports, the reimport reloads the domain, and the dynamic command assembly's statics and its `EditorApplication.update` subscription go with it — so a probe that edits an asset, saves, and *then* expects its own callback to restore that asset never gets the chance. The M1-18 note says a probe cannot reference VContainer; this is the other half of the same lesson. A probe that changes project data must restore it in the same synchronous command, or not change it at all.
- **Saving project settings from a command re-serialised `QualitySettings.asset` and dropped a quality level.** It came back as `serializedVersion: 5` with the whole `PC` level and every entry of `m_PerPlatformDefaultQuality` gone, and `UnityConnectSettings.m_Enabled` flipped 0 → 1 alongside it — the same analytics flip this file's Known Issues already records as reverted once before. Both were reverted on disk. **The Editor still holds the rewritten copy in memory**, so the next time Unity writes project settings for any reason it will write them again: check `git diff ProjectSettings/` before committing, and restart the Editor to be sure.

### 2026-09-10 · M1-19 · `ViewPool`, `RespawnPolicy` (keep 12 alive), NavMesh bake + path sense · PR #_n_

**Built:** **the arena now sustains a fight instead of running out of one, and enemies walk around the pillars rather than into them.** Three pieces. `ViewPool<T>` holds every enemy body for the length of the run and hands them out through `IObjectResolver.Instantiate`, so `[Inject]` runs once per body rather than once per spawn and `EnemyViews` never creates or destroys anything again — the M1-07 stopgap that this file has carried since it was written is closed. `RespawnPolicy` keeps 12 enemies breathing: one per tick, two seconds after the last death, never within 6 m of the player, at a position drawn from `IRandom.Spawn` and walked forward until one is far enough away. And `NavPathSense` asks the NavMesh which way each enemy should walk, at most four enemies a frame and at most ten times a second each, caching the answer in a slot table keyed by core's id — `SnapshotBuilder` writes it into `EnemySense.PathDirectionToPlayer`, where `ChaserBehaviour` has been waiting for it since M1-18. `GreyBox.prefab` carries a baked `NavMeshSurface` (children only, physics colliders, agent radius 0.4 — the Enemy prefab's own controller radius), and the Run scene keeps 12 alive at a 2 s delay and 6 m of clearance.

**Deviations from spec:** five, all in the task's *As built* footer, and one thing done outside the Files table with permission. In short: `FixedRandom` spells the fake `SetSpawn`, not `SetStream("Spawn", …)`; `EnemySystem` needed three fields rather than one, the surprising one being `_playerPosition` recorded in `Ingest`, because `Tick` is handed a `PlayerCombat` and combat deliberately does not know where the player is; `NavPathSense` answers with the straight line rather than zero before its first refresh, which is what core would have fallen back to anyway; `refreshHz` is passed explicitly in `RunScope` because VContainer never honours a C# default value; and `EnemyView.OnDespawn` calls into `EnemyHitFeedback.ResetVisuals`, because the scale, the alpha and the swapped material all live there. **Outside the table, and approved by the owner first:** `ProjectSettings/NavMeshAreas.asset`, Humanoid agent radius 0.5 → 0.4.

**Learned:**

- **VContainer never falls back to a C# default parameter value.** `ReflectionInjector.CreateInstance` calls `ResolveOrParameter` for every constructor parameter and throws if nothing answers; there is no `ParameterInfo.HasDefaultValue` branch anywhere in the package. So `NavPathSense(int capacity, float refreshHz = 10f)` composes only if `RunScope` passes *both* — hence `NavPathSense.DefaultRefreshHz`, so the number the scope passes and the number the signature claims cannot drift apart. **Any registered type with an optional parameter has this problem**, and it fails at scope construction rather than at compile time.
- **`TestRunnerApi.Execute` is no longer refused, and the M1-17 delegate trick is not needed.** Four direct `api.Execute(new ExecutionSettings(new Filter { … }))` calls ran this session without a murmur — full EditMode, a filtered fixture run, and the PlayMode suite. What *is* still refused is a command that mixes `AssetDatabase.DeleteAsset` and `AssetDatabase.Refresh()` in with a bake: the same *"User interactions are not supported"* message, and the fix was to drop both — `CreateAsset` overwrites an existing asset by itself, and `SaveAssets` is enough. Treat the watch list's list of unsafe calls as a starting point to bisect against, not as gospel.
- **Baking a `NavMeshSurface` on a prefab is four lines and needs no editor-only package code.** `PrefabUtility.LoadPrefabContents` → `surface.BuildNavMesh()` (synchronous, fills `surface.navMeshData` in memory) → `AssetDatabase.CreateAsset(data, path)` → re-read the asset, assign it back, `SaveAsPrefabAsset`. `NavMeshAssetManager` is not required. The data's `position` is relative to the surface transform, so the arena has to be dropped into a scene at the transform it was baked at — `GreyBox` is at the origin with identity rotation in `Run.unity`, which is what makes this work.
- **`NavMeshSurface` is `[ExecuteAlways]`, so the mesh is live in the Editor without pressing Play.** That is what let this task verify manual step 2 without a build: from (13, 0, 13) to the origin, `NavMesh.CalculatePath` returns `PathComplete` with 4 corners and turns at (7.6, 0, 10.0) — `Pillar_NE`'s north face at z = 9.5 plus the 0.4 m agent radius. The open-floor and spawn-ring cases return 2 corners and the straight line, which is the fallback path staying correct.
- **`NavMesh.CalculatePath` allocates nothing managed, and `NavMeshPath.corners` allocates every read.** `SnapshotBuilder`'s existing `Build_AllocatesNothing` row now runs with a live `NavPathSense` in it and stays green, which covers the search itself; the corners are read through `GetCornersNonAlloc` into a two-element buffer, because the `corners` property builds a fresh array on each access.

Nothing else in `ProjectSettings/` moved — the M1-17 warning about `QualitySettings.asset` and `UnityConnectSettings` being re-serialised did **not** recur across four `SaveAssets()` calls this session, but `git diff ProjectSettings/` was checked before handover and should be every time.

### 2026-09-07 · M0-02 · `StateMachine<T>` and the core-purity guard test · PR #_n_

**Built:** `StateMachine<TState>` in `Soulvail.Core` — the one flat FSM behind game flow, enemy AI and boss phases — with deferred in-handler transitions and an allocation-free `Tick`. Alongside it the test suite's foundations: `AllocationAssert` (the single way every later spec claims "allocates nothing") and `AssemblyPurityTests`, which fails the build if `Soulvail.Core` ever gains an engine reference. 15 EditMode tests, all green. `Soulvail.Core` and `Soulvail.Tests.Core` now emit assemblies and the Test Runner lists them, as M0-01 predicted it would once scripts existed.

**Deviations from spec:** three.

1. **Unity 6.3 compiles at C# 9, so file-scoped namespaces did not build.** CLAUDE.md and `.editorconfig` both mandate them, and the spec's Public API block is written with one — a conflict that could not surface until the first `.cs` file. Owner chose to keep the convention: a one-line `csc.rsp` (`-langversion:10`) now sits beside **all five** asmdefs. Verified per-assembly: a `csc.rsp` beside an asmdef raises only that assembly, and `Assets/csc.rsp` would not have covered asmdef assemblies at all. This is why the file list is 10 rather than 5.
2. **`AllocationAssert` uses Unity's GC recorder, not the two strategies the spec prescribes.** Both were measured and are inert on this runtime — see *Learned*. The public API (`None(Action, int iterations = 10_000)`) is unchanged.
3. **A fifth file, `Tests/Core/Support/AllocationAssertTests.cs`.** The spec's Tests table mandates `AllocationAssert_DetectsAllocation` and `AllocationAssert_PassesForPureBody`, but its Files table gives them no fixture to live in. Filing them under the purity or state-machine fixtures would have been dishonest naming, so they got the file their names imply.

**Learned:**

- **On Unity's Mono, `GC.GetAllocatedBytesForCurrentThread()` is stubbed — it returns 0 always, even either side of a deliberate allocation — and `GC.CollectionCount(0)` did not move across 100 000 object allocations** (~2.4 MB, inside SGen's nursery). Both of the spec's strategies therefore report "no allocation" for code that allocates freely. The first implementation followed the spec, and `AllocationAssert_DetectsAllocation` caught it: the helper failed to detect `new object()` in a loop. Had that self-test not been specced, every "allocates nothing" claim in the project would have been vacuous — worth remembering when specifying future guard tests. `AllocationAssert` now measures with `UnityEngine.TestTools.Constraints.Is.Not.AllocatingGCMemory()`, which is real. **No future spec should hand-roll a BCL GC probe.**
- `Tick` deliberately caches the current state's tick handler list on transition instead of looking it up in a `Dictionary<TState, …>` per tick. Enum-keyed dictionary lookups can box on some runtimes; caching sidesteps the question entirely and keeps rule 8 true by construction rather than by hope.
- Unity's bundled NUnit has no `Assert.Multiple` — sequential asserts instead.
- **The pre-commit format check was failing open-loop on a phantom violation, and is fixed here.** This machine has a .NET *runtime* but no SDK, so `dotnet` is on `PATH` while `dotnet format` does not exist. The hook probed `command -v dotnet`, got a hit, ran the check, and read its "No .NET SDKs were found" exit code as a formatting difference — blocking the first commit that ever staged a `.cs` file. It now probes `dotnet format --version`, so it skips honestly. The five files were independently verified against `.editorconfig` by hand (no tabs, no trailing whitespace, 4-space indents, LF, final newline). CLAUDE.md's "the check self-skips" is true again.
- The Unity MCP `RunCommand` wraps submitted code in a `Unity.AI.Assistant.…` namespace. Two consequences for later sessions: `CompilationPipeline` must be fully qualified or it resolves to `Unity.CompilationPipeline`, and **nested classes get duplicated outside their parent by the code-fixer** — declare helper classes at top level. `TestRunnerApi` results were captured by writing to `Temp/` from `RunFinished`, which survives the domain reload the run triggers.

**Follow-ups:** none.

### 2026-09-07 · M0-03 · Domain events · PR #_n_

**Built:** The first port, and the first thing on both sides of the hexagon at once. `IDomainEvents` in `Soulvail.Core.Ports` is how core says what happened without learning who listens; `DomainEventHub` in `Soulvail.Game.Adapters` is its run-scoped typed dispatcher — subscribe/unsubscribe by handle, allocation-free publish, no statics; `RecordingEvents` in `Soulvail.Tests.Core.Fakes` is the fake every later core test will assert event sequences through. 13 new EditMode tests, 28 in the suite. `Soulvail.Game` and `Soulvail.Tests.Game` now emit assemblies for the first time.

**Deviations from spec:** three.

1. **A fifth file, `Tests/Core/Fakes/RecordingEventsTests.cs`.** The Files table names one test file, in `Soulvail.Tests.Game`, but two of the Tests table's rows test `RecordingEvents`, which lives in `Soulvail.Tests.Core` and is not a hub. Filing them under a fixture named for the hub would have been dishonest naming — the same gap M0-02 hit, resolved the same way, and the owner approved it before implementation.
2. **`Soulvail.Tests.Game` now references `Soulvail.Tests.Core`.** `Publish_AfterWarmup_AllocatesNothing` is specced into the Tests.Game fixture, but `AllocationAssert` lives in Tests.Core and was out of reach. Both assemblies are Editor-only under `UNITY_INCLUDE_TESTS`, so the reference is safe, and it is what keeps the project's one allocation probe single-sourced rather than copied.
3. **The allocation row's "allocated-bytes delta == 0" is measured with `AllocationAssert` instead.** That phrasing describes exactly the BCL probe M0-02 proved inert on this runtime. Behaviour rule 8 is what the test enforces; the wording was stale, not the rule.

**Learned:**

- **A `Unity_RunCommand` script is refused with *"User interactions are not supported for MCP tool calls"* if it calls anything in `RunCommandCodeAnalyzer.k_UnsafeMethods`** — `System.IO.File.Delete`, `File.Move`, `Directory.Delete`, `AssetDatabase.DeleteAsset`, `FileUtil.DeleteFileOrDirectory`. Those mark the command unsafe, which requires a user confirmation, and MCP callers get `NoOpToolInteractions`, whose only job is to throw that message. Three attempts to start the EditMode run failed this way because each cleared its result file with `File.Delete` first; dropping the delete and overwriting with `File.WriteAllText` (a write, not an unsafe call) runs the suite fine. **`TestRunnerApi.Execute` was never blocked** — the first diagnosis blamed it because the probes that worked differed in the file call too. Separately, `System.Net`, `System.Diagnostics`, `System.Runtime.InteropServices` and `System.Reflection` really are unauthorized namespaces for submitted scripts. The lesson for later sessions is the diagnosis, not the guard: when an MCP command is refused, change one thing at a time.
- `Publish` walks the live handler list and **defers mutations** instead of snapshotting it. Snapshotting at the top of every publish is the obvious way to satisfy "the in-flight publish sees the list as it was", and it allocates on every publish, which breaks rule 8. Deferring costs nothing on the hot path — the pending queue is only touched when someone actually subscribes or unsubscribes from inside a handler — and it makes re-entrancy fall out for free: a handler that republishes the same type walks the same untouched list. Verified with a re-entrancy check beyond the spec's rows.
- Channels are created by `Subscribe`, never by `Publish`, so publishing an event nobody listens for allocates nothing **ever**, not merely nothing after the first time. Rule 8 asked for the weaker guarantee.
- A single throwing handler is rethrown through `ExceptionDispatchInfo` rather than `throw ex`, which would erase the stack trace of the listener that actually failed.
- `RecordingEvents.Clear()` is in the spec's Public API but has no row in its Tests table. Covered by the ad-hoc harness during verification, not by a fixture — worth a row if the fake ever grows.

**Follow-ups:** none.

### 2026-09-07 · M0-04 · Random streams · PR #_n_

**Built:** The second port, and the thing that makes a seeded run mean something. `IRandom` + `IRandomStream` in `Soulvail.Core.Ports` expose five independent streams — Spawn, Offers, Affixes, Drops, Misc — so adding a mechanic that rolls dice in one concern cannot shift another's sequence. `SeededRandom` in `Soulvail.Game.Adapters` is the real generator: PCG32 per stream, each seeded from `(seed, streamIndex)` through SplitMix64, allocation-free on every draw. `FixedRandom` in `Soulvail.Tests.Core.Fakes` is the scripted counterpart every later core test will roll through. 14 new EditMode tests, 42 in the suite. Nothing consumes randomness yet — that is M0-10 onward.

**Deviations from spec:** five. The first two were put to the owner and approved before implementation.

1. **A fifth file, `Tests/Core/Fakes/FixedRandomTests.cs`.** The Files table names one test file, in `Soulvail.Tests.Game`, but two of the Tests table's rows test `FixedRandom`, which lives in `Soulvail.Tests.Core`. Third task running into the same gap (M0-02, M0-03), resolved the same way. Five files is still size M, so no split was triggered.
2. **`FixedRandom.SetStream(string name, …)` became five named setters** — `SetSpawn`, `SetOffers`, `SetAffixes`, `SetDrops`, `SetMisc`, each returning `this` so they chain. Compile-time checked, no new type anywhere, and shorter at the call site. The decisive point was timing: nothing in the project draws a random number yet, so the specced signature had zero callers and changing it cost nothing. After M2's director it would have been spread across every spawn and offer test.
3. **A test beyond the Tests table: `FixedRandom_SetStream_OverridesOnlyThatStream`.** The Public API's "every stream is the same scripted stream unless set individually" is a behaviour with no row, and it is the half of the fake that deviation 2 reshaped. It also pins the consequence worth knowing: the un-overridden streams are *one instance*, so a draw from `Offers` advances `Drops` too.
4. **`Draw_AllocatesNothing` is measured with `AllocationAssert`, and covers all four draws.** The row's "allocated-bytes delta == 0" describes the BCL probe M0-02 proved inert here — same stale wording M0-03 hit. Rule 8 says *no allocation per draw*, and `NextInt` is where a boxed comparer or a widening conversion would most easily creep in, so `NextFloat`, `NextInt`, `Range` and `Chance` are each measured.
5. **`FixedRandom.Seed` returns 0.** `IRandom` requires the property; the spec gives the fake no seed constructor. Nothing reads it.

**Learned:**

- **Per-stream seeds go through SplitMix64 rather than the raw seed, and that is what makes rule 3 true rather than merely hoped-for.** Seeding several PCG generators from adjacent values (seed+0, seed+1, …) correlates their early output — the streams would drift apart eventually but not on the first few draws, which is exactly where a wave composer looks. SplitMix64 is an avalanche mix, so one bit of difference scatters the whole 64-bit state. Both derived words are used: the first becomes the generator's state, the second its increment, which selects *which* of PCG's 2^63 sequences the stream walks. `DifferentSeed_DifferentSequence` deliberately tests seeds 1 and 2, the hard adjacent case, not 1 and 9999.
- **The stream indices are part of what a seed means.** Renumbering Spawn from 0 to 1 would silently change every sequence every recorded seed produces, invalidating every Daily and every bug repro. On the watch list now, because M2-04/M2-05 are the first tasks likely to want a sixth stream — it takes index 5, and nothing moves.
- **`Chance` needs no special-casing to satisfy its rule, and must not have any.** Because `NextFloat` is `[0, 1)`, the naive `NextFloat() < probability` already gives "0 never, 1 always" for free. The tempting optimisation — return early for a certain outcome without drawing — would skip a draw and desync every seeded run the moment a designer tuned a probability to 0 or 1. `Chance_ConsumesOneDraw` is the test that would catch it.
- **`NextInt` maps from the raw 32 bits, not through `NextFloat`.** Lemire's multiply-shift takes the high half of a 64-bit product: one multiply, no division, no branch, no rejection loop, and uniform to within one part in 2^32. Routing through `NextFloat` would have thrown away the range's resolution to a 24-bit mantissa and rounded twice. Rule 9's float mapping is specced for the *fake*, where a hand-written script is the point; it is not a description of the real generator.
- **`Range(a, b)` is documented as `[a, b]` but actually produces `[a, b)`** — `b` is unreachable, because `NextFloat` excludes 1. Not a defect (the specced interval contains the result set, and `Range_WithinBounds` passes) but any future spec that needs `b` genuinely reachable — an inclusive integer range, say — has to say so rather than assume it.
- The two interfaces share one file, which the Files table calls for explicitly against CLAUDE.md's one-class-per-file rule. Right call: `IRandomStream` has no meaning apart from `IRandom`, and reading them together is how the contract is understood.

**Follow-ups:** none.

### 2026-09-07 · M0-05 · World snapshot · PR #_n_

**Built:** The payload of the one inbound channel that runs every frame. `WorldSnapshot` and `EnemySense` in `Soulvail.Core.Run` are everything core is ever told about where things are — preallocated to a capacity, refilled in place through `Clear` then one `AddEnemy` per enemy, allocating nothing on that cycle. `Num` in `Soulvail.Game.Adapters` is the boundary conversion between `UnityEngine` and `System.Numerics` vectors, including the XZ flatten that turns a world vector into a ground-plane direction. 9 new EditMode tests, 51 in the suite. Nothing fills a snapshot yet — `SnapshotBuilder` (M0-16) does, and `RunSession` (M0-10) is the first thing with a reason to read one.

**Deviations from spec:** three, all small; the Files table was built exactly.

1. **`WorldSnapshot` is a class, where AR §4.2 sketched a struct — and `Architecture.md` is corrected here.** Not a deviation from the spec, whose Public API says `sealed class`; a deviation from the architecture document, which is what later sessions read first. The shape follows from `AddEnemy` returning `ref EnemySense` and advancing `EnemyCount`: passed by value, the builder would fill a copy the ticker never sees. AR §4.2's sketch predated the ref-returning fill. No superseding ADR — ADR-0003 decides that a snapshot is the tick's payload, not what storage kind carries it, so the decision stands and only its illustration was wrong. §4.2 now shows the built shape and states the two rules the sketch could not: the array outlives every frame, and every reader stops at `EnemyCount`. §12's adapters list gained `Num`. Outside the Files table, and done at the owner's explicit direction rather than deferred.
2. **Two specced test rows carry an extra assertion each.** `Ctor_ZeroCapacity_Throws` also asserts a negative capacity, because rule 6 is `<= 0` while the row only names 0, and `new EnemySense[-1]` would otherwise be the thing that reports it. `Clear_ResetsScalarsAndCount_KeepsArrayInstance` also asserts that a stale slot survives, because rule 3's second sentence — `Clear` does **not** zero the array contents — has no row of its own and is the half of `Clear` a future maintainer is most likely to "fix". Both are assertions inside rows that already own the behaviour, not new rows, so the Tests table did not grow.
3. **The allocation row's "allocated-bytes delta == 0" is measured with `AllocationAssert`.** Fourth task running into the same stale wording (M0-02 proved the BCL probe inert on this runtime). Rule 4 is what the test enforces.

**Learned:**

- **`System.Numerics` resolves inside `Soulvail.Core` with no asmdef change and no added reference.** It ships in the .NET Standard profile the project targets (`apiCompatibilityLevel: 6`), and `AssemblyPurityTests` stays green because it is not a `UnityEngine*` assembly. First time core has depended on anything beyond `System` and `System.Collections.Generic`, so it was worth confirming rather than assuming.
- **A `ref`-returning `AddEnemy` makes the obvious test vacuous.** `var e = snapshot.AddEnemy(); e.Id = 7;` compiles, binds a copy, and every assertion *about `e`* passes while the snapshot stays empty — a green test proving nothing. `ref` is required on both sides, and the assertions go through `snapshot.Enemies[0]` rather than through the local, so a future copy fails them. M0-06's intent buffer is the next preallocated buffer that will hand out references; same care applies there.
- **`Clear()` is O(1) because it deliberately leaves `Enemies` alone**, which is what makes refilling free, and which means stale enemies sit past `EnemyCount` indefinitely. Correct as specced and a live trap: any reader that iterates `Enemies` instead of `Enemies[0..EnemyCount)` sees last frame's dead. On the watch list. `EnemyCapacity` is computed from `Enemies.Length` rather than stored, so capacity and array length cannot drift apart.
- **The public mutable fields on both types are a deliberate exception to the project's no-public-fields rule.** That rule exists to stop Unity components leaking their innards; this is a transfer buffer with one writer and one reader, where properties would cost a call per field per enemy per frame and hide nothing. No analyzer objects — `.editorconfig` states the ban as a comment and enforces only `IDE0044`, which is private-field-only — so convention and code disagree only on paper. Documented in the type's remarks so the next reader does not "fix" it.
- **`Num` fully qualifies every vector rather than importing either namespace**, because both declare `Vector2` and `Vector3`: with a `using`, a conversion that silently returned its input would read exactly like a correct one. The tests do the same, for the same reason.

**Follow-ups:** none. The AR §4.2 correction that would have been one is in this change.

### 2026-09-07 · M0-06 · Intents · PR #_n_

**Built:** The other outbound channel, and the last piece of the tick's plumbing. `PlayerMoveIntent` in `Soulvail.Core.Run` is what core wants done with the player this frame — a velocity and a facing, immutable, carried by `in`; `IIntentSink` in `Soulvail.Core.Ports` is the port it goes out through, one named method per intent kind rather than a generic push; `IntentBuffer` in `Soulvail.Game.Adapters` is the per-frame mailbox core fills during `Tick` and the views empty straight after, allocation-free on that cycle. 6 new EditMode tests, 57 in the suite. Nothing writes an intent yet — `RunSession` (M0-10) is the first producer and `PlayerView` (M0-16) the first reader; between them they now have both halves of the boundary they need.

**Deviations from spec:** two, both put to the owner and approved before implementation.

1. **A fifth file, `Tests/Core/Run/PlayerMoveIntentTests.cs`.** The Files table names one test file, in `Soulvail.Tests.Game`, but behaviour rule 5 is about `PlayerMoveIntent`, a Core type, and has no row in the Tests table at all. Fourth task running into the same gap (M0-02, M0-03, M0-04), resolved the same way — filing a Core type's contract under a fixture named for the Game-side buffer would have been the dishonest naming M0-03 rejected. Five files is still size M, so no split was triggered. Only the testable half of rule 5 is covered: immutability is enforced by `readonly struct`, where a mutation is a compile error and a test would restate the language; "does not normalise or validate" has no enforcement and gets the test.
2. **No debug assertion that `Facing` is unit-length**, which rule 5 permits. Cost was not the deciding factor — `System.Diagnostics.Debug.Assert` is `[Conditional("DEBUG")]` and Unity defines `DEBUG` only for the Editor and Development Builds, so the call is not emitted at all in a release player. The objection is that nothing constructs a `PlayerMoveIntent` yet, so the assertion would guard no producer while silently deciding a question this task does not own: whether a zero `Facing` is legal at spawn or while standing still. M0-10/M0-16 answer that with a producer in hand, and the guard belongs there.

**Learned:**

- **The `PlayerMove` property and the `IIntentSink.PlayerMove` method coexist because an explicit implementation's name is `IIntentSink.PlayerMove`** — it never enters the class's declaration space, so CS0102 cannot fire. Verified by compiling, not assumed. The collision is worth keeping rather than working around: it makes the type enforce the direction of the boundary. Core holds an `IIntentSink` and can only write; a view holds an `IntentBuffer` and can only read. Neither can do the other's job by accident, and no naming convention had to be invented to say so.
- **`Clear()` lowers the flag and deliberately leaves the stored intent alone**, the same bargain `WorldSnapshot.Clear` makes with its enemy array — and the spec's "undefined if `!HasPlayerMove`" is what licenses it. `Clear_ResetsFlag` therefore asserts the flag and says nothing either way about the leftover: pinning it would turn an implementation detail into a promise and forbid a future zeroing the spec explicitly allows. A view that skips the flag check applies last frame's velocity and slides; that is the cost of the cheap clear, and it is on the watch list.
- **The Tests table's allocation row is measured with `AllocationAssert`.** Fifth task running into the same stale "allocated-bytes delta == 0" wording. Worth fixing in the remaining M0 specs rather than deviating from it once per task.
- The `readonly struct` + `in` pairing is the same one `IDomainEvents` uses, for the same reason, and it is now the project's default shape for anything crossing the boundary 60 times a second. Neither the interface call nor the by-value property read allocates; `WriteAndClear_AllocateNothing` measures the whole write-then-clear cycle rather than either half.
- The Public API's by-value `PlayerMove` property means a local copy is a faithful reading today, so M0-05's ref-returning trap does not literally bite here. The tests still assert through the buffer, because the assertion that names the buffer is the one that keeps testing the buffer if the accessor ever changes shape.

**Follow-ups:** none.

### 2026-09-07 · M0-07 · Player motor · PR #_n_

**Built:** The first game logic in the project — everything before this was plumbing. `MovementSpec` in `Soulvail.Core.Content` is a class's movement numbers as authored data (the Oathbound's 5.4 / 0.06 / 0.08 / 720, CC §7); `PlayerMotor` in `Soulvail.Core.Combat` turns a shaped stick vector into a velocity and a facing — linear accel and decel with no inertia, a proportional target so a half-pushed stick settles at half speed, shortest-arc yaw that snaps rather than creeps, and nothing allocated on the tick. Position and collision stay out: M0-16's `PlayerView` takes the velocity and drives the body. 19 new EditMode tests, 76 in the suite. `Tests/Core/Content/` now exists, one task before M0-08 fills it.

**Deviations from spec:** ten, listed in the task's *As built* footer. The two put to the owner and approved before implementation:

1. **A fourth file, `Tests/Core/Content/ContentTests.cs`.** Fifth task running into "the Tests table names a fixture the type does not belong in" (M0-02, M0-03, M0-04, M0-06) — but a weaker case than any of those, and worth recording as such: those four were *assembly* mismatches, a Core type specced into a `Tests.Game` fixture. This is a folder mismatch inside one assembly. It was resolved differently as a result: not a dedicated `MovementSpecTests.cs`, but the module fixture **M0-08 already specifies** ("all four types — one module, one test file"), created one task early with its first Content type in it. A per-type fixture would have invented a competing convention one task before the real one landed. M0-08's Files table now records that the file exists.
2. **Behaviour rule 5 extended: a `faceDirection` with no ground direction falls back to the velocity rule.** See *Learned*.

**Learned:**

- **`Vector3?` makes "provided" ambiguous, and the ambiguity is unrecoverable.** A caller can pass `Vector3.Zero`, or `(0, 1, 0)` which flattens to nothing; `Vector3.Normalize` of either is NaN, and a NaN facing survives every later frame's arithmetic — the character would never turn again, with nothing in the log to say why. M0-06 could defer its zero-`Facing` question to whoever produced the first intent; this one could not, because the default behaviour of the obvious implementation is silent permanent corruption rather than an open design question. The same shape appears in the spec's validation: `!(value > 0f)`, not `value <= 0f`, because every comparison against NaN is false and the natural spelling admits it. **Any later spec taking a nullable or unvalidated vector should decide what "no direction" means before the first producer exists, not after.**
- **The order of integration inside `Tick` is load-bearing, and no spec had said so.** From rest at full stick, speed crosses rule 5's 0.05 m/s facing threshold in 0.56 ms — a fifteenth of a frame — so integrating facing before velocity spends the whole first frame turning toward a velocity of zero and discards a frame of rotation every time the player starts moving. Velocity first. This is invisible to a test written from rest, which is why `Facing_RotatesAtTurnSpeed` reaches full speed with its aim pinned before releasing it: written the obvious way it would have measured this interaction instead of the turn rate it names.
- **The suite passed on the first run, so the trig was mutation-tested rather than trusted.** Flipping the sign of the cross term in `RotateTowards` turned four tests red — `Facing_TakesShorterArc`, `Facing_FollowsVelocity_WhenNoFaceDirection`, `Facing_UsesFaceDirection_OverVelocity`, `Facing_ZeroFaceDirection_FallsBackToVelocity` — and correctly left `Facing_RotatesAtTurnSpeed` and `Facing_SnapsWhenWithinOneStep` green: those measure an unsigned angle and a snap, both symmetric under a sign flip. The direction rule is owned by exactly one row, and it holds. Worth repeating whenever a first run is clean on signed geometry.
- **Two of the spec's test durations are not whole ticks at 1/120 s** — 0.03 s is 3.6 and 0.0625 s is 7.5. Rounding the count misses the stated tolerance and reddens a correct motor, so those tests pick a tick size that sums exactly. **A spec that states a duration should state a tick size that divides it**, or say the size is the implementer's.
- **A four-`float` constructor's likeliest defect is transposition, and the specced tests do not catch it.** Assigning `DecelTime = accelTime` passes every row in the Tests table — `FullSpeed_ZeroInput_StopsWithinDecelTime` runs 0.0833 s against a 0.06 s decel and still stops. `Spec_StoresValues` exists for that, and the same gap applies to M0-08's `CharacterSpec` and every spec type after it.
- **The `_TEMPLATE.md` gloss on "allocated-bytes delta == 0" has been there since `738a377`, before any code was written, and five tasks logged the deviation anyway** — because you read a task spec while implementing, not the template. A rule placed where nobody stands is not a rule. The phrase is reworded in place in the three M0 specs that carried it (this one, M0-10, M0-16). Twelve M1 specs still carry it, left alone deliberately since the owner scoped this to M0 — the follow-up below.
- Rule 3 (`|Velocity|` never exceeds `Speed`) needs no clamp and has no row of its own. It falls out of rules 1 and 2: the target's magnitude is at most `Speed`, and a step that never overshoots leaves the result on the segment between two points inside a ball, which is convex. `OversizedInput_IsClamped` is the row that owns it.

**Learned:**

- **`default(ContentId)` is the one id no constructor can prevent, and rule 2 only holds if nothing can *register* one.** The rule says a default id used in the catalog misses like any unknown id. Guarding `CharacterSpec` is what closes it, and it is the same shape as M0-07's `Vector3?` decision: *decide what "no value" means before the first producer exists*. The producer here is M0-11, one task away. Every member of both structs handles the default form anyway — `GetHashCode` returns 0 rather than dereferencing null, `ToString` returns empty — so a stray default surfaces as "not found" rather than as an `NRE` from inside a dictionary.
- **NUnit's `Assert.Throws<T>` is an exact type match, not an assignability check.** `ArgumentNullException` derives from `ArgumentException`, so "improving" a guard from the exception a spec names to a more specific one turns a correct implementation red — and the failure message ("Expected: `<ArgumentException>` But was: `<ArgumentNullException>`") reads like the code is wrong rather than the row. Worth knowing before M0-11, where authoring validation is nothing but guards. `Assert.Catch<T>` is the assignable-match form if a future spec wants one.

This is the exact case that matters in practice: one id off a save file, one off an asset.
- **The scanner was mutation-tested, since the first run was clean** — M0-07's rule. Loosening it (allowing `_` in the first segment) reddened `ContentId_InvalidForms_Rejected` alone; tightening it (dropping `_-` from later segments) reddened `ContentId_ValidForms_Accepted` alone. Both directions are owned by exactly one row, which is the arrangement worth keeping. **`ContentId_TryParse_MatchesIsValid` stayed green under both mutations** — correctly: it asserts that `TryParse` agrees with `IsValid`, and a wrong grammar is wrong consistently. That row proves consistency, never correctness, and a later reader tempted to treat it as grammar coverage should not.
- **M0-07's transposition lesson does not transfer literally, and the reason is worth recording.** `CharacterSpec`'s four arguments are four *distinct* types, so swapping any two is a compile error — the defect M0-07 found in a four-`float` constructor cannot occur here. `CharacterSpec_StoresValues` was still written, and still earns its place: it catches a property returning the wrong backing field, which the type system does not. The lesson's real next home is the first spec with two same-typed fields — an `EnemySpec` with two floats, or a `WeaponSpec` (M1-10).

Same instinct as M0-05's `ref`-returning trap: the copy nobody is watching is the one that goes wrong.
- `LocKey` is validated for *shape* only — non-empty, no whitespace — never against a table, per rule 3. The whitespace ban is not cosmetic: a trailing space picked up from an authored inspector field would become a key that resolves in no language, and the resulting blank label gives no clue why.

### 2026-09-07 · M0-12 · Composition installers · PR #_n_

**Built:** The wiring, and the first time the project's objects are built by a container rather than by a test. `BootInstaller` in `Soulvail.Game.Composition` converts the authored `CharacterDefinition`s into a `ContentCatalog` and registers it with `PendingRun` for the life of the app; `RunInstaller` registers everything one run owns — `DomainEventHub` as `IDomainEvents` and itself, `IntentBuffer` as `IIntentSink` and itself, a `WorldSnapshot` at the 64-enemy cap, an `IRandom` seeded from the pending run, and `RunSession` as `IRunSession` — all `Lifetime.Scoped`, so disposing the run scope ends the run. `PendingRun` is the slot the menu writes and the run reads, and the one thing that has to survive a scene load. **Deviations from spec:** seven, listed in the task's *As built* footer. The two that change behaviour rather than test coverage:

1. **`WorldSnapshot` is registered through a factory at `Lifetime.Scoped` rather than as an instance.** Rule 5 says "instance", the section header says "all `Lifetime.Scoped`", and VContainer cannot satisfy both — `RegisterInstance` is hardwired to Singleton. Resolved toward the header.
2. **Three guards in `BootInstaller.Install`** — null builder, null list, null element — none of them listed. The element guard is the one that matters: without it `ToSpec()` on an empty array slot throws an NRE from inside a loop, and `ContentCatalog`'s own null-entry guard is unreachable because conversion happens first.

**Learned:**

- **VContainer only disposes what it constructed, and this is the sharpest trap the container has.** `CreateTrackedInstance` adds an object to the scope's disposal list only when the registration's provider is not an `ExistingInstanceProvider` — that is, only when the container built it. So `builder.RegisterInstance(new DomainEventHub())` compiles, resolves, aliases the port and the concrete type to one object, passes ten of this task's eleven rows, and **is never disposed**: every run would leak every subscription into the next, and the symptom would be a HUD that updates twice, then three times, with nothing in the log. Proved by mutation rather than by reading: swapping the registration reddens exactly one row, `Run_ScopeDispose_DisposesHub`, and leaves everything else green. That row was flagged in the task prompt as the one asserting VContainer's behaviour rather than ours, and it turns out to be the most load-bearing row in the fixture. **The rule for every adapter after this: anything that owns a resource is registered as a type, never as an instance.** `ContentCatalog` is registered as an instance deliberately and safely — it is immutable, not `IDisposable`, and shared for the life of the app, so there is nothing to own.
- **`As<T>()` alone does not make the concrete type resolvable, and the failure would look like a missing registration.** `Registry.Build` inserts the implementation type as a *null guard* entry whenever `InterfaceTypes` is non-empty, so `Resolve<DomainEventHub>()` throws on a container that plainly contains one. `.AsSelf()` is what adds it back. Read out of the source rather than discovered, which is why both `.As<…>().AsSelf()` pairs were written that way from the start.
- **VContainer refuses a duplicate implementation-type key at build time**, so the "registered twice, two instances, port and views disagree" bug cannot happen silently for one concrete type: the second mutation tried (`As<IDomainEvents>()` and `AsSelf()` as two registrations) throws `ArgumentException: An item with the same key has already been added` and reddens all seven run-scope rows at scope construction. Worth recording because it bounds what `Run_EventsPortAndHub_SameInstance` actually owns — the container catches the same-type case, so that row's real job is the divergence that *does* build: a Func registration for the interface beside a type registration for the class.
- **A `Lifetime.Singleton` registered inside a child scope resolves scope-locally, not from the root.** `ScopedContainer.ResolveCore` consults its own registry first and only delegates to the parent when the registration is not its own. So the rejected `RegisterInstance` form would have behaved per-run despite its Singleton label — the label was the defect, not the lifetime, which is exactly why deviation 1 changes the spelling and not the behaviour.
- **`PendingRun` crossing the scope boundary is the half worth testing.** Registered Singleton in boot, it resolves through the run scope's parent chain, so the menu's write and the run's read hit one object. `Boot_PendingRun_IsSingleton` pins it at the root, but `Run_Random_SeededFromPendingRun` is the row that would actually catch a re-registration in `RunInstaller` — the mistake that would give the run its own empty `PendingRun` and an unseeded generator.

1. **`SceneLoader` does not use `Application.CanStreamedLevelBeLoaded`** — see *Learned*. The specced API is inert and would have rejected every load.

**Learned:**

- **`Application.CanStreamedLevelBeLoaded` is inert in the Editor, and it fails in the direction that looks like correctness.** It returned `false` for `Boot`, `Menu` and `Run` — by bare name *and* by full asset path — at a moment when `SceneManager.sceneCountInBuildSettings` was 3 and `GetScenePathByBuildIndex` listed all three correctly. A `LoadAsync` guarded by it rejects every scene in the game, and the symptom is a Boot screen that never advances with an `ArgumentException` blaming Build Settings that are in fact correct. **This is M0-02's lesson in a new API**: the obvious probe answered confidently and wrongly, and the only reason it was caught is that the build-settings write was verified by asking three different APIs the same question instead of one. `SceneUtility.GetBuildIndexByScenePath` is honest but path-only — `-1` for a bare name — so `IsInBuild` walks the build list and compares both forms. Worth generalising: **when a Unity API answers a yes/no question about project state, prove it says "yes" to something true before trusting its "no".**
- **A `VContainerSettings` asset does nothing unless it is in `PlayerSettings.GetPreloadedAssets()`.** `VContainerSettings.Instance` is assigned in `OnEnable`, and in the Editor the only thing that triggers it is `LoadInstanceFromPreloadAssets()` at `RuntimeInitializeOnLoadMethod(BeforeSceneLoad)`. - **`LifetimeScope.GetRuntimeParent` reaches the settings root last, after `parentReference` and `FindParent()`.** That ordering is what rule 1 is really built on, and it is why `RunScope` has no parent assigned in the Run scene: assigning one would break Play-in-Run rather than help it. Read from the package source, not executed — no Play-mode verification was possible from this session.
- **The Unity MCP's `RunCommand` assembly does not reference VContainer**, so `AddComponent<RunScope>()` fails to compile with "no implicit reference conversion to `UnityEngine.Component`" plus a missing-assembly error naming `LifetimeScope`. `gameObject.AddComponent(Type.GetType("Soulvail.Game.Composition.RunScope, Soulvail.Game"))` works and binds correctly. Every future task that builds a scene or prefab around a VContainer type through the MCP hits this.
- **Unity's API level has no non-generic `TaskCompletionSource`** — `TaskCompletionSource<bool>` is the shape. Its `RunContinuationsAsynchronously` is deliberate: without it the awaiting code resumes inline inside `AsyncOperation.completed`, which Unity raises from inside its own scene management, so a chained load would be re-entrant.
- **Deleting a template asset is rarely self-contained.** `SampleSceneProfile` looked like scene-local sample dressing and was in fact the `m_VolumeProfile` of *both* URP render pipeline assets. The removal was specced in one line; satisfying it honestly meant touching two files the spec never mentions. Checking `grep -rl <guid>` across `Assets` and `ProjectSettings` before any deletion cost one command and would have cost a broken render pipeline otherwise.
- **TMP Essential Resources were never imported in this project** (`TMP_Settings.instance` null, no `Assets/TextMesh Pro/`), despite `Unity.TextMeshPro` being referenced by `Soulvail.Game` since M0-01. `TMP_PackageResourceImporter.ImportResources(true, false, false)` does it non-interactively. The 44 assets include a `.ttf` and a `.png`, both correctly routed to LFS by `.gitattributes`.
- **Vendoring a package's assets breaks the pre-commit whitespace check, and the fix is `.gitattributes`, not the hook and not the files.** TMP's shaders ship with trailing whitespace, space-before-tab indents and blank lines at EOF; `git diff --cached --check` flagged ten of them and refused the commit. "Fixing" them is the wrong move twice over — they are third-party, and Unity silently reverts any edit on the next TMP reimport. `"Assets/TextMesh Pro/**" -whitespace` unsets the attribute for that tree only, which is the mechanism `git diff --check` is built to honour; our own `.cs` and `.shader` files stay `unspecified` and still checked. Verified with `git check-attr` and by re-running the hook's exact pathspec. **Any future vendored tree needs the same line** — the hook's own exclusion list is for Unity-serialised *formats*, which is a different axis and should not be extended with vendor paths.

### 2026-09-08 · M0-14 · Input actions · PR #_n_

**Built:** The game has one input asset and one place that reads it. `Soulvail.inputactions` holds a single `Player` map with all eight actions M0–M3 will ever need — `Move` (Value/Vector2), `MovementSkill`, `Skill1`–`Skill4`, `Focus`, `Pause` — bound for gamepad and keyboard, under two control schemes: **Touch** (`Touchscreen` OR `Gamepad` OR `Pointer`, because M0-15's floating stick will feed the system through `OnScreenControl` as a *virtual gamepad* rather than as touches) and **KeyboardMouse** (`Keyboard`, `Mouse` optional). Only `Move` is consumed — the other seven exist so M1-09, M1-16 and M3-10 add a reader here rather than reopening the asset. The URP template's `InputSystem_Actions.inputactions` is gone and Project-wide Actions points at ours. 136 EditMode tests, up from 131.

**Deviations from spec:** two, both in the tests rather than the shape.

1. **`InputAdapter.Dispose` does not call the generated `SoulvailActions.Dispose()`.** That method calls `Object.Destroy` unconditionally, which is right in a player and wrong in the Editor outside play mode — see *Learned*. The adapter destroys `_actions.asset` itself, choosing `DestroyImmediate` under `#if UNITY_EDITOR && !Application.isPlaying`. The public API in the spec is unchanged; only what "dispose the actions" compiles to differs.
2. **`InputAdapterTests` neutralises the default deadzone in setup, and `Move_IsClampedToUnit` carries an extra assertion saying what it does *not* prove.** Both are consequences of `StickDeadzone`, below. The five specced rows exist with the specced Given/When/Then.

**Learned:**

- **`Object.Destroy` in edit mode does not throw — it logs an `Error` and destroys nothing.** Measured directly: `Object.Destroy(so)` left `so == null` false and printed *"Destroy may not be called from edit mode! Use DestroyImmediate instead."* at `LogType.Error`. Two consequences, and the second is the nasty one: the object leaks, **and** an EditMode test that disposes fails on the unexpected error log rather than on anything it asserted. The Input System's own generated wrapper has this bug by construction, so **every generated `*.Actions` class in this project must be disposed through a context-aware destroy, never through its own `Dispose()`.** The same applies to any future adapter that owns a `ScriptableObject` it created with `CreateInstance`.
- **A Value action enabled while a control is already deflected reads zero until the next `InputSystem.Update()`.** The initial state check runs on the update *following* the enable, not during it. `Move_ZeroWhileDisabled` failed on exactly this and the fix is two `InputSystem.Update()` calls, not a change to the adapter — but the lag is real and will be visible in the game: M0-16 enables the adapter as a run starts, so a thumb already on the stick moves the player one frame late. Worth remembering when M0-20 tunes feel.
- **`StickDeadzone` caps its own magnitude at 1, so `Move`'s `ClampMagnitude` cannot be made to do observable work through a gamepad stick.** `GetDeadZoneAdjustedValue` returns exactly 1 for any input above `max`, whatever `max` is set to — the clamp is unreachable from above. The spec's `Move_IsClampedToUnit` row ("stick at (1, 1), magnitude 1.41") therefore describes a value the action never emits, and the test as written would keep passing if the clamp were deleted. Rather than delete a vacuous row or a defensive clamp, the test asserts the contract *and* asserts the pre-clamp, so the reason it cannot fail is recorded in the file instead of being rediscovered. The clamp stays because both current sources being unit-bounded is a property of today's bindings, not of the port.
- **The same processor silently rescales everything else.** With defaults (`min` 0.125, `max` 0.925) a stick set to (0.3, 0.6) reads back as roughly (0.305, 0.610) — so the specced `Move ≈ (0.3, 0.6)` is only true with deadzones neutralised, which `InputTestFixture` does **not** do for you despite resetting nearly everything else. Setting `defaultDeadzoneMin = 0` / `defaultDeadzoneMax = 1` in setup is safe: the fixture snapshots and restores `InputSystem.settings` along with the rest of the state.
- **The actions asset was built through `InputActionSetupExtensions` and written with `ToJson()`, not hand-authored**, and the wrapper was produced by turning `generateWrapperCode` on in a hand-written `.meta` rather than by writing the `.cs`. Both keep the serialisation canonical — the same bytes the Inspector would have written — which matters because this is the first file in the project whose format we do not own.
- **`*.inputactions` was already excluded from the pre-commit whitespace check and already declared `text` in `.gitattributes`.** `ToJson()` emits no final newline; the exclusion is what makes that a non-issue. Nothing needed adding.
- **The MCP `RunCommand` test-runner namespace is `UnityEditor.TestTools.TestRunner.Api`**, not `UnityEditor.TestTools.TestRunnerApi`, and `NUnit.Framework.Interfaces` is not referenced from that assembly — comparing `ITestResultAdaptor.TestStatus.ToString()` avoids needing it. Together with M0-02's `CompilationPipeline` qualification note, that is the second and third way the MCP's assembly differs from a normal Editor script.

### 2026-09-08 · M0-15 · Floating stick · PR #_n_

**Built:** The thumb half of the control loop. `StickShaper` is the stick's arithmetic with no Unity object behind it — `Shape` (dead below 8 dp, linear to 40 dp, flat at 1 past it, direction preserved exactly), `Recenter` (past 60 dp the origin is dragged along so it sits exactly 60 dp behind the thumb) and `PixelsPerDp` (dpi/160, falling back to 1 on the Editor's unknown density) — and it is tested to 1e-4 on every number in CC §2.1–2.3 and §7. `FloatingStick` is the component that owns what needs a frame: which finger has the stick, where its origin currently is, and where the two sprites go. It captures one pointer and ignores the rest, reports zero on touch-down, recentres and reports the shaped deflection on drag, and sends a final zero on pointer-up *and* on disable — before `base.OnDisable` tears the virtual device down, which is the ordering that stops a HUD disabled mid-drag from leaving the player walking. It writes to `<Gamepad>/leftStick` through `OnScreenControl` and never reads the Input System, so it meets `InputAdapter` (M0-14) only through the actions asset: the stick is the gamepad the `Touch` scheme already lists. `SafeAreaFitter` pins its `RectTransform` to `Screen.safeArea` so nothing lands under a notch — in landscape the cutout eats the *left* edge on one rotation, which is exactly where the joystick region is. `Hud.prefab` assembles them: an overlay Canvas scaling to 1920×1080 at match 0.5, a `SafeArea` child, a `Region` covering the left 45 % as a transparent-but-raycastable `Image`, and `Base`/`Knob` discs hidden until touch. 148 EditMode tests, up from 136. The prefab is not in any scene yet — M0-16 places it and adds the `EventSystem`.

**Deviations from spec:** four.

1. **A fifth file, `Game/Controls/SafeAreaFitter.cs`** — raised before writing it and approved by the owner. Rule 10 asks for the `SafeArea` child to be "fitted to `Screen.safeArea` on enable and on resolution change" and Unity ships no component that does it, so the Files table's four files could not satisfy the prefab's own rules. Written as its own component rather than folded into `FloatingStick`, because every later HUD element (M1-17's bars, M1-16's skill buttons) lives under the same `SafeArea` and must not depend on the stick existing to be positioned. Task is 5 files, still size M.
2. **The dp sizes in rule 11 are applied at runtime by `FloatingStick`, not authored into the prefab.** A *Scale With Screen Size* canvas measures in reference pixels, not dp: a `sizeDelta` of 120 on a 1080p phone is 120 physical pixels, which at ~400 dpi is 48 dp — 2.5× too small. That matters here rather than being cosmetic, because the ring's 120 dp diameter is exactly twice `MaxRadiusDp`: its edge is where recentring begins, so a ring at the wrong scale actively lies about the mechanic. `OnPointerDown` therefore sizes both sprites from `dp × pxPerDp ÷ canvas.scaleFactor`. The prefab still authors 120/52 as its resting values so it reads correctly in the Editor at 1× .
3. **`Base` is a disc at 60 % alpha, not a ring.** There is no built-in ring sprite, and M0 adds no art. Both sprites use Unity's built-in `UI/Skin/Knob.psd` circle, told apart by alpha (0.6 base, 0.9 knob), which introduces no asset file. The ring treatment belongs with the rest of the HUD art.
4. **A twelfth test, `ShapeAndRecenter_DoNotAllocate`, is not in the spec's Tests table.** Behaviour rule 9 ("no per-frame allocation") is the only rule the table leaves unmeasured, because the drag path needs an `EventSystem` and cannot be driven from EditMode. The test covers the half that can be — every `StickShaper` call the component makes per drag frame — through `AllocationAssert`, and its own remark records what it does not cover.

**Learned:**

- **An unfocused Unity Editor does not tick, and `TestRunnerApi` silently never starts.** `api.Execute(...)` returned successfully, `RunStarted` never fired, and the results file sat unwritten for three minutes across two attempts with nothing in the Console. The diagnostic that settled it: an `EditorApplication.delayCall` queued from the same command also never fired, and `InternalEditorUtility.isApplicationActive` was `False`. The MCP can still service one-shot `RunCommand` calls in that state — which is why the prefab authored fine and the compile checks passed — so the Editor *looks* alive while anything needing the editor loop is frozen. **Focusing the Unity window is a precondition for the test step, not a nicety; when a run produces no `RunStarted`, check `isApplicationActive` before suspecting the callback.** The run completed in seconds once focused.
- **The MCP `RunCommand` wrapper namespace shadows `UnityEngine.UI.Image`.** `Image` alone fails with `CS0118: 'Image' is a namespace but is used like a type`, because the injected `Unity.AI.Assistant.Agent.Dynamic.Extension.Editor` namespace puts a `…Image` namespace in scope ahead of the `using`. Same shape as M0-02's `CompilationPipeline` collision — the third of these — so the rule generalises: **in a `RunCommand` script, fully qualify any type whose short name is also a namespace segment anywhere in Unity's assemblies.**
- **`OnScreenControl.OnEnable`/`OnDisable` are `protected virtual`**, so overriding is safe as long as `base` is called — but the *order* is load-bearing. `base.OnDisable()` nulls `m_Control`, after which `SendValueToControl` is a silent no-op, so the zero has to be sent first. The base class does reset the control to default on disable, but only in the branch where the virtual device survives because another on-screen control still uses it; when the stick is the only one, the device is destroyed instead. Belt and braces was cheap and the failure mode — a player walking into a wall through the whole next scene — is not.
- **`Screen.safeArea` has no change event**, so `SafeAreaFitter` polls. The check is three struct comparisons against cached values per frame and does nothing until one moves, which is cheaper than re-applying blindly and dirtying the layout every frame. It also refuses to divide by a zero-sized screen: that is reported on the odd frame during a resolution change and while backgrounded, and NaN anchors on a `RectTransform` never recover.
- The deadzone and radius boundaries are deliberately opposite and both are tested: `Shape` is *closed* at 8 dp (exactly 8 is still zero, so a resting thumb cannot twitch the player) while `Recenter` is *open* at 60 dp (exactly 60 does not move, so holding at full extension does not drag the origin every frame). Either one flipped would be invisible in play and obvious in a log.

- **`SafeAreaFitter` has no tests.** Its anchor math is four lines and reachable only through `Screen`, which EditMode cannot set. Either M0-16 extracts the rect→anchors computation as a pure static and tests it, or it is left to the Device Simulator's notch profiles. Worth a decision rather than a drift.
- **Behaviour rules 4–9 are verified by hand, not by the suite.** They need an `EventSystem`, a canvas and a live pointer; M0-16 is the first task that has all three in a scene, and is where a PlayMode test for capture/recentring/release would go if it is judged worth the cost.

### 2026-09-08 · M0-16 · Snapshot builder, player view, run ticker · PR #_n_

**Learned:**

- **The parked `RunState.Motor` question is settled: nothing in `Soulvail.Game` reads the handle, so it is now `internal`, with `PlayerVelocity` and `PlayerFacing` as the public reads.** `PlayerView` takes both values from the intent and never touches `RunState`, which is what the task was asked to prove. The names differ from the spec's suggested `Velocity` / `Facing` on purpose: `RunState` already calls the player's position `PlayerPosition`, and `WorldSnapshot.PlayerVelocity` is the same quantity coming back the other way one frame later, so the qualified names keep both symmetries. `RunSessionTests` changed on two lines, as M0-10 predicted. **The seal is now closed in both directions — `RunState`'s own fields and everything reachable through them — and any future field that hands out a mutable object needs the same question asked of it.**
- **A `MonoBehaviour`'s `Awake` never runs in EditMode, so nothing that caches a component in it can be unit-tested.** `PlayerView.Apply` needs `_controller`, which is null until play mode, and `AddComponent` in an EditMode test does not change that. This is not a flaw to work around — it is the reason the spec leaves `Apply` and `RunTicker` to manual verification — but it does mean the *value* assertion in `Build_CopiesPlayerPositionAndVelocity` cannot be made non-trivial: a fresh view genuinely reports zero velocity, so the row pins that the field is written and that nothing leaks into it, and says so in an asserted note rather than a comment. **Any future test of a view's apply path is a PlayMode test or it is nothing.**
- **`PlayerView.Velocity` is deliberately not `CharacterController.velocity`.** The controller reports resolved displacement over `dt`, which collapses to zero the instant the player leans on a wall — core reading that back as `WorldSnapshot.PlayerVelocity` would see someone who had stopped trying to move rather than someone who is blocked. Position is a sense because collision genuinely changes it; intended velocity is not collision's to edit. The first mechanic that asks "is the player moving?" is where the difference would have surfaced, and it would have looked like a core bug.
- **`InputSystemUIInputModule` assigns the package's `DefaultInputActions` when it is added with no asset**, so the `EventSystem` needs no wiring and `Soulvail.inputactions` needs no UI map. Verified on the serialized field rather than assumed: `m_ActionsAsset` reads `DefaultInputActions` immediately after `AddComponent`.
- **The play-mode verification hit M0-15's unfocused-Editor trap again, in a new shape, and then worked once the window was focused.** Unfocused, `EnterPlaymode` succeeded and the game genuinely ran for a burst — 1492 frames, 25 s — and then froze with `Time.time` identical across three later `RunCommand` calls minutes apart; `EditorApplication.QueuePlayerLoopUpdate` does not thaw it, and input injected in the meantime is queued and never consumed. **Anything that needs frames to elapse needs the window focused, exactly as the EditMode runner does.**
- **Manual steps 1–4 were measured, not eyeballed**, by an `EditorApplication.update` driver that injects a known stick deflection through `Gamepad` and samples the view: top speed 5.400 m/s, \|v\| 0.0000 and 0.00000 m of slide after release, facing 0.00 moving +Z and 90.00 on stick +X and held after release, the pillar stopping the player at 1.995 m from its centre and both walls at ±17.505, every collision case with 0.00000 m of jitter. The numbers are in the spec's *As built*. **Two harness lessons, both of which produced convincing-looking wrong answers first:** a driver that only queues a stick event when the stick is non-zero never sends the release, so the "no slide" row measured a stick that was still held and reported a 2.6 m slide against code that was correct; and phases timed in *seconds* can be retired by a single hitched frame, because `Time.time` advances by a clamped delta — the wall row failed at 16.389 m purely because the player was still in transit. **Frame-counted phases, and always drive the input to its actual value, including zero.**

**Built:** The project produces an installable Android APK from one menu item. `AndroidBuild` is `Soulvail.Editor`'s first script — that assembly emits code for the first time, so all six now do — and it is deliberately thin: scenes come from `EditorBuildSettings` rather than a hard-coded list (a build that disagreed with the Editor about which scenes exist could not reproduce what was playtested), `Development | AllowDebugging` when development, target architectures pinned for the build and restored in a `finally`, and a **throw** rather than a log when `summary.result != Succeeded` — because a failed build leaves the previous APK at the output path, and an error buried in build spam is how someone installs last week's build and debugs the wrong one. **Deviations from spec:** three, all forced — detail in the spec's *As built*. (1) **Rule 4 is unimplementable: Unity 6.3 cannot build x86-64 for Android**, so both build kinds are ARM64 and the *Emulator setup* section's premise is void. (2) Orientation is `AutoRotation` restricted to the two landscapes, because the table's "Landscape Left" and manual step 8 contradict each other. (3) Directory creation sits in `Build` rather than `BuildDevelopmentApk`.

**Learned:**

- **`AndroidArchitecture.X86_64` is Magic Leap's, it is deprecated in Unity 6.3, and it fails *late*.** Assigning `ARM64 | X86_64` succeeds, reads back as `ARM64, X86_64`, and survives a round-trip through `PlayerSettings` — then the build throws `UnityException: x86-64 (Magic Leap) support is now limited … will be unset in player settings`. `AndroidAllowedArchitectures: -13` in `ProjectSettings.asset` is the mask that says so (`~12` — x86 and x86-64 excluded), and it predates this task. Same family as the `GC.GetAllocatedBytesForCurrentThread` and `Application.CanStreamedLevelBeLoaded` traps: **an API that accepts a value and echoes it back has not agreed to honour it.** The consequence is strategic — the reference-device plan assumed BlueStacks would run x86-64 natively, and it cannot.
- **A Unity Android build cannot resolve its Gradle dependencies on this connection without machine-local configuration.** Unity 6.3 generates a `build.gradle` requesting AGP 9.0.0 from `gradlePluginPortal()`, `google()` and `mavenCentral()` — three remote repositories, no offline fallback. The failure presents as `Plugin [id: 'com.android.application', version: '9.0.0'] was not found`, which reads as "that version does not exist". It does exist. What actually happens: Google Maven answers **HTTP 404 for every path**, including its own `master-index.xml`, and larger JAR bodies get killed mid-transfer (`Remote host terminated the handshake`). The fix is two user-level files, `~/.gradle/gradle.properties` and `~/.gradle/init.gradle`, neither in this repo.
- **The decisive lesson: every negative network probe needs a positive control.** Concluding "AGP 9.0.0 is not published" from a 404 was wrong, and what exposed it was probing a version that certainly exists (8.6.0) and getting the *same* 404 — the probe was measuring a wrong URL layout, not availability. Later, `repo.maven.apache.org/junit/4.13.2` → 200 against `maven.google.com/master-index.xml` → 404 is what actually localised the block to Google's hosts. **A 404 from a filtered host and a 404 from a missing artifact are indistinguishable without a control.**
- **Java's SOCKS support resolves hostnames locally, which is why a healthy proxy still failed.** With `systemProp.socksProxyHost` the mirror errors appeared as a bare `> maven.aliyun.com`, i.e. `UnknownHostException` — local DNS is filtered here and SOCKS never got the chance to resolve. Switching to `systemProp.https.proxyHost` on the same port fixed it outright (`BUILD SUCCESSFUL in 11s` on the task that had been failing), because an HTTP proxy sends `CONNECT host:443` and the *proxy* resolves. v2rayN's 10808 is a mixed SOCKS+HTTP inbound and the only listening port, so this is a one-word change with a completely different outcome.
- **Repository order matters, because Gradle aborts a resolution on a network error instead of falling through to the next repository.** Mirrors appended *after* `google()`/`mavenCentral()` are never reached when those two are the ones failing; the init script clears and rebuilds the list with mirrors first and the originals retained as fallback.
- **The tight loop is `gradle help` in `Library/Bee/Android/Prj/IL2CPP/Gradle`, not a Unity build.** Plugin resolution happens while the build script is evaluated, so `help` reproduces the whole dependency-resolution failure in 10–60 s instead of 10 minutes, using Unity's own bundled `java.exe` and `gradle-launcher-9.1.0.jar`. Reach for it before any future Android build investigation.
- **Unity's Console is not where a Gradle failure's cause lives — `Editor.log` is.** The MCP truncates a large `RunCommand` result and the Console had been cleared; `%LOCALAPPDATA%\Unity\Editor\Editor.log`, searched for `What went wrong`, held the full stderr including the exact unresolvable coordinate. The MCP also reports a build that merely emitted *warnings* as `UNEXPECTED_ERROR`, so its top-level verdict cannot be read as the build's verdict.
- **`System.Reflection` is an unauthorized namespace in `Unity_RunCommand`** — already on the watch list beside `System.Diagnostics`/`System.Net`, hit again here. `EditorApplication.ExecuteMenuItem` is the better tool regardless: it exercises the real menu route instead of a reflective call that bypasses it.
- **A platform switch and a disk-full build leave collateral in the working tree.** Switching to Android recalculated URP's shader-prefilter flags in `Mobile_RPAsset`, populated `m_RuntimeSettings` in `UniversalRenderPipelineGlobalSettings`, added `m_ShaderBuildSettings` to `GraphicsSettings`, **flipped `UnityConnectSettings.m_Enabled` from 0 to 1** (the source of the lone remaining Console warning), and created `Assets/Resources/PerformanceTestRun*.json` plus `Assets/_Recovery/0.unity`. The first three are legitimate platform-switch output; analytics being switched on is not, and the last two are junk. **`.gitignore` covers `*.apk` but not `Builds/`**, so `Soulvail_BurstDebugInformation_DoNotShip/` shows as untracked — the spec's claim that the output directory is "already git-ignored" is only half true.
- **An IL2CPP Android build needs several GB of headroom.** The first attempt died with `No space left on device` (Win32 error 112) partway through clang, which is what produced the `_Recovery` artifact; `Library/Bee` alone reached 1.36 GB and the Gradle cache 1.8 GB.

**Learned:**

- **The APK does not launch, and the reference-device plan was wrong about why.** M0-19 predicted that BlueStacks would have to translate ARM64 and that IL2CPP under translation was the risk. `adb logcat` says translation is fine: `IL2CPP: JNI_OnLoad` and `Unity: Context Type: GameActivity` both appear, so houdini executed our arm64 code. Nothing in `Soulvail.Core`, the scopes or the views is implicated. Android graphics APIs are `[Vulkan, OpenGLES3]` (`m_APIs: 150000000b000000`, `m_Automatic: 0`), Vulkan first, so a release build or an `androidVulkanDenyFilterList` entry are the two cheap routes out; M0-20a takes them in that order.
- **The `OnBackInvokedCallback` `NoClassDefFoundError` in that same log is a red herring, and a costly-looking one.** It arrives first, carries a 25-frame stack through `UnityPlayer.initialize`, and reads exactly like a fatal error — but it is logged at `I` level, Unity catches it, and execution continues for another full second into graphics init before the real crash. **The first exception in a logcat is not the cause of death; the `F`-priority frames are.** Filtering `logcat -d "*:E"` is what separated them.
- **A negative result about an emulator needs the same positive control M0-19's network probing needed.** "BlueStacks cannot run our APK" and "BlueStacks cannot run ARM64 IL2CPP" are different claims, and only the log distinguishes them. Asserting the second from the first would have sent M0-20a hunting for an x86 build that Unity 6.3 cannot produce — the exact dead end M0-19 already paid for.
- **BlueStacks' ADB accepts connections long before it serves them.** `adb devices` reported `device` and `get-state` said `device` while `shell`, `exec-out` and `logcat` all returned `error: closed`. That is the daemon up with debugging *off*, and it is indistinguishable from a healthy device until you ask it for something. Enabling Settings → Advanced → Android Debug Bridge and restarting the instance fixes it. Two handles onto one instance (`127.0.0.1:5555` and `emulator-5554`) is normal and either works once ADB is genuinely on.
- **This BlueStacks instance is Android 9 / SDK 28, not the Android 11 the Current State recorded**, and it reports itself as a Samsung `SM_G998B` with `ro.product.cpu.abilist = x86_64,x86,arm64-v8a,armeabi-v7a,armeabi`. The `arm64-v8a` entry is why `pm install` accepted an ARM64-only APK at all — **the abilist advertises translation, it does not promise execution.** Fourth instance of the family the watch list has been collecting: an API that accepts a value and echoes it back has not agreed to honour it.
- **The Known-issues block this task inherited was stale in both of its claims, and git said so in one command.** The URP and `GraphicsSettings` output was *committed* in `5f8a331`, `/Builds/` was added to `.gitignore` in that same commit, and the two junk artifacts are gone from disk — the working tree was already clean at the start of this task. `UnityConnectSettings.m_Enabled` is `0` in `HEAD` and was `0` at repo init, so the analytics flip was reverted before it was ever committed. The `"Diagnostics Data is enabled…"` warning that PROGRESS attributed to it actually comes from `InsightsSettings.m_EngineDiagnosticsEnabled: 1`, which has been `1` since repo init and only fires **during an Android build**, never on a reimport. **A "known issue" describing uncommitted working-tree state has a short shelf life; check it against `git status` before repeating it.**
- **The Editor's Game view was set to portrait 1440 × 2960 while the build is landscape-locked.** Every framing and stick-band judgement made in that view measures the wrong aspect, and M0-18's 25.6 × 32.8 m figure assumes 16:9 landscape. Worth a glance at `Screen.width/height` before trusting any feel measurement taken in the Editor.
- **The MCP's `result.Log` does not honour format specifiers.** `"{0:F2}"` is emitted literally rather than substituted, while a bare `{0}` works — so numeric evidence has to be pre-formatted with `ToString("F2")` or read as a raw `Vector3`. Cost a wasted probe here; noted so it does not cost another.
- **The unfocused-Editor trap is now four-for-four, but it is not absolute.** `isApplicationActive` read `False` at the moment the EditMode run was requested and the run completed anyway, ten seconds later. Play mode and the PlayMode runner still genuinely need sustained focus. The reliable technique is unchanged and worked throughout: request the run, then read the results **off disk** with a `Temp/` file rather than through another MCP call, so polling never steals focus back.
